## Decisões fixadas neste plano (o codeAgent não deve reabrir)

### D1. Evolução do schema — sem migration sqlx nova (ver "Pontos de atenção" A1)
- As colunas novas de `notebook_tasks` entram **só** pelo `ensureTasksTables` (`src/storage/tauri.ts`), de forma idempotente: o `CREATE TABLE IF NOT EXISTS` continua idêntico ao da v18; depois dele, `PRAGMA table_info(notebook_tasks)` lista as colunas existentes e, para cada coluna da lista `TASKS_EXTRA_COLUMNS` que faltar, roda `ALTER TABLE notebook_tasks ADD COLUMN <ddl>`. Memoização e reset em falha seguem o padrão atual.
- `TASKS_EXTRA_COLUMNS` cresce por fase:
  - Fase 2: `scheduled_date TEXT`
  - Fase 3: `task_group TEXT` (`group` é palavra reservada do SQL)
  - Fase 4: `important INTEGER NOT NULL DEFAULT 0`, `recurrence TEXT`, `recurrence_next_id TEXT`
- **Não** adicionar `Migration { version: 19.. }` em `src-tauri/src/lib.rs`. Acrescentar apenas um comentário logo abaixo da v18: "colunas posteriores de notebook_tasks são adicionadas por ensureTasksTables (storage/tauri.ts) — ALTER TABLE não é idempotente e as migrations não rodam no DB de produção (checksum v11)".
- Preservação dos dados de produção: `due_date` **não muda** (vira semanticamente o deadline); colunas novas nascem `NULL`/`0`. Nenhum UPDATE/rebuild de tabela.

### D2. Modelo de dados (TypeScript)
`Task` em `src/types/index.ts` ganha, por fase:
- Fase 2: `scheduledDate: string | null` — "fazer em" (`YYYY-MM-DD`). `dueDate` continua o nome do campo e passa a significar **deadline** (comentário no tipo).
- Fase 3: `group: string | null`
- Fase 4: `important: boolean`, `recurrence: TaskRecurrence | null`, `recurrenceNextId: string | null`, com
  ```ts
  export type TaskRecurrence =
    | { freq: 'daily' }
    | { freq: 'weekly'; days: number[] } // 0 = domingo … 6 = sábado, ordenado, ≥ 1 dia
    | { freq: 'monthly' }                 // mesmo dia do mês da data-âncora
  ```
  Persistido como JSON em `recurrence`; `rowToTask` faz `JSON.parse` em try/catch (inválido → `null`).
- `TaskPatch` (`src/lib/tasks.ts`) inclui cada campo editável quando ele nasce.
- `NewTaskInput` (`src/hooks/useTasks.ts`) e `createProjectTasks` (App) aceitam os campos novos opcionais (default `null`/`false`).

### D3. Data de planejamento e atraso (helpers puros em `src/lib/tasks.ts`)
- `planDate(t)`: Fase 1 = `t.dueDate`; a partir da Fase 2 = `t.scheduledDate ?? t.dueDate`. **Todo agrupamento/contagem usa `planDate`**, nunca `dueDate` direto — assim a Fase 2 só troca a implementação.
- `overdueKind(t, todayKey): 'deadline' | 'plan' | null` (Fase 2; na Fase 1 existe só o caso `'deadline'`):
  - `'deadline'` (vermelho, `--accent-danger`): aberta e `dueDate < today`.
  - `'plan'` (amarelo, novo token `--accent-late: #e6c449`): aberta, não é `'deadline'`, e `scheduledDate < today`.
- `isOverdue(t, today)` = `overdueKind(t, today) !== null`.
- `scheduledAfterDeadline(t)` = `scheduledDate && dueDate && scheduledDate > dueDate` → aviso "After deadline" (permitido, só sinalizado).

### D4. Semana e contadores
- Semana começa no domingo (como o Calendar). Helpers novos em `src/lib/tasks.ts`: `addDaysKey(key, n)`, `startOfWeekKey(key)` (domingo), `endOfWeekKey` (já existe), `weekDayKeys(startKey)` (7 chaves). `parseKey` deixa de ser privado só se outro módulo precisar.
- Contadores da faixa de resumo (`computeTaskSummary(tasks, todayKey)` em `src/lib/tasks.ts`), sobre as tasks do filtro de projeto ativo:
  - **Overdue**: abertas com `isOverdue`. Chip vermelho se houver alguma `'deadline'`, senão amarelo.
  - **Today**: abertas não-atrasadas com `planDate === today`.
  - **Week**: abertas não-atrasadas com `today <= planDate <= fim da semana` (inclui Today).
  - **Doing**: `status === 'doing'`.
  - **Done this week**: `status === 'done'` com `completedAt` entre domingo 00:00 e sábado 23:59 da semana corrente.
  - **Barra da semana**: `doneThisWeek / (doneThisWeek + abertas com planDate <= fim da semana, incluindo atrasadas)`; rótulo `Week 1/5`. Total 0 → barra oculta.
- Clicar num chip aplica um filtro de lista (`'overdue' | 'today' | 'week' | 'doing' | 'doneWeek' | null`); clicar de novo limpa. Com filtro ativo a lista mostra um único grupo com o rótulo do chip.

### D5. Regras de `rescheduleCount` (Fase 2, em `applyTaskPatch`)
- Deadline: regra atual mantida (havia `dueDate`, novo valor não-nulo e diferente → +1).
- Do date (rollover): havia `scheduledDate` e o novo valor é não-nulo e **posterior** → +1. Antecipar, definir o primeiro do date ou limpar não contam.
- Um único contador alimenta o badge `↻N`.

### D6. Layout transversal — máximo espaço para o título
Componente compartilhado `TaskLine` (`src/components/TasksView/TaskLine.tsx` + `.module.css`), usado na lista, no Week board, no Kanban e no bloco `/tasks`:
- Linha 1: checkbox (alinhado ao topo, `align-items: flex-start`) + título ocupando **toda** a largura restante. Título com `display: -webkit-box; -webkit-line-clamp: 2; -webkit-box-orient: vertical; overflow: hidden; overflow-wrap: anywhere;` e `title={task.title}` (tooltip com o título completo). No board/kanban o clamp é 3 linhas (prop `lines`).
- Linha 2 (só se houver metadado): `TaskMeta` — chips de 11px, cor `--text-muted`, `gap: 6px`, `white-space: nowrap; overflow: hidden`, ícones Phosphor de 11–12px. Ordem fixa: data (planDate, colorida pelo `overdueKind`), deadline (ícone `Target` + data, só quando diferente da planDate ou quando a data já é a coluna do board), `↻N`, ponto azul "doing" (quando a task não está num grupo/coluna que já diga isso), projeto (só em "All projects"), group (Fase 3), ⚑ important (Fase 4), checklist `2/5` (Fase 4).
- Nada de metadado na linha do título. Remover as classes antigas `.doingBadge`, `.rowProject`, `.rowDue` (dead code).
- O ícone ⚑ (`Flag`) fica reservado para Important (Fase 4); o deadline usa `Target`.
- Calendar (cards do dia e bloco Overdue): só aplicar o clamp de 2 linhas + `title` no `.taskCardTitle` (sem trocar o componente).

### D7. Área principal das Tasks
- Estado no App: `tasksMainView: 'list' | 'week' | 'kanban' | 'review'` (Fase 2 cria com `'list' | 'week'`; Fase 3 adiciona `'kanban'`; Fase 4 `'review'`), lembrado em `localStorage` (`monet:tasks-main-view`, leitura/escrita em try/catch; `'review'` nunca é persistido).
- `'list'`: comportamento atual (TasksView na Sidebar + Editor com a nota-corpo).
- `'week' | 'kanban' | 'review'`: a TasksView e o Editor saem; um único painel ocupa toda a área à direita do NotebookList. Esse painel tem no topo o mesmo `TasksHeader` da lista (seletor de visão, filtro de projeto, faixa de resumo, quick add).
- Clicar num card (board/kanban/review) → `tasksMainView = 'list'` + `selectTask(task)` (abre a nota-corpo).
- Clicar num chip da faixa de resumo fora da lista → muda para `'list'` com o filtro aplicado. Por isso o filtro de resumo (`tasksSummaryFilter`) mora no App, ao lado de `tasksFilter`.

### D8. Drag manual (Week board e Kanban)
Hook `useCardDrag` (`src/components/TasksView/useCardDrag.ts`): `mousedown` no card grava a origem; o drag só começa após 4px de movimento (abaixo disso é clique). Durante o drag: `document` `mousemove` move um "ghost" (clone do card em `position: fixed`, `pointer-events: none`) e calcula a coluna alvo por `document.elementFromPoint` + `closest('[data-drop-key]')`; `mouseup` chama `onDrop(taskId, dropKey)` e limpa tudo; `Escape` cancela. `body.style.userSelect = 'none'` enquanto arrasta. **Sem HTML5 DnD.** Colunas não-droppable não têm `data-drop-key`.

### D9. Atomicidade
Nenhuma operação nova exige transação. Lote (S10), "mover para a próxima semana" (S12) e conclusão de recorrente (gera a próxima) são saves sequenciais no mesmo `persist` do `useTasks`, com um único `tasks-changed`. Sem BEGIN/COMMIT via plugin e sem comando Rust novo.

- **A1 — Constraint "migração via migrations sqlx existentes" substituída (bloqueia só a Fase 2).** O próprio `src/storage/tauri.ts` documenta que as migrations **não rodam no DB de produção** (checksum mismatch da v11; o retry do plugin pula o migrate) — por isso existe o `ensureTasksTables`. Uma migration v19 com `ALTER TABLE` não chegaria às tasks reais, e, combinada com o ALTER idempotente do runtime, pode falhar com "duplicate column" num DB em que o runtime adicionou a coluna antes (ex.: cold start com lock), travando as migrations seguintes. O plano usa apenas o ALTER guardado por `PRAGMA table_info` dentro do `ensureTasksTables` (D1). Os dados são preservados (`due_date` intacto = deadline; `scheduled_date` nulo).
