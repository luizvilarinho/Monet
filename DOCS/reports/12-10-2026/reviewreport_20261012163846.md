## Problemas

### [crítico] Recorrência mensal gera mês 13 em dezembro — `src/lib/tasks.ts` `stepOccurrence`
```ts
const d = parseKey(fromKey)
const lastDay = new Date(d.getFullYear(), d.getMonth() + 2, 0).getDate()
return toDateKey(d.getFullYear(), d.getMonth() + 1, Math.min(d.getDate(), lastDay))
```
`toDateKey(y, m0, d)` só formata a string (`m0 + 1`) e não normaliza. Para uma âncora em dezembro (`getMonth() === 11`) o resultado é `2026-13-15`. Ao concluir uma task mensal de dezembro, a próxima ocorrência é **persistida** com `scheduled_date`/`due_date` inválido. As consequências:
- some do Week board e do Calendar, porque nenhuma chave de dia casa;
- a ordenação e o `isOverdue` passam a se basear em comparação de string com valor inválido;
- o `<input type="date">` das propriedades fica vazio;
- a ocorrência seguinte só se corrige por acaso, porque `parseKey` normaliza.

Correção: montar um `Date(y, m + 1, min(d, lastDay))` e formatar a partir dele (`toDateKey(nd.getFullYear(), nd.getMonth(), nd.getDate())`), ou fazer o rollover do ano manualmente. Diária e semanal usam `addDaysKey`, que normaliza, e não são afetadas.

### [importante] Corrida do ALTER idempotente entre janelas no primeiro start após o upgrade — `src/storage/tauri.ts` `ensureTasksTables`
A janela `keep` é criada oculta no startup (`tauri.conf.json`, `visible: false`) e monta `useTasks()`, assim como a `main`. Cada janela tem sua própria instância de `TauriStorage` e, portanto, sua própria memoização de `tasksTablesReady`. As duas usam o mesmo pool do plugin. No primeiro start com o DB de produção as duas fazem `PRAGMA table_info` antes de qualquer ALTER. As duas tentam `ALTER TABLE … ADD COLUMN scheduled_date`, e a perdedora falha com `duplicate column name`.
- Efeito: `getTasks()` rejeita naquela janela, `useTasks` fica com `loaded=false`/`loadFailed=true` e `tasks=[]`. Se a perdedora for a `main`, a lista de Tasks, o Calendar, o NotebookList (`x/y`) e os lembretes ficam vazios até chegar um `tasks-changed` de outra janela ou até reiniciar. Não há retry automático no `reload` da main.
- Não há perda de dados: o memo é resetado na falha, as escritas seguintes refazem o ensure e o `useNotesIndexSync` é protegido por `tasksLoaded`. Mas é exatamente o cenário de "abrir o app com o DB de produção" pedido no Left behind da Fase 2. O sintoma (tasks sumidas no primeiro start) é o mesmo tipo de susto do bug de cold start já registrado (`project-coldstart-db-lock-race`).
- Correção sugerida: em cada ALTER, tratar o erro com `duplicate column name` como sucesso (try/catch por coluna). Outra opção é reler `PRAGMA table_info` ao falhar e só propagar se a coluna continuar ausente.

### [importante] Drop do Week board em dia passado deixa a task "atrasada no planejamento" — `WeekBoard.tsx`
A coluna Overdue não aceita drop, conforme pedido. Mas as colunas de dias anteriores a hoje (na semana corrente ou em semanas anteriores, via ‹) aceitam. O drop grava `scheduledDate` no passado e o card pula imediatamente para Overdue (amarelo). Na prática é o mesmo efeito que o Task Report quis proibir ("Arrastar para a coluna Overdue não deve ser permitido"). Sugestão: não marcar `data-drop-key` em colunas com `d < todayKey`, ou esmaecê-las durante o drag.

### [nit] Duplicação possível de ocorrência com dois toggles no mesmo frame — `useTasks.updateTasks`
A deduplicação depende de `tasksRef.current`, que só é atualizado no render. Duas chamadas antes de um re-render (ex.: done → todo → done muito rápido) leem `recurrenceNextId === null` nas duas e geram duas ocorrências. Pela UI é improvável. Registro apenas.

### [nit] Reabrir a recorrente depois de gerar a próxima mantém as duas abertas
Desmarcar a original deixa a ocorrência gerada intacta. Remarcar não duplica (correto). Isso atende "desmarcada após gerar", mas o comportamento não está documentado no Execution Report. Vale confirmar com o Coordenador.

### [nit] Quick add: palavras comuns em PT viram data
`ter`, `sex`, `qua`, `dom`, `seg`, `hoje` e, em EN, `sun`/`sat`/`wed` são reconhecidos como data em qualquer posição do título (ex.: "verificar se vai ter deploy" → Do Tue). O chip × resolve, mas o falso positivo de `ter` é frequente em PT. Uma opção é aceitar só os nomes completos em PT ou exigir que o token esteja no fim do texto.

### [nit] `handleCommand` (App) não ignora comandos `local`
Hoje o único caminho que chama `onCommand` é o Enter do Editor, que intercepta `/tasks` antes. Um `if (def.local) return false` em `handleCommand` evita mandar `/tasks` para a IA se outro caminho surgir.

### [nit] Bloco `/tasks` fora do editor
Em `note.content`, o bloco aparece como a tag crua em: export `.md` da nota, preview de nota vinculada/embed (o sanitizer do `markdown.ts` remove a tag e o bloco some) e busca. O clipboard e o RAG estão cobertos. Não bloqueia.

### [nit] Weekly review grava direto na nota diária de hoje
`saveWeeklyReview` faz `saveNote` com o conteúdo lido de `notesRef`. Se a janela keep estiver com a nota de hoje aberta e editada, o autosave dela pode sobrescrever o review (ou o contrário). Mesmo padrão de outras escritas, mas o review é texto que o usuário perderia.

### [nit] Tool "Tasks" do chat ignora a visibilidade de IA por caderno
`queryTasksText` recebe todos os cadernos e tasks. A tool é opt-in do usuário, então não bloqueia. Mas um caderno com RAG desligado tem as tasks expostas ao modelo quando a tool está ligada. Sem contexto suficiente para dizer se isso contraria uma regra de produto. Fica a critério do Orquestrador.

### [nit] Outros
- `reminder_state` acumula linhas `task-deadlines` para sempre (sem limpeza). Volume pequeno.
- `ChatToolsMenu`: com um modelo sem tools, o toggle fica desabilitado, mas se estava ligado continua contando em `activeCount`.
- `newTaskRow` trata Enter no container: Enter num botão de chip (× / "Create #X?") também dispara `handleCreate`.
- `taskChecklist` é recalculado a cada mudança em `notes` e invalida o `tasksContextValue`, o que re-renderiza todas as node views TaskRef/`/tasks` a cada autosave. Aceitável hoje.
- Helpers de data duplicados: `DAY_SHORT` em `WeekBoard.tsx` e `taskQuickAdd.ts` (já existe `WEEKDAY_SHORT` em `lib/tasks.ts`) e `keyDate` (`taskQuickAdd.ts`) = `parseKey` (`lib/tasks.ts`, não exportado).
- `WeekBoard.weekStart` não acompanha a virada do dia com a visão aberta.

## Avaliação por área

**Schema / storage (`storage/tauri.ts`, `lib.rs`, `types`)**
- Correção: o ALTER só adiciona as colunas ausentes; `due_date` não é tocado; linhas existentes ficam NULL/0; o UPSERT inclui as colunas novas. O `INSERT` usa uma lista explícita de colunas, então um downgrade continua funcionando. `parseRecurrence` é seguro contra JSON inválido. Ressalva: a corrida entre janelas descrita acima.
- Padrões: segue o precedente de `ensureReminderStateTable`/`ensureTasksTables` (DDL idempotente no runtime por causa do checksum v11). O comentário no `lib.rs` documenta a decisão A1.

**Regras de task (`lib/tasks.ts`, `useTasks.ts`)**
- `applyTaskPatch`: rollover conta mudança de deadline ou adiamento do do date, uma vez por patch. Correto.
- `planDate`, `overdueKind`, `taskSpan`, `groupTasks`/`groupTasksBy`, `computeTaskSummary` e `compareTasks` estão consistentes entre si.
- Recorrência: a deduplicação por `recurrenceNextId` mais a existência da ocorrência funciona dentro de uma janela e entre janelas (as outras recarregam via `tasks-changed`). Bug crítico no passo mensal.
- `updateTasks` faz um único `setTasks`, saves sequenciais e um único `tasks-changed`, sem transação manual (respeita a restrição).

**Sync task↔nota (A7)**
- `stripGroupPrefix` é aplicado só no sync vindo da nota de origem, com comparação sem diferenciar maiúsculas e só quando o prefixo é igual ao group atual. `convertPipeTitles` não reescreve a nota de origem (só o título da nota-corpo). Sem reescrita de `note.content` pela tabela. Correto.

**Lembretes (`useReminders.ts`)**
- O hook é montado só na `App` (janela main, via `main.tsx`). A keep e o assistant não montam, então não há duplicação. O estado em `reminder_state` com o id determinístico `deadline:<id>:<date>:eve|day` cobre reinícios. A separação dos dois checks em try/catch próprios evita que a ausência da nota diária bloqueie os deadlines. Correto.

**Atalhos de teclado (`useTaskKeyboard.ts`)**
- O `onKeyDown` fica no container da lista/board. `isTextTarget` ignora input/textarea/select/contenteditable, e eventos com Ctrl/Alt/Meta são ignorados. O editor (nota-corpo e TaskPropertiesBar) fica fora do container. "New task…", o filtro do bloco `/tasks` e o popover de data são inputs. Não encontrei caminho para os atalhos dispararem enquanto se digita. O Enter numa linha focada não é tratado duas vezes (o container checa `target !== currentTarget`).

**Drag (`useCardDrag.ts`, `WeekBoard.tsx`, `KanbanBoard.tsx`)**
- Implementação manual com mousedown/mousemove/mouseup e limiar de 4px, ignorando controles. O ghost é removido no cleanup, Esc cancela e o clique pós-drag é engolido. Overdue não aceita drop, No date limpa só o `scheduledDate`, e soltar na mesma coluna é no-op. Ressalva sobre os dias passados acima.

**Bloco `/tasks` (`TasksQueryBlock*`, `Editor.tsx`, `MonetClipboard.ts`, `noteFileText.ts`, `extensions.ts`)**
- Só o filtro vai para `note.content`, com atributo escapado. O node está registrado em `buildBaseExtensions` (main e keep), então o autosave não destrói o bloco. A serialização segue o mesmo padrão do `linked-note`. O clipboard troca a tag pela lista legível; o RAG recebe `[Tasks block: filtro]`. O Enter local não chama a IA. Correto.

**Tool do chat (`useChat.ts`, `ChatPanel.tsx`, `ChatToolsMenu.tsx`)**
- `query_tasks` só entra no payload com `supportsTools && tools.tasks && getTasksSnapshot`, e apenas o `ChatPanel` principal fornece o snapshot. O default é `false` e as tools salvas sem a chave caem em `false`. Segue o fluxo de rodada única (2ª requisição sem tools). Não há execução proativa.

**UI (TasksHeader, TasksView, TaskLine, TaskPropertiesBar, WeeklyReview, DueTodayBlock, Calendar, NotebookList, TaskRefView)**
- Título com 2–3 linhas e tooltip, metadados numa segunda linha. `localStorage` em try/catch, e o `review` nunca é persistido. Sem lógica de negócio relevante no JSX além de filtros simples. As convenções do projeto (CSS modules, comentários em PT, UI em EN, `useConfirm`) foram respeitadas.

**Segurança**
- Nada relevante. O atributo do bloco é escapado na serialização e decodificado no clipboard. O DDL do ALTER vem de uma constante.

**Dead code**
- `TaskRow` e o CSS morto do TasksView foram removidos. A varredura de classes CSS dos módulos tocados e dos exports novos não encontrou nada sem uso: os exports não referenciados fora do arquivo, como `groupTasks` e `nextOccurrenceDate`, são usados internamente. Só há as duplicações de helpers citadas nos nits.
