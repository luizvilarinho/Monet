## 1. Barra de ícones de tabela

### Como funciona hoje
- `src/components/Editor/FormattingToolbar.tsx` usa o `BubbleMenu` do Tiptap v3 (`@tiptap/react/menus`, plugin `@tiptap/extension-bubble-menu` 3.23.4, posicionado com Floating UI). É **uma barra só** para formatação e tabela: `shouldShow` retorna true quando há seleção **ou** o cursor está numa tabela (`ed.isActive('table')`).
- Opções atuais: `{ placement: 'top', offset: 8 }`. Como não há `getReferencedVirtualElement`, a âncora é o **retângulo do cursor/seleção** (`posToDOMRect(selection.from, selection.to)`). Com o cursor na 2ª linha, a barra fica logo acima do cursor, ou seja, em cima da linha anterior (o cabeçalho, no print).
- O elemento do menu é anexado em `view.dom.parentElement` (wrapper do `EditorContent`), que fica dentro de `.body` (`Editor.module.css`: `position: relative; overflow-y: auto`, é o container de scroll). Então a barra rola junto com o conteúdo e é cortada pelo topo de `.body`.
- O middleware `flip` já vem ligado por padrão. Quando falta espaço acima, a barra pula para baixo da âncora.
- CSS da tabela: `.tableWrapper { margin: 0.7em 0 }`, `table { margin: 0.7em 0 }`, `.proseEditor { padding-top: 20px }`. Altura da barra é cerca de 36px (botão de 28 + padding de 3+3 + bordas).

### Como resolver (recomendado)
1. **Ancorar na tabela, não no cursor.** O `BubbleMenu` aceita a prop `getReferencedVirtualElement` (é chamada a cada `updatePosition`). Quando `editor.isActive('table')`, suba `selection.$anchor` (ou `$anchorCell` numa `CellSelection`) até o node `table`, pegue `view.nodeDOM(pos)` (com `resizable: true` isso devolve o `div.tableWrapper` do TableView), use o `<table>` dentro dele e retorne `{ getBoundingClientRect: () => rect, getClientRects: () => [rect] }`. Fora de tabela, retorne `null` para manter o comportamento atual (âncora = seleção).
2. `options={{ placement: 'top-start', offset: 6, flip: false, shift: { crossAxis: true, padding: 4 } }}`.
   - `top-start` alinha a barra à borda esquerda da tabela.
   - `flip: false` evita que a barra pule para baixo de uma tabela grande.
   - `shift` com `crossAxis` mantém a barra dentro da área visível de `.body` na vertical. Quando o topo da tabela sai da tela por scroll, a barra "gruda" no topo visível. Nesse caso ela inevitavelmente cobre uma linha, mas continua acessível. Isso é aceitável; a alternativa seria a barra sumir.
   - Para o "grudar" acompanhar o scroll, passe `options.scrollTarget = <elemento .body>`. Hoje o plugin só escuta o scroll de `window`. É preciso expor o `scrollRef` do `Editor.tsx` para o `FormattingToolbar` (via prop; o mais seguro é guardar o elemento em state, porque o ref é `null` no primeiro render).
3. **Reservar espaço quando a tabela é o 1º bloco.** O título fica fora do ProseMirror, então uma nota que começa com tabela tem só ~30px (20 de padding + 0.7em) acima dela, menos que os ~42px da barra mais o offset. Adicione em `Editor.module.css` algo como `.proseEditor > :global(.tableWrapper:first-child) { margin-top: 32px; }`. Assim a barra cabe acima sem ser cortada e sem precisar de flip.
4. Tabela de uma linha só (só cabeçalho) fica coberta automaticamente, porque a âncora é a tabela inteira.

Observações:
- Seleção de texto **dentro** da tabela também passa a ancorar no topo da tabela, pois é a mesma barra. Acho coerente; se preferirem, dá para ancorar na tabela só quando `!hasSelection`.
- Quando há um parágrafo logo antes da tabela, a barra cobre esse parágrafo, não a tabela. Isso atende ao requisito ("sem sobrepor texto da tabela").
- Não precisa de lib nova.

## 2. Clipboard e `<br>`

### Origem exata (copy-out, `text/plain`)
O texto copiado é gerado pelo `tiptap-markdown` 0.9.0. Em `extensions.ts`, o `Markdown.configure({ transformCopiedText: true, transformPastedText: true, html: true })` registra a extensão interna `MarkdownClipboard` (`node_modules/tiptap-markdown/src/extensions/tiptap/clipboard.js`). O `clipboardTextSerializer` dela serializa o `slice` inteiro como Markdown. Ela tem precedência sobre o `ClipboardTextSerializer` do core do Tiptap: mesma prioridade (100), e o `ExtensionManager.plugins` inverte a lista, então as extensões do usuário vêm antes das do core.

O código emite `<br>` (sem barra) em três lugares. Não existe `<br />` no código; o `<br />` do relato deve ser só a notação usada ou a renderização do app de destino.
1. **Linha em branco entre parágrafos (causa mais comum).** O `ParagraphWithBlankLines` (nosso, `extensions.ts` L58-96) serializa todo parágrafo vazio **interno** como `<br>`, para manter o round-trip do markdown persistido. No clipboard isso vaza: copiar "linha A / (vazia) / linha B" gera `A\n\n<br>\n\nB`.
2. **Hard break (Shift+Enter) dentro de célula de tabela.** Em `tiptap-markdown/.../nodes/hard-break.js`, com `state.inTable` ligado, o hard break é escrito como HTML (`<br>`). Fora de tabela vira `\` seguido de quebra de linha (barra invertida literal no texto colado fora do app; também precisa sair).
3. **Tabela "não-serializável" ou seleção parcial de células.**
   - `nodes/table.js` só gera Markdown quando a 1ª linha é toda `tableHeader` e cada célula tem um único parágrafo. Caso contrário, despeja a tabela inteira em HTML (`<table><tr><td><p>…<br>…`).
   - Uma `CellSelection` que não cobre a tabela inteira gera, via `CellSelection.content()` do prosemirror-tables, um slice de **`tableRow`s soltos**, sem o node `table`. Não existe serializer Markdown para `tableRow`, então cai no `markdownHTMLNode` e sai `<tr><td>…</td></tr>` no texto. Isso vale inclusive para **uma única célula** selecionada como `CellSelection`.

### Paste-in
- Colar `text/plain` passa pelo `clipboardTextParser` do `MarkdownClipboard`: o texto é parseado como Markdown com `html: true`, então `<br>` e `<br />` viram hardBreak e não aparecem literalmente.
- Colar dentro do editor usa o `text/html` do ProseMirror (`data-pm-slice`), sem passar pelo serializer de texto.
- Ou seja, o `<br>` literal só aparece quando o texto vai para um destino que usa `text/plain` cru: outros apps, os textareas do chat/NotesChat, o input de título, um **code block** (o ProseMirror cola texto cru em `spec.code`) e o paste sem formatação (Ctrl+Shift+V).
- O único handler custom de paste (`Editor.tsx` L238, `handlePaste`) trata só imagens; não interfere.
- Conclusão: **corrigir a geração (copy-out) resolve a causa.** Não recomendo normalizar `<br>` no paste-in: isso estragaria colar HTML legítimo num code block.

### Onde e como corrigir (recomendado)
Criar uma extensão própria de clipboard (ex.: `MonetClipboard`, em `src/components/Editor/`), registrada em `buildBaseExtensions`. Com isso o editor principal **e a janela keep** recebem a correção. Ela deve ter `priority` acima de 100, para rodar antes do `MarkdownClipboard`. Depois troque para `transformCopiedText: false` no `Markdown.configure` (deixar `true` seria config morta). Mantenha `transformPastedText: true`.

Ela implementa duas props do ProseMirror:

- **`transformCopied(slice, view)`**: se a seleção é `CellSelection` com `$anchorCell.pos === $headCell.pos` (uma célula), troque o slice pelo conteúdo da célula (`new Slice(cell.content, 1, 1)`, ou equivalente). Assim o `text/html` também deixa de levar uma tabela 1×1: colar fora de tabela dá texto, não uma tabela nova. Esse hook também é usado no drag; não há efeito colateral relevante.
- **`clipboardTextSerializer(slice, view)`**, por ordem de decisão:
  1. **Seleção dentro de uma única célula** (`CellSelection` de 1 célula, ou `TextSelection` cujos `$from`/`$to` têm o mesmo ancestral `tableCell`/`tableHeader`): **texto puro**, `slice.content.textBetween(0, size, '\n', leaf => leaf.type.name === 'hardBreak' ? '\n' : '')`. Sem marcas Markdown, hard break vira quebra real.
  2. **`CellSelection` com várias células, ou tabela inteira**: monte a tabela Markdown à mão, sem depender do `nodes/table.js`. Pegue as linhas do slice: são `tableRow`s soltos, ou o `table` quando a seleção cobre tudo. Para cada célula, use `editor.storage.markdown.serializer.serialize(cell.content)`, depois junte as quebras com espaço (`/\\\n|\n+/g` vira `' '`), remova `<br>` e escape `|` como `\|`. A primeira linha é seguida de `| --- | ... |`, mesmo se não for header (o GFM exige). Complete linhas mais curtas com células vazias.
  3. **Demais casos** (texto comum, ou seleção que começa fora e termina dentro da tabela): percorra os filhos de topo de `slice.content`.
     - Nodes `table` (inclusive o parcial/aberto do caso "começa fora, termina dentro") vão para o mesmo construtor do item 2.
     - Grupos de outros blocos vão para `editor.storage.markdown.serializer.serialize(fragment)`, depois de:
       - trocar cada `hardBreak` por um text node `'\n'` com as mesmas marcas. O `state.text()` do prosemirror-markdown quebra a linha corretamente e ainda respeita a indentação de listas. É mais seguro do que um regex de `\\\n`, que comeria a barra invertida no fim de linha em code block;
       - pós-processar as linhas que são exatamente `<br>`, trocando por linha vazia. É seguro porque texto digitado `<br>` é escapado para `&lt;br&gt;` pelo serializer de text; o mesmo truque já existe em `App.tsx` `stripCommandLines`.
     - Junte as partes com `\n\n`.

Pontos de atenção:
- Tabelas aninhadas (dentro de toggle/lista) continuam no caminho do `tiptap-markdown`. É raro; dá para aceitar ou tratar recursivamente.
- O `text/html` de seleções comuns não muda; colar dentro do editor continua preservando a formatação.

## 3. Subject → Caderno

### Mapa do código
- **UI:** **não existe menu de contexto de subject.** A linha do subject (`SortableSubjectItem` em `src/components/NotebookList/NotebookList.tsx` L169-267) tem só o botão hover "×" (delete) e duplo-clique para renomear; a linha do caderno tem o botão hover `ArrowRight` ("move to another notebook"). Nenhum componente usa `onContextMenu`. Recomendo **um botão hover novo na linha do subject** (ícone Phosphor, ex.: `ArrowSquareOut`, `title="Turn into notebook"`), ao lado do "×", com o confirm modal já usado em `handleDeleteSubject`. Ele fica oculto para o subject Tasks (`isTasks`, como já acontece com rename/delete). O Sidebar.tsx **não** está envolvido: lá só há o dropdown "assign subject" das notas.
- **Persistência:**
  - `useSubjects` (`save/remove/refresh`), `useNotes.save` e `useNotebooks.create` atualizam o state primeiro e depois chamam o storage.
  - `storage.deleteSubject` (`src/storage/tauri.ts` L474) **apaga em cascata as notas com `subject_id = id`**. Logo, as notas precisam ser re-salvas com `subjectId: null` **antes** do delete (mesma lógica de `handleMoveNotebook`/`deleteNotebook`).
  - `monet:notebook-order` é mantido via `setNotebookOrder` + `saveOrder`.
- **Subject Tasks:** identificado **pelo id** (`tasksSubjectId(nb) = 'tasks-<nb>'`, `isTasksSubject`), não pelo nome. Um subject comum chamado "Tasks" não é o especial e pode ser convertido.
- **RAG (`useNotesIndexSync`):** é reativo; não precisa chamar nada. No diff de notas (L428-452), uma nota cujo `notebookId` mudou em relação ao último sync gera `enqueueUpsertNow`, e o backend move o arquivo sem refazer o embedding. O job de upsert procura o caderno em `notebooksRef`; se não achar, **apaga a nota do índice**. Por isso o caderno novo precisa existir no state antes dos `saveNote` (o `createNotebook` já faz isso ao ser aguardado).
- **Chat:** o vínculo de pasta de chat é por caderno (`linkNotebookToChatFolder`) e subjects não têm vínculo. Nada a desfazer; o caderno novo nasce sem pasta, como qualquer caderno novo.
- **Reader / Calendar:**
  - As citações do Reader apontam para a nota por `targetNoteId`, e `handleNoteLinkNavigation` resolve o caderno pela nota. Mudar de caderno não quebra nada.
  - O campo `date` é preservado pelo spread da nota.
  - O caderno Calendar é filtrado da `NotebookList`, então seus subjects nem aparecem na lista. A ação não fica alcançável ali, e não é preciso fazer nada além de um guard defensivo (`sourceNotebookId !== CALENDAR_NOTEBOOK_ID`).
  - Inbox: subjects comuns do Inbox podem ser convertidos normalmente; o subject Tasks do Inbox fica bloqueado pela regra geral.

### Decisões do Coordenador e implicações
1. **Subject Tasks bloqueado.** O guard fica em dois lugares: o botão some quando `isTasks`, e o handler também retorna se `isTasksSubject(subject)`.
   - Caso residual: uma nota-corpo de task (`task.noteId`) pode ter sido reatribuída a um subject comum pelo dropdown de assign. Nesse caso, o handler deve detectar `tasks.some(t => t.noteId === n.id)` e usar `relocateTask(task, destId)`, que move a task e a nota para o subject Tasks do destino, em vez de achatar a nota. Isso segue o mesmo padrão do `movedNoteIds` de `handleMoveNotebook`.
2. **Mesmo nome → mesclar no caderno existente (raiz, sem duplicar).**
   - **Regra de match:** reutilizar a regra de `resolveProject` (App.tsx L436-442): `trim().toLowerCase()` igual, excluindo o Calendar. Se houver mais de um caderno com o nome, escolha o primeiro na ordem da sidebar (`applyOrder(notebooks, notebookOrder)`), para ser previsível. Sugiro extrair um helper `findNotebookByName(name)` usado pelos dois.
   - **Caso especial: o próprio caderno de origem tem o mesmo nome do subject** (ex.: caderno "Work" com subject "Work"). Pela regra, o subject é "dissolvido": as notas vão para a raiz do mesmo caderno e o subject é apagado. É consistente com a decisão; só garanta que o código não trate isso como "mover para outro caderno". O `notebookId` não muda, então nada acontece no RAG. Também é preciso chamar `refreshSubjects()` ou contar com o `removeSubject` do hook.
   - **Ordem:** ao mesclar em caderno existente, `monet:notebook-order` **não muda**. Só se insere na ordem quando um caderno é criado. Sugestão: inserir logo **após o caderno de origem**, e no topo se a origem não estiver na lista. O padrão atual de criação põe no topo; qualquer uma das duas serve.
   - **RAG ao mesclar:** igual à criação (move reativo). Nuance pré-existente, que também afeta `handleMoveNotebook`: se o destino estiver com o RAG desligado, a regra "mudou de caderno, upsert imediato" ignora o `disabled`. Vale anotar, mas não é escopo desta task.
3. **Subject vazio:** cria o caderno vazio (ou, se o nome existir, só apaga o subject).

### Sequência segura sugerida (`handleSubjectToNotebook(subjectId)` em App.tsx)
1. Guards: o subject existe na lista do caderno ativo, não é o Tasks e o caderno de origem não é o Calendar.
2. `dest` = caderno existente pelo nome (regra acima) ou `await createNotebook(subject.name)` + inserção na ordem.
   - Se a origem tem o RAG desligado (`disabledNotebookIds.has(source)`) e o caderno é **novo**, chamar `setNotebookIndexEnabled(dest.id, false)` **antes** de mover as notas. Sem isso, notas que o usuário excluiu do RAG seriam embedadas. Recomendo herdar o estado; confirmem.
3. Tasks cujas notas-corpo estão no subject vão para `relocateTask(task, dest.id)`.
4. As demais notas do subject recebem `saveNote({ ...n, notebookId: dest.id, subjectId: null, updatedAt })`.
   - **Atenção:** `useNotes.save` engole erros. Se um save falhar, o passo 5 apaga a nota em cascata. Recomendo salvar via `storage.saveNote` direto com try/catch e **abortar antes do delete** se algo falhar, ou fazer o mesmo checando o retorno. Esse risco também existe hoje em `handleMoveNotebook`.
5. `await removeSubject(subjectId)`, que cascateia `ai_responses`/notas que ainda apontem para ele. Neste ponto não deve sobrar nenhuma.
6. Seleção: navegar para o caderno de destino com `setActiveNotebookId(dest.id)` e `setActiveSubjectId(null)`.
   - Se a nota ativa estava no subject, mantenha `activeId`, porque ela continua existindo com o mesmo id. Caso contrário, abra a primeira nota do destino ou `null`.
   - `useSubjects(activeNotebookId)` recarrega sozinho ao trocar de caderno.
   - No caso "mesmo caderno", só `setActiveSubjectId(null)`.
7. `noteOrder` é global por id e não muda; `tasksFilter` não é afetado.

## Resumo de recomendações
- **Tabela:** `getReferencedVirtualElement` apontando para o `<table>`, `placement: 'top-start'`, `flip: false`, `shift({ crossAxis: true })`, `scrollTarget` = `.body`, e `margin-top` extra quando a tabela é o primeiro bloco.
- **Clipboard:** extensão própria com `clipboardTextSerializer` + `transformCopied` e prioridade acima de 100, e `transformCopiedText: false` no Markdown. A causa principal do `<br>` é o marcador de linha em branco do `ParagraphWithBlankLines`; também o hard break dentro de tabela e o fallback HTML para tabelas e linhas de `CellSelection`. Não mexer no paste-in.
- **Subject → Caderno:** botão hover novo na linha do subject (não existe menu de contexto); o handler segue a sequência acima. Os cuidados principais são o cascade do `deleteSubject`, o `saveNote`, que engole erro, e a herança do flag de RAG desligado.
