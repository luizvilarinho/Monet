## 1. Correção

### `[crítico]` A repaginação nova do `ResizeObserver` dispara na abertura e joga o leitor uma página para trás

`EpubReader.tsx:574-590`:

```ts
observer = new ResizeObserver(() => {
  if (resizeTimer) clearTimeout(resizeTimer)
  resizeTimer = setTimeout(() => {
    ...
    const cfi = currentCfiRef.current
    resizeEpubRendition(current)
    if (cfi) void displayEpubAt(current, cfi).catch(() => {})   // ← incondicional
  }, RESIZE_DEBOUNCE_MS)
})
observer.observe(element)
```

`ResizeObserver.observe()` entrega **uma notificação inicial** mesmo sem nenhuma mudança de tamanho — o `lastReportedSize` de um alvo novo é (0,0). Confirmado por medição nesta review (Chrome headless, página mínima, elemento estático de 400×200): `fires_without_any_size_change=1`.

Consequência, ~150 ms depois de o livro aparecer:

1. `resizeEpubRendition(current)` é um **no-op** — o guard de `_stageSize` do `DefaultViewManager.resize` (`node_modules/@likecoin/epubjs/src/managers/default/index.js:213-218`) retorna cedo porque o tamanho não mudou. Foi exatamente com esse guard que a B1 justificou a chamada redundante ("torna a chamada redundante um no-op", B1 §decisão 5).
2. Mas o `displayEpubAt(current, cfi)` que a B2 acrescentou fica **fora** do guard e roda assim mesmo, com `cfi` = o `location.start.cfi` da página atual.
3. `display(startCfi)` é precisamente a operação que a própria B1 mediu como imprecisa: *"14 das 40 primeiras páginas"* em spread e *"12 de 40"* em coluna única renderizam o `start.cfi` no fim da coluna anterior, e `moveTo` ancora pelo x renderizado. O comentário de `resumeEpubAt` em `lib/epub.ts:319-339` documenta isso em detalhe.

Ou seja: em ~1/3 das posições, **o leitor abre no lugar certo (o `resumeEpubAt` faz o seu trabalho) e ~150 ms depois volta uma página sozinho** — o sintoma que o Coordenador reportou ao testar a B1 e que motivou a correção pontual `20260808040000`.

Pior: o `relocated` resultante chama `schedulePositionSave`, então a posição errada é **persistida**. A cada sessão a aposta é refeita, o que faz a posição derivar para trás ao longo do tempo, não apenas uma vez.

Por que o harness não pegou: a suíte da B2 exercita `src/lib/epub.ts` bundlado, não o `EpubReader.tsx`. O `ResizeObserver` e a decisão de reposicionar vivem no componente. A medição de "resize drástico perde a posição (343 → 178)" está certa e a correção é legítima — o defeito é ela ser aplicada **incondicionalmente**, inclusive quando não houve resize nenhum.

Correção mínima sugerida (guardar o tamanho observado e só reposicionar quando ele muda de fato):

```ts
let lastW = element.clientWidth
let lastH = element.clientHeight
observer = new ResizeObserver(() => {
  if (resizeTimer) clearTimeout(resizeTimer)
  resizeTimer = setTimeout(() => {
    resizeTimer = null
    if (cancelled || !renditionRef.current) return
    const w = element.clientWidth
    const h = element.clientHeight
    if (w === lastW && h === lastH) return   // notificação inicial / no-op
    lastW = w; lastH = h
    const current = renditionRef.current
    const cfi = currentCfiRef.current
    resizeEpubRendition(current)
    if (cfi) void displayEpubAt(current, cfi).catch(() => {})
  }, RESIZE_DEBOUNCE_MS)
})
```

Endurecimento complementar (opcional): usar `resumeEpubAt` em vez de `displayEpubAt` nesse caminho. O destino é sempre um CFI de início de página, que é o caso para o qual `resumeEpubAt` foi escrito, e ele já degrada bem quando não existe página equivalente após a repaginação. O custo é o pulo visível de ida e volta que a B1 rejeitou no caminho de fonte — aceitável num resize, que já é visualmente ruidoso, mas não substitui o guard de tamanho acima (com o guard, o caso espúrio nem chega lá).

### `[importante]` O controle "2 col" não força duas colunas — e com a coluna de chat aberta ele é inerte

O requisito 9, com o esclarecimento do Coordenador registrado na abertura do execution report, pede *"um mecanismo visível para o usuário alternar entre 1 e 2 colunas — não uma decisão interna de configuração"*. O que foi entregue alterna entre `spread: 'auto'` e `spread: 'none'` (`lib/epub.ts:687-692`), mantendo `minSpreadWidth = 800`. `Layout.calculate` só usa `divisor = 2` quando `this._spread && width >= this._minSpreadWidth`, então **"2 col" continua sendo "auto"**: a decisão interna de 800 px segue no comando.

Isso não é teórico nas dimensões reais do app. Janela default 1280 (`tauri.conf.json`), descontando `.pageArea` padding 48 e `.viewerSurface` padding 40:

| Configuração | Área de leitura | Efeito de "2 col" |
| --- | --- | --- |
| nav recolhido (48), chat fechado | 820 px | 2 colunas |
| nav recolhido (48), chat aberto (340) | ~804 px | 2 colunas, por 4 px |
| nav expandido (280), chat fechado | ~812 px | 2 colunas |
| **nav expandido (280), chat aberto (340)** | **~572 px** | **inerte — 1 coluna nos dois estados** |

O `title` do botão ("Two columns (when wide enough)") divulga a limitação, então não é engano do usuário; mas a tela em que o Coordenador vai usar chat + sumário é justamente a que não responde ao controle.

Isso também não sustenta a linha da tabela de validação do execution report: *"Toggle 1 col ↔ 2 col — `divisor` 2↔1 com repaginação real"*, declarada como **idêntica nos três modos**. Na terceira geometria do próprio harness (coluna de chat aberta, 554 px) o `divisor` é 1 nas duas posições do controle; não há 2↔1 a medir ali. A medição das outras duas geometrias continua válida — a generalização é que não.

Remédio de uma linha, se o Coordenador quiser o controle literal: passar o mínimo junto do modo — `rendition.spread(mode, mode === 'auto' ? 0 : undefined)` (o `Layout.spread` aceita `min >= 0`, então 0 zera o `minSpreadWidth`) — e, no `renderTo`, `minSpreadWidth: 0` quando a preferência for `auto`. Alternativa mais conservadora: desabilitar o botão "2 col" quando a área medida estiver abaixo de 800 px, para o controle nunca parecer quebrado. Decisão de produto; registro o desvio em relação ao requisito.

### O que foi verificado e está correto

- **`readerContext.ts` — saída do PDF byte a byte idêntica.** Verificado por leitura, não por confiança no report: `Position: ${positionLabel ?? \`page ${pageNum} of ${totalPages}\`}` reproduz a string anterior caractere a caractere quando a prop é ausente, e `[${label}, …]` com `label = \`p. ${h.page}\`` reproduz o item de grifo. O único jeito de a saída mudar é um chamador passar string vazia (`??` não cai em `''`), e o `EpubReader` sempre passa template não vazio. Idem `pendingQuote.positionLabel ?? \`p. ${page}\`` no `ReaderChatPanel`.
- **`rowToHighlight`/`saveHighlight`.** `cfi: r.cfi ?? null` na leitura e `h.cfi ?? null` na escrita. O `SELECT * FROM book_highlights` já traz a coluna nova. Para PDF a coluna era NULL antes (não estava no INSERT) e continua NULL depois (`cfi = excluded.cfi` com `h.cfi` ausente) — nenhuma mudança de comportamento. `parseHighlightRects` continua no comando do posicionamento do PDF.
- **`saveBook`.** `COALESCE` só em `locations_json`; para PDF é `COALESCE(NULL, NULL)` = NULL. `format` fora do `DO UPDATE`. Sem efeito no PDF.
- **Contrato do `page`.** Grifo grava `epubLocationOrdinal(cfiRange)` (1-based) e a posição grava `start.location + 1` — mesma régua, honrando o contrato do `useHighlights`. Verifiquei que `EpubCFI.compare` (`epubcfi.js:360-374`) trata CFI range usando os passos de `start`, então passar um range para `locationFromCfi` compara corretamente contra as entradas de location.
- **`getPageText` devolve a fatia, não o XHTML.** Confirmado na fonte da lib: `Locations.parse` (`locations.js:151-172`) empurra **range** CFIs cobrindo ~`chars` caracteres, então `cfiFromLocation(n)` → `book.getRange` → `toString()` é a fatia. Bate com os 1.616 chars medidos.
- **CFI de grifo que não resolve.** `drawEpubHighlight` valida por `book.getRange` antes de chamar `annotations.highlight` e devolve `false`; o item continua no painel, legível e citável. A validação é necessária, não defensiva: um CFI inválido rebentaria dentro do hook `render` do `Annotations` e derrubaria o render da seção.
- **Grifos sobrevivendo a repaginação.** Estruturalmente correto, não só medido: `Annotations` registra `inject` no hook `render` (`annotations.js:20`), e o resize destrói/recria as views, então as marcas são reanexadas; na troca de spread as views não morrem e `IframeView.reframe` chama `pane.render()` + `placeMark` em rAF (`managers/views/iframe.js:361-370`).
- **Hit-test em modo spread.** Verificado na fonte do `marks-pane`: `proxyMouse` escuta no `contentDocument` do iframe e converte com `markRect − iframeRect` (`events.js:98-124`), então a detecção é em coordenadas relativas ao iframe e independe de haver 1 ou 2 colunas. É por isso que clicar no **texto** grifado (e não só no SVG) dispara `markClicked` — a explicação do executor está certa.
- **Livro sem TOC / posição antes da primeira âncora.** `flattenTocAnchors` exclui entradas irresolúveis (`href`/`sectionIndex` nulos, que a B1 já marcava), `anchors.length === 0` → `null`, e âncora de mesma seção posterior à posição não vira `best` → fallback "só %". Correto.
- **64 âncoras num único XHTML.** `resolveEpubChapter` compara `EpubCFI(el, section.cfiBase)` com o CFI da posição dentro da mesma seção; `spinePos` e `section.index` são a mesma régua no epubjs. Correto por construção, além de medido.
- **Ciclo de vida / desmontagem.** `aborted()` cobre o caso de o cleanup rodar antes de `handle` existir; os três `off*` são desregistrados; `handle.destroy()` (e não `rendition.destroy()` também) evita dupla destruição do manager. Os dois flush de debounce estão em efeitos posteriores, então rodam depois do cleanup da carga.
- **Grifo não vaza entre livros.** `useHighlights(book.id)` zera o estado e o `EpubReader` remonta (o `Library` passa por `openBook = null` ao voltar).
- **Requisito 10.** `EPUB_INCOMPLETE_ERROR_NAME` nomeado em `lib/epub.ts` e traduzido em `lib/books.ts`, no mesmo padrão do DRM/timeout.

### Borda da janela (segunda metade do requisito 9)

A conclusão "não é do app" **se sustenta**. Confirmei de forma independente: a janela `main` em `tauri.conf.json` declara só `label/title/width/height` (sem `resizable`, `decorations` ou `maximized`); `grep` por `setResizable|maximize|setSize|setFullscreen|LogicalSize` no `src` e por `set_resizable|maximize|set_size|set_fullscreen|window_state` no `src-tauri/src` não retorna nada; não há `tauri-plugin-window-state` no `Cargo.toml`. Com decoração default o Tauri não faz hit-test próprio, então a borda é área não-cliente do OS e o WebView não a alcança.

Ressalva de método, que vale registrar: isso é **hipótese não falsificada**, não reprodução. O que fecharia o assunto é o Coordenador restaurar a janela (sair do maximizado) e tentar arrastar. Se falhar assim, a conclusão cai e vira investigação de verdade.

`[nit]` Dois grifos com o mesmo CFI range: a limitação registrada está **corretamente diagnosticada mas com a alcançabilidade subestimada**. O mecanismo é o que o executor diz — `hash = encodeURI(cfiRange + type)` em `annotations.js:35`. O que o report chama de "inatingível pela UI sem esforço deliberado de duplicar uma seleção caractere a caractere" na verdade acontece com **duplo clique na mesma palavra duas vezes**: o duplo clique produz o mesmo range exato, sem nenhum esforço. Há ainda um efeito que o report não menciona: ao apagar um dos gêmeos, o `drawnRef` do sobrevivente continua marcado como desenhado, então a marca dele **não é redesenhada** e só volta ao reabrir o livro. Nada se perde (os dois itens continuam no painel e o texto está íntegro), e concordo que trocar o store de anotações da lib por um overlay próprio é desproporcional. Mas a mitigação barata existe e cabe em três linhas: recusar a criação quando já houver grifo com o mesmo `cfi` (em `handleHighlight`), tornando a limitação inalcançável em vez de improvável.

`[nit]` Pré-validar todo grifo salvo com `book.getRange` (decisão 1, correta em si) força o `Section.load()` de toda seção que contenha grifo já na abertura, e o epubjs **cacheia o documento parseado indefinidamente** (`Section.load` só limpa em `unload()`). No arquivo de teste (1 item de spine) isso é invisível; num livro de 100 capítulos com grifos espalhados, a abertura parseia e retém dezenas de DOMs. Mitigação barata: `section.unload()` depois de validar as seções que não são a corrente. Não bloqueia.

## 6. Organização e boas práticas

- Camadas respeitadas: todo epubjs em `lib/epub.ts`, nenhum import de `@likecoin/epubjs` no componente; storage isolado; hooks reusados sem alteração de contrato.
- Tipagem: união discriminada `Book = PdfBook | EpubBook` obriga cada leitor a declarar o formato, e o dispatch do `Library` estreita em tempo de compilação. `tsc` limpo com `noUnusedLocals`.
- Sem listener vazado: os três `off*`, o `document.mousedown`, o `window.keydown`, o `ResizeObserver` e os dois timers de debounce têm cleanup.
- Sem `setState` pós-unmount: todos os caminhos assíncronos checam `cancelled`/`aborted()`.
- CSS: nenhuma classe morta (verifiquei as 69 definidas contra os 66 usos; as 3 restantes são falso positivo de nome de arquivo/seletor de elemento).

`[nit]` **Dead code:** `PagePoint.w` (`EpubReader.tsx:115-120`) é escrito em três lugares e nunca lido — `toolbarStyle` usa `x/y`, `popoverStyle` usa `x/y/h`. É espelho fiel do mesmo campo inútil em `Reader.tsx:94-99`, então é duplicação de um defeito existente, não invenção nova; a regra do repo manda tirar na revisão, e aqui sai de graça (o arquivo é novo).

`[nit]` `resolveEpubChapter` resolve o fragmento com `doc.getElementById(anchor.fragment)` sem `decodeURIComponent` e sem fallback para `[name=...]` (NCX de EPUB 2 antigo). Num livro com id de âncora percent-encoded ou com `<a name>`, toda entrada de TOC deixa de resolver e a citação cai no fallback "só %" — degrada conforme o requisito, não quebra, mas perde o capítulo em livros que poderiam tê-lo.

`[nit]` A toolbar de seleção é posicionada com `left: Math.max(8, anchor.x)` sem clamp à direita, dentro de uma `.pageArea` com `overflow: hidden`. Seleção colada na borda direita de uma área larga empurra parte da toolbar para fora e ela fica inalcançável. O `Reader.tsx` tem o mesmo cálculo, mas lá a área tem `overflow: auto`, então dá para rolar até ela. Cosmético.

## Bugs extras (fora do escopo, no código que precisei ler)

- `Annotations.remove` do epubjs (`annotations.js:72-92`) faz `delete this._annotations[hash]` mas só limpa `_annotationsBySectionIndex` **dentro** do `views.forEach`. Com zero views no momento da remoção, o hash órfão sobra no índice e o `inject` seguinte chama `.attach` em `undefined`, derrubando o render da seção. A janela de zero views existe (o `DefaultViewManager.resize` faz `clear()` antes de reenfileirar o `display`), mas remover um grifo exige clique + confirmação, então na prática é inalcançável. Registro por ser exatamente o tipo de coisa que aparece se algum dia a remoção virar automática.
