## 1. Problema

Promover itens `- [ ]` de notas a tasks estruturadas (tabela própria), manter o vínculo nota ↔ task sem reescrever `note.content` a partir da tabela, e mostrar as tasks numa view especial e no Calendar.

## 2. Serialização e o padrão do ReminderChip → `<task-ref>`

**Como funciona hoje**
- Notas são markdown via `tiptap-markdown@0.9` com `html: true` (`src/components/Editor/extensions.ts`).
- `ReminderChip.ts` é um node inline `atom` com `parseHTML: [{ tag: 'reminder-chip' }]` e `addStorage().markdown.serialize` que faz `state.write('<reminder-chip data-id=".." data-time=".."></reminder-chip>')` (sem `closeBlock`). No parse, o markdown-it emite o HTML inline e o `parseHTML` do Tiptap o reconhece.
- O estado "disparado" fica na tabela `reminder_state` e chega à view por `RemindersContext` (`RemindersProvider` em `App.tsx:1472` e em `KeepPanel.tsx:228`). `ReminderChipView` lê `useReminderState()`.

**Como replicar**
- Criar `TaskRef.ts` + `TaskRefView.tsx` + `TasksContext.tsx` copiando o padrão. **Só o atributo `id`** (`data-id`). O prazo NÃO deve ir no atributo (ao contrário do `data-time` do reminder): ele muda na tabela, e mudar o atributo reescreveria a nota. A pill lê `due_date`/status do contexto.
- Markdown resultante: `- [ ] Buy milk <task-ref data-id="abc"></task-ref>`. Confirmado no código: `markdown-it-task-lists` só exige o prefixo `[ ] `, então a tag no fim da linha não quebra a detecção de task item. Recomendo inserir a pill **no fim do primeiro parágrafo** do taskItem.
- **Crítico:** o node tem que entrar em `buildBaseExtensions` (o comentário em `extensions.ts:96-100` avisa: sem isso, a janela keep descarta o node no parse e o autosave apaga a tag).
- Remoção para o RAG: `src/lib/noteFileText.ts` já tira tags genéricas (`TAG_RE`). O preview de nota vinculada (`renderNoteContent`, rehype-sanitize) também remove. Nada a fazer.
- A exportação (`handleExport`) vai gravar a tag crua, igual hoje acontece com o reminder-chip. Aceitável no MVP.
- Copiar e colar: `transformCopiedText: true`, então a tag vai junto com o mesmo id. "Ambos referenciam a mesma task" sai de graça.

## 3. Checkbox refletindo a tabela sem reescrever a nota

**Como o TaskItem funciona** (`node_modules/@tiptap/extension-list/src/task-item/task-item.ts`, v3.23.4): NodeView vanilla (sem React) `li > label > input + span`, `div` (contentDOM). O `change` do checkbox faz `setNodeMarkup(checked)`, ou seja, **escreve no doc** e vira `- [x]` no markdown. `update()` só roda quando o node **ou suas decorations** mudam. O serializer markdown usado é o do `tiptap-markdown` (busca por nome `taskItem`), então um `TaskItem.extend({...})` mantém a serialização.

**Abordagem recomendada: decoration + NodeView próprio**
1. `TaskItem.extend({ addNodeView })` com uma cópia enxuta da NodeView original, **mesma estrutura de DOM** (o CSS em `Editor.module.css:298-371` e o widget de drag `monetTaskDragHandle`, `CommandExtension.ts:734`, dependem dela).
2. Um plugin ProseMirror (`taskStatusPluginKey`) guarda `Map<taskId, status>` no estado. O React o alimenta com `tr.setMeta(key, map)`. Transação só de meta **não dispara `onUpdate`/autosave** (o Tiptap só emite `update` com `docChanged`). Já existe precedente: `bumpResponses` em `Editor.tsx:~486`.
3. O plugin gera `Decoration.node` para cada taskItem cujo **primeiro parágrafo** contém um `taskRef` com id conhecido, com spec `{ taskStatus }` + attr `data-task-status`. A troca de decoration força o `update(node, decorations)` da NodeView, que faz `checkbox.checked = status === 'done'` e `li.dataset.checked`, com fallback para `node.attrs.checked` quando não há decoration.
4. Clique no checkbox de item vinculado: chama um callback (via `extension.options`/`editor.storage`) → `updateTask(id, done|todo)`.
   - **Recomendação (híbrido):** o clique na própria nota também aplica `setNodeMarkup(checked)`. É uma edição do usuário na nota, legítima. Assim o `- [x]` fica coerente para RAG/export/chat na maioria dos casos. O que nunca acontece é a tabela → nota. Status mudado fora da nota aparece só por decoration, e o markdown fica defasado (aceito).
5. Task inexistente (sem entrada no Map) → sem decoration → checkbox comum, e a pill não renderiza nada. Cobre o edge case.

Alternativa descartada: `ReactNodeViewRenderer` no taskItem. Daria acesso direto ao contexto, mas NodeView React em list item com conteúdo aninhado é mais pesada e arriscada (seleção, wrappers do contentDOM, widget de drag). O React fica só na pill.

**Impacto do `- [ ]` defasado**
- `CalendarView.tsx:15` `noteHasUnfinishedTodos` (`/^- \[ \] .+/m`) pinta o dot roxo. **Mudar para ignorar linhas que contêm `<task-ref`**: itens promovidos passam a ser representados pelos marcadores laranja das tasks, e não contam duas vezes nem ficam presos por markdown defasado.
- RAG/chat `/week` veem o `[ ]`/`[x]` da nota (podendo estar defasado): aceitável no MVP.

**Sincronizar o título:** fazer como o `useReminders` (regex no markdown): para cada linha com `<task-ref data-id>`, título = texto sem tags e sem `- [ ] `. **Atualizar só quando `note.id === task.source_note_id`**, para evitar ping-pong entre cópias coladas. Rodar no main com debounce sobre `notes`. As edições da keep chegam no main pelo `refreshNotes` no focus, que já existe.

## 4. BubbleMenu "Add to Tasks"

- `FormattingToolbar.tsx` já usa `useEditorState` com selector. Basta acrescentar `eligibleTaskItems`: `doc.nodesBetween(from, to)` coletando `taskItem` cujo **primeiro parágrafo intersecta a seleção** (atenção: o `nodesBetween` também visita ancestrais. Sem esse filtro, selecionar uma subtarefa promoveria a task pai) e que não tenham `taskRef` com id existente. O botão aparece se `eligible.length > 0`, seguindo o padrão do `onAskAi` (prop vinda do Editor/App).
- **Popover fora do BubbleMenu:** o BubbleMenu esconde quando o editor perde foco/seleção, e um `<input type="date">` rouba o foco. Seguir o padrão do `TimePicker`: o clique captura as posições/itens e fecha o menu, o Editor abre um popover `position: fixed` nas coords da seleção (`view.coordsAtPos`), e o Enter confirma.
- Ao confirmar: cria as tasks (status = `checked ? done : todo`, `source_note_id` = nota ativa) e insere `taskRef` no fim do primeiro parágrafo de cada item, em **ordem reversa de posição**, numa única transação.
- Sugestão de projeto: `task_projects.notebook_id === activeNote.notebookId`.
- A keep não tem FormattingToolbar, então "Add to Tasks" fica só no main (ok).

## 5. Caderno especial Calendar → Tasks

**Como o Calendar é feito**
- Linha **real** na tabela `notebooks` com id fixo `'calendar'` (`lib/calendar.ts`), criada por UPSERT em `App.tsx:376-395`.
- `NotebookList.tsx:475-499` renderiza essa linha à parte (ícone, sem drag/rename/delete) e a filtra da lista ordenável. `Sidebar.tsx:261` e o move de notebook a filtram dos destinos.
- `App.tsx:1433`: quando `activeNotebookId === calendarNotebookId`, o `CalendarView` **substitui a Sidebar** (lista de notas) e o Editor continua mostrando a nota diária.

**Recomendação: NÃO criar `tasks` como linha em `notebooks`**
Uma linha em `notebooks` apareceria em tudo que lista cadernos: ChatPanel (pastas), SaveToNoteModal, QuoteToNoteModal, NotebookPickerModal, SearchPalette, Library/Reader, e `useNotesIndexSync` (criaria pasta RAG de notas vazia). Também não pode receber notas: `handleCreateNote`/Ctrl+N com `activeNotebookId='tasks'` criaria nota órfã. Proposta:
- Entrada fixa **virtual** no `NotebookList` (ícone `CheckSquare`/`ListChecks`, logo abaixo do Calendar), sem linha no banco.
- Estado próprio no App (ex.: `tasksViewOpen` + `selectedTaskId`) em vez de um id sentinela em `activeNotebookId`. Se preferirem o sentinela, guardar `handleCreateNote`, `useSubjects`, `chatNotebookId`, `EmptyEditor` etc.
- **Layout:** a TasksView deve ocupar **Sidebar + Editor** (lista agrupada à esquerda, painel de detalhe à direita), mantendo NotebookList e AiPanel. Só no slot da Sidebar (160–400px) a lista + detalhe ficaria apertada.
- "Open source note": `setActiveNotebookId(note.notebookId); setActiveId(id)`, sumindo se a nota não existir em `notes`.
- Card de task no Calendar → abrir a TasksView com `selectedTaskId`.

## 6. Migrations e storage

- Próxima versão livre: **17** (`src-tauri/src/lib.rs`, a última é `16 books_epub_support`). Padrão: `Migration { version, description, sql, kind: Up }` com comentário dizendo que a tabela é de propriedade do frontend.
- **Risco conhecido:** `storage/tauri.ts:498-513` documenta que builds antigos do MSI aplicaram uma v11 diferente e o sistema de migrations em produção pode estar travado (checksum mismatch, e o plugin pula o migrate). Por isso existe `ensureReminderStateTable`. **Recomendo o mesmo: `ensureTasksTables()` idempotente (`CREATE TABLE IF NOT EXISTS` + índices) chamado nos métodos de tasks**, além da migration 17.
- Camada: tipos em `src/types/index.ts` (`Task`, `TaskStatus`, `TaskProject`), métodos na interface `StorageAdapter` (`storage/index.ts`), implementação em `storage/tauri.ts` (Row + `rowToX` + `INSERT ... ON CONFLICT(id) DO UPDATE` + `this.scheduleCheckpoint()`) e stubs que lançam erro em `storage/browser.ts`. Hook `useTasks` no estilo de `useNotebooks` (atualização otimista + `saveError`).
- Sugestão de índices: `tasks(status)`, `tasks(due_date)`, `tasks(source_note_id)`. Sem FK para `notes` (a task sobrevive à nota). `project_id` com FK `ON DELETE SET NULL` ou tratado na aplicação.
- Regras (`reschedule_count`, `completed_at`) devem ficar numa função pura em `src/lib/tasks.ts` (`applyTaskPatch(prev, patch)`), usada por todas as janelas.

## 7. Janelas secundárias e sync

- `main.tsx` escolhe a janela pelo label: `assistant` (chat, não toca notas: **não precisa de nada**) e `keep` (edita a nota diária de hoje com `buildBaseExtensions`: **precisa**).
- Precedente: `useReminders` faz `emit('reminders-fired', ...)` e a keep faz `listen` (`KeepPanel.tsx:152`). As capabilities já incluem as 3 janelas.
- Proposta: toda mutação de task faz `emit('tasks-changed')`. Main e keep fazem `listen` e recarregam da tabela (ou aplicam o payload). Na keep: carregar as tasks no `keep-shown`, prover `TasksProvider` + alimentar o plugin de status, e o clique no checkbox grava na tabela e emite. O `emit` do JS chega a todas as janelas, inclusive a emissora, então o main pode usar o mesmo caminho de reload.

## 8. CalendarView: dots, cards e cores

**Hoje** (`CalendarView.tsx`)
- `dayDotMap`: dot por dia para notas diárias e notas com `date`. `todo` = roxo (`#9370db`), `content` = **vermelho** (`.dot` base `#e05555`).
- **Laranja (`.dotOrange #ef9f27`) já é usado** para "houve atividade hoje".
- `dayCards`: notas `dated` (borda `--accent`) e notas criadas/editadas no dia (borda `--accent-ai`).
- `today = useMemo(() => new Date(), [])` **nunca atualiza**: a virada de dia com o app aberto já é um bug latente e precisa de um `useToday()` (tick/focus) para Today/Overdue funcionarem.

**Onde encaixar**
- Passar `tasks` como prop. Em `src/lib/tasks.ts`, funções puras: `taskSpan(task, todayKey)` (de `created_at` até `due_date`; sem prazo → só hoje; vencida → `null` + overdue; `due < created` → overdue), `isOverdue`, `completedOn(dayKey)`.
- Grade: marcador laranja próprio (ex.: barrinha/anel sob o número, para coexistir com o dot de nota). No dia do prazo, um destaque mais forte.
- Abaixo da grade: bloco **Overdue** (só quando `selectedDay === todayKey`), depois a seção **Tasks** (cards laranja com checkbox, e riscadas as `done` do dia passado por `completed_at`) com botão "+ task", depois os cards de notas existentes.

**Tokens/tema**
- Só existe tema **escuro** (`App.css :root`, `color-scheme: dark`). Não há light theme, então o requisito "light/dark" se reduz ao tema atual.
- Tokens: `--accent`, `--accent-ai`, `--accent-warn (#ef9f27)`, `--surface-1..3`, `--text-*`, `--border`. Não há token de vermelho/perigo.
- **Conflito de cores:** o laranja já significa "atividade hoje" e o vermelho já é o dot de "nota com conteúdo". Recomendação: criar `--accent-task` (laranja) e `--accent-danger` (vermelho) em `App.css`, e recolorir o dot "atividade hoje" e o dot base de conteúdo para algo neutro (ex.: `--text-muted`/`--accent`). Sem isso, laranja e vermelho ficam ambíguos no Calendar.

## 9. Riscos e recomendações

| # | Risco | Recomendação |
|---|-------|--------------|
| 1 | `tasks` como linha em `notebooks` vaza para ~8 lugares e permite notas órfãs | **Mudança de design:** entrada virtual no NotebookList + estado próprio no App |
| 2 | Migrations em produção possivelmente travadas (histórico da v11) | Migration 17 **e** `ensureTasksTables()` idempotente no storage |
| 3 | Esquecer `TaskRef`/TaskItem estendido em `buildBaseExtensions` → keep apaga tags | Registrar só em `extensions.ts` |
| 4 | Markdown `- [ ]` defasado quando o status muda fora da nota | Híbrido (clique na nota escreve; tabela nunca escreve) + `noteHasUnfinishedTodos` ignora linhas com `<task-ref` |
| 5 | Popover dentro do BubbleMenu some ao focar o input de data | Popover fixo fora do menu (padrão TimePicker) |
| 6 | `nodesBetween` pega taskItem ancestral | Filtrar pelo primeiro parágrafo intersectando a seleção |
| 7 | Cores laranja/vermelho já usadas no Calendar | Tokens novos + recolorir os dots atuais |
| 8 | `today` congelado no CalendarView | Hook `useToday()` compartilhado com a TasksView |
| 9 | Título com cópias da mesma task-ref em várias notas | Sincronizar só a partir de `source_note_id` |
| 10 | Enter no meio de item vinculado pode levar a pill para o novo item | Aceitar no MVP (a pill fica no fim, então o caso comum é seguro) |
| 11 | PRD lista "Não é um gerenciador de tarefas" como não-meta (`PRD.md:129`) | Não bloqueia (aprovado pelo Coordenador), mas o PRD deve ser atualizado depois |

**Ordem sugerida para o planner:** (1) tipos + storage + migration + `lib/tasks.ts`; (2) `useTasks` + evento `tasks-changed`; (3) TaskRef + TaskItem estendido + plugin de status + contexto (main e keep); (4) "Add to Tasks" + popover; (5) TasksView + entrada no NotebookList; (6) integração com o Calendar + tokens + `useToday`; (7) sync de título.

**Mudança de escopo:** só a do item 1 (Tasks como caderno virtual, não como linha em `notebooks`) e a do item 7 (recolorir os dots existentes). O resto cabe no escopo aprovado.
