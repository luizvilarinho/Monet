## Item 1 — O que a IA enxerga da nota

### Como a nota é guardada
`note.content` é markdown gerado pelo tiptap-markdown. Os blocos customizados são gravados como HTML cru:
- `embedBlock` → `<embed-block data-cmd="<responseId>" data-collapsed="…"></embed-block>`: **vazio**. O texto fica na tabela SQLite `ai_responses` (`id` = `commandId`).
- `toggleBlock` → `<div data-type="toggle-block" data-title="…" data-collapsed="…">…HTML interno…</div>`: o conteúdo está lá, em HTML.
- `linkedNoteBlock` → `<linked-note data-note-id="…" …></linked-note>`: vazio, guarda só o id.

### Como cada caminho serializa hoje

| Caminho | Onde | Resposta embutida | Toggle | Nota linkada |
| ------- | ---- | ----------------- | ------ | ------------ |
| RAG de notas (alimenta o chat principal e o NotesChat via busca) | `useNotesIndexSync` → `buildNoteFileText` → `cleanNoteContentForAi` (`src/lib/noteFileText.ts`) | **Perdida**: `EMBED_BLOCK_RE` só cobre o formato antigo `<!--monet-embed:…-->`, então a tag `<embed-block …>` chega crua no texto | Incluído (título + texto, sem formatação) | Só `[Linked note: título]` |
| NotesChat (contexto efêmero) | `buildNotesContext` → `cleanNoteContentForAi` (`src/components/NotesChat/notesContext.ts`) | Perdida (igual acima) | Incluído | Só o título |
| Slash commands (nota atual) | `App.tsx` `handleCommand` → `buildUserMessage` → só `stripCommandLines` | **Perdida** (tag crua) | Vai como HTML cru (a IA lê o texto no meio das tags) | Tag crua, sem título |
| Slash `/week` e notas datadas do Calendar | `getWeekCalendarNotes` / `getDatedNotes` → `stripEmbedBlockTags` + `stripCommandLines` | Removida de propósito | HTML cru | Tag crua |
| Export .md (não é IA) | `handleExport` → `expandEmbedBlocks` | Expandida como blockquote | — | — |

O chat principal (`useChat` modo `main`) não manda a nota aberta: ele só vê notas pelo RAG. O Assistant e o Reader não entram neste item.

### Problemas encontrados
1. **A resposta embutida não chega à IA em nenhum caminho.** A regex de embed é de um formato legado, e o RAG e o NotesChat mandam a tag `<embed-block …>` como lixo.
2. **Os slash commands não usam o serializador limpo.** Mandam o markdown cru, com o HTML do toggle e as tags de nota linkada e de task-ref.
3. **A regex do toggle (`TOGGLE_BLOCK_RE`, que é lazy até `</div>`) é frágil.** Toggles aninhados aparecem dentro do HTML como `<toggle-block …>`: o título do toggle interno se perde, e listas viram texto sem marcador. Funciona no caso comum, mas não é "igual ao conteúdo fora do toggle".
4. **Os textos das respostas só existem carregados para a nota ativa** (`useAi(activeId)`, carga preguiçosa). O RAG precisa das respostas de qualquer nota, então falta um método de storage (ex.: `getResponseTexts(ids): Map<id, string>` com `SELECT id, response FROM ai_responses WHERE id IN (…)`).

### Proposta: ponto único de serialização
Evoluir `cleanNoteContentForAi` em `src/lib/noteFileText.ts` (ou renomear para `serializeNoteForAi`) recebendo resolvers:

```ts
serializeNoteForAi(content, {
  resolveNoteTitle,                 // já existe
  resolveNoteContent?,              // id → content (notesRef), 1 nível, ignora ciclo/link quebrado
  resolveEmbedResponse?,            // commandId → texto da resposta; ausente = ignora
  linkedNoteBudget?,                // truncar cada nota linkada (ex.: 2000 chars)
})
```

- Expandir `<embed-block>` e `<linked-note>` **antes** do toggle, porque eles podem estar dentro dele (a ordem atual da cadeia já favorece isso).
- Delimitadores sugeridos: `[AI response — /cmd]` … `[/AI response]` e `[Linked note: título]` … `[/Linked note]`. O conteúdo do toggle entra como texto normal (título + corpo), sem marcador.
- Nota linkada: o conteúdo dela passa pelo mesmo serializador **sem** `resolveNoteContent` (profundidade 1), o que já resolve os ciclos.
- Toggle: trocar a regex por um parse com `DOMParser`/`template` (o código roda no WebView, e o próprio ToggleBlock já usa `document`). Assim dá para tratar toggles aninhados e gerar `- ` para `li`. É opcional, mas é o que torna o conteúdo "igual ao de fora do toggle".

Consumidores após a mudança:
- `buildNoteFileText` (RAG) e `buildNotesContext` (NotesChat): já usam a função, só passam os resolvers novos.
- `handleCommand`/`buildUserMessage`, `getWeekCalendarNotes`, `getDatedNotes` (App.tsx): passam a usar a função. Com isso `stripEmbedBlockTags` vira dead code e deve ser removida. `expandEmbedBlocks` continua só se o export quiser manter o formato blockquote; senão pode sair também.
- Para o NotesChat, o App precisa passar ao `NotesChatPanel` um resolver de resposta baseado em `responses` (nota ativa).

### Decisão de escopo para o Coordenador (RAG + nota linkada)
Expandir o conteúdo da nota linkada **dentro do arquivo RAG** da nota A tem dois custos:
- **Chunks duplicados:** B já é indexada sozinha, então a busca devolve B duas vezes.
- **Invalidação:** quando B muda, todas as notas que linkam B precisam ser reindexadas. O diff atual de `useNotesIndexSync` é por nota, então seria preciso varrer as notas procurando `data-note-id="B"`.

**Recomendação:** expandir a nota linkada só nos contextos efêmeros (NotesChat e slash commands) e manter `[Linked note: título]` no RAG. Resposta embutida e toggle entram no RAG normalmente. Para o RAG, a resposta embutida precisa do método de storage novo e de um cache no `useNotesIndexSync`. `fileTextFor` hoje é síncrono e também é usado na comparação do debounce: ou o cache é pré-carregado, ou essa comparação passa a ser assíncrona. Se o Coordenador quiser mesmo a nota linkada no RAG, dá para fazer (dificuldade sobe para Média/Alta pela invalidação).

### Limite de contexto
- O NotesChat já trunca a nota em 8000 chars (`NOTE_TEXT_BUDGET`). Esse orçamento vai passar a incluir as linkadas.
- Os slash commands **não têm limite** hoje. Sugestão: limitar cada nota linkada (ex.: 2000) e o total (ex.: 12000).

## Item 2 — Exclusão de tasks

### O que já existe
- `storage.deleteTask(id)` (`src/storage/tauri.ts:698`), `useTasks.deleteTask` (`src/hooks/useTasks.ts:154`) e `App.deleteProjectTask` (`App.tsx:648`), que apaga a task **e a nota-corpo**.
- Exclusão individual já existe no `TaskPropertiesBar` (barra no topo da nota da task), com confirmação via `useConfirm`. Falta a ação na linha/card.
- Seleção múltipla já existe em `useTaskKeyboard` (Ctrl/Shift+clique, Shift+setas), compartilhada por `TasksView`, `KanbanBoard` e `WeekBoard`. `TaskBatchBar` aparece com 2+ selecionadas.

### Pontos a mexer
- `useTasks`: criar `deleteTasks(ids)` no padrão de `updateTasks` (um `setTasks`, um `tasks-changed`, deletes sequenciais, **sem BEGIN/COMMIT**).
- `App`: `deleteProjectTasks(ids)` → `deleteTasks` + `removeNote` de cada nota-corpo. Se a task aberta no editor estiver entre as apagadas, fechar antes, como o `onDelete` atual faz (`showTaskNote(null)` / `setActiveId(null)`).
- `useTaskKeyboard`: expor `deleteSelected` (com os `targets`). `TaskBatchBar`: botão "Delete" com `ConfirmModal`.
- `TaskLine` / card do Kanban / card do WeekBoard: ação de excluir no hover ou em menu.
- Botão "Clear" no grupo Done do `TasksView` (cabeçalho da seção `key === 'done'`) e na coluna "Done this week" do `KanbanBoard`. O WeekBoard não tem coluna Done.

### Riscos e ambiguidades
- **TaskRef/LinkedTaskItem: sem risco de quebra.** `TaskRefView` já renderiza vazio quando a task não existe, e o checkbox volta a usar o atributo `checked` da nota, que pode estar defasado. `findEligibleTaskItems` deixa o item virar task de novo. RAG e resumo de tasks se atualizam pelo diff.
- **O que o "Clear" apaga (decidir):**
  - Na lista, o grupo "Done" é cortado em 50 (`DONE_LIMIT`).
  - Nos modos *date* e *project*, o grupo "Done" inclui também as tasks **dropped** (`!isOpen`).
  - No Kanban, a coluna mostra só as concluídas **nesta semana**.
  - **Sugestão:** o Clear apaga exatamente as tasks do escopo que o grupo representa (status do grupo + filtro de projeto atual, sem o corte de 50), e a confirmação mostra a contagem ("Delete 73 done tasks and their notes?"). No Kanban, apagar só o que a coluna mostra.
- **Conflito de nome:** a `TaskBatchBar` já tem um botão "Clear" (limpar seleção). Para o Done, usar "Clear done" ou "Clear all".
- A tecla `Delete` hoje marca como *dropped*. Manter assim (excluir é irreversível e não há undo) ou usar outra combinação.
- Apagar a task apaga a nota-corpo, e não há desfazer: a confirmação deve dizer isso.

## Item 4 — Tools e memória no NotesChat

### O que já existe
A memória por caderno **já está implementada** (commit `63b4f51`, "feat: chat e RAG nas anotações", 2026-10-11):
- Cada caderno tem uma pasta de chat própria: `ensureScopedFolder({ kind: 'notebook' })`, com o vínculo em `monet:notes-notebook-folder-link`. As conversas do NotesChat ficam nessa pasta (`ChatConversation.folderId`).
- O `NotesChatPanel` já mostra o `ChatToolsMenu` (Web Search + "Folder memory"), um botão 🧠 que abre o `FolderMemoryModal`, o system prompt e os documentos da pasta.
- O `useChat.send` resolve `containingFolder` pela conversa. Com `memoryEnabled`, injeta `MEMORY_SYSTEM_PROMPT` + a memória atual e expõe a tool `update_folder_memory`, igual ao chat principal.

**Por que o usuário pode achar que não existe:**
- A memória nasce **desligada** (`memoryEnabled: false` em `makeNewFolder`).
- O toggle fica escondido dentro do menu de ferramentas, com o rótulo genérico "Folder memory".
- A tool só funciona com modelo que suporta tools.

### Recomendação
Não criar uma memória nova. Ajustes sugeridos:
1. Renomear para "Notebook memory" no contexto do NotesChat. O `ChatToolsMenu` pode receber um `label` opcional.
2. Opcional: ligar a memória por padrão nas pastas criadas por `ensureScopedFolder` de caderno.
3. **Tool Tasks (`query_tasks`)**: no NotesChat, passar `getTasksSnapshot` ao `useChat(models, { mode: 'notes', getTasksSnapshot })` e `tasksTool={{ supported }}` ao menu. Isso complementa as tasks do caderno que já vão no contexto efêmero.
4. **Save web sources** (`folderWebResearch`): basta passar `folderWebResearch` e `setFolderWebResearchEnabled`, que já são retornados por `useChat`.
5. **Deep Research**: o estado `tools` é **compartilhado via localStorage** (`monet:chat-tools`) entre as instâncias. Se o usuário ligou Deep Research no chat principal, o NotesChat herda isso ao montar **sem nenhum botão ou indicador**, e também não mostra `deepResearchPhase`. Expor o botão e o progresso ou forçar desligado no modo `notes`. Isso é um bug latente, vale corrigir junto.
6. Thinking toggle e anexar arquivo/imagem: dá para expor (o `useChat` já suporta), mas é opcional e fica fora do foco "memória".
