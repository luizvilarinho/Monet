## Decisões de design (fixas; o codeAgent não decide)

**D1. TaskStatus.** `type TaskStatus = string`. Built-ins: `todo`, `doing`, `done`, `dropped` (`BUILTIN_STATUS_IDS`). Helpers únicos em `src/lib/tasks.ts`: `isDone(t)`, `isDropped(t)`, `isOpen(t) = !isDone && !isDropped`. Semântica de `isOpen` para custom: **aberto** (conta em Doing/Week/Overdue/Calendar/DueToday/review; nunca concluído). Proibido `status === 'todo' || status === 'doing'` fora desses helpers.

**D2. Registro.** Tabela SQLite `task_statuses(id TEXT PK, name TEXT NOT NULL, color TEXT, sort_order INTEGER NOT NULL, wip_limit INTEGER NULL, builtin INTEGER NOT NULL DEFAULT 0)`. Seed `INSERT OR IGNORE` dos 4 built-ins (ids fixos, sort 0..3). Ids custom = `st_<nanoid(8)>`, nunca reaproveitados; renomear só altera `name`. Built-ins: só cor e WIP editáveis (`done`/`dropped` sem WIP); não renomeáveis nem excluíveis. Sem reordenação manual (fora de escopo).

**D3. Migração idempotente, sem BEGIN/COMMIT.** Tudo em `ensureTasksTables` (src/storage/tauri.ts:616, já memoizada e zerada em falha): `CREATE TABLE IF NOT EXISTS` em `TASKS_TABLES_SQL`; colunas novas em `TASKS_EXTRA_COLUMNS` via `PRAGMA table_info` + `ALTER` tolerando "duplicate column"; seed por `INSERT OR IGNORE` (cada statement um `db.execute` independente). Para `notebooks.color`, helper `ensureNotebookColorColumn` memoizado, mesmo tratamento de "duplicate column". Excluir status = 2 execuções separadas, nesta ordem: `UPDATE notebook_tasks SET status='todo' WHERE status=?` e depois `DELETE FROM task_statuses WHERE id=? AND builtin=0`; falha entre as duas é segura (reexecutar é idempotente). Nunca BEGIN/COMMIT (pool sqlx). Não depender das migrations Rust (não rodam em prod).

**D4. Múltiplas janelas (main/Keep/assistant).** Toda leitura/escrita das tabelas novas passa por `ensureTasksTables` (nunca assumir que a janela principal já criou). Estado compartilhado = SQLite, não localStorage (exceto visão ativa, preferência por janela). Hook `useTaskStatuses` (carrega no mount + `listen('tasks-changed')`, mesmo `origin` do `useTasks`); CRUD emite `tasks-changed`; `useTasks.reload` também recarrega statuses. Saved views e cor de projeto usam o mesmo evento (sem canal novo). Fallback de render: status desconhecido (ex.: excluído em outra janela) é exibido como aberto, nome = id, cor neutra; nunca descartado nem reescrito. Corrida de seed/ALTER coberta por D3.

**D5. normalizeTaskStatus** (tauri.ts:282) deixa de descartar: aceita qualquer string não vazia; vazio/null vira `'todo'`.

**D6. Mover task entre projetos (S4).** Reutilizar `relocateTask`/`moveProjectTask` (App.tsx:614-632): move a nota-corpo (`notebookId` + `subjectId = ensureTasksSubject(dest)`) e depois `updateTask({notebookId})`. Não criar caminho paralelo. Ordem: nota primeiro, task depois; se `saveNote` falhar, não atualizar a task e mostrar `saveError`. Drop na mesma coluna = no-op. Inbox usa o id do caderno Inbox existente. Recorrente: move só a ocorrência atual.

**D7. Visões declarativas.** `src/components/TasksView/views.ts` exporta `TASK_VIEWS` (`list, week, kanban, projects, groups, review`, depois `plan`); saved views vêm do banco no mesmo dropdown (grupo "Saved"). `TasksMainView = string`, validada contra a lista; fallback `list`.

**D8. Colunas genéricas.** Extrair de `KanbanBoard.tsx` um `BoardColumns` (colunas `{key,title,color?,count,wipLimit?,cards,sections?}` + `cardFor` + `dropKey`) sobre `useCardDrag` (mouse manual existente). Instanciar Status (Kanban), Projects, Groups. Colunas de largura fixa (~260px) com scroll horizontal, no lugar de `repeat(3, minmax(...))`.
