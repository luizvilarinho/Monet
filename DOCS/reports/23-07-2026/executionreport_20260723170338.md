### CodeAgent — fix tool-calling loop — 20260723200500
- Summary: Substituído o fluxo fixo de "rodada 1 + follow-up hardcoded sem tools" por um loop recursivo de tool-calling com teto de rodadas, em `src/hooks/useChat.ts`, dentro de `send()`.
- Estrutura do loop: extraída uma função `registerToolCallHandler(expectedRequestId, upcomingRound, priorToolMessages)` que registra `toolCallHandlerRef.current` fechando sobre o `requestId` esperado daquela rodada (bug lateral encontrado e corrigido de graça: o código antigo validava `p.requestId` contra o `requestId` da 1ª chamada mesmo dentro do handler da 2ª rodada — como os `requestId` de cada rodada são gerados via `crypto.randomUUID()`, mesmo sem o zeramento do handler o encadeamento nunca teria funcionado por causa desse mismatch). A chamada inicial (rodada 1) continua exatamente como antes: sempre com `tools: toolsPayload`, sem gate de teto — preserva 100% o comportamento pra quem não chama tool nenhuma. `registerToolCallHandler(requestId, 2, [])` é chamado logo antes dela. Quando o handler processa uma tool call, monta `roundToolMessages` (acumulando `priorToolMessages` + o resultado desta rodada) e decide `canContinue = upcomingRound < MAX_TOOL_ROUNDS`: se true, a próxima chamada sai com `tools: toolsPayload` e um novo handler é re-registrado (`registerToolCallHandler(nextRequestId, upcomingRound + 1, roundToolMessages)`) para permitir mais uma tool call encadeada; se false, a chamada sai sem `tools` e `toolCallHandlerRef.current = null` — força resposta final em texto e termina o loop (sem handler pendente, não há como um tool_call subsequente ser processado mesmo que o modelo tentasse).
- Teto escolhido: `MAX_TOOL_ROUNDS = 3` (constante de módulo, junto de `DEFAULT_TOOLS`). Com a rodada 1 sempre tendo tools, e o gate sendo `upcomingRound < MAX_TOOL_ROUNDS`, o resultado é: rodada 1 (tools) → rodada 2 (tools, `2 < 3`) → rodada 3 (sem tools, `3 < 3` é false, força texto). Ou seja, 2 rodadas com tool-calling disponível (cobre o caso `web_search` → `save_web_source` pedido pelo Coordenador) e a 3ª sempre textual, evitando loop infinito. O valor antigo (implícito, sem teto configurável) equivalia a `MAX_TOOL_ROUNDS = 2` (rodada 1 com tools, rodada 2 sempre sem) — só 1 chance de tool call, por isso `save_web_source` nunca aparecia disponível na prática.
- Comunicação do resultado de `save_web_source` pra rodada seguinte: seguindo o padrão já usado por `toolSearchMessage` (system message textual acumulado no payload da próxima chamada), adicionada uma variável irmã `saveWebSourceMessage` no mesmo escopo do handler, populada em 4 casos dentro do branch `save_web_source` já existente: sucesso (`"Source saved successfully: <title|url>."`, logo após `documentsScanWatchedFolder`), já salvo anteriormente / dedupe (`"Source already saved previously: <title|url>."`), extração falhou (`"Source save failed: could not extract content from <url>."`) e exceção capturada no catch existente (`"Source save failed: <mensagem>."`), além de um caso não coberto antes (url/folder ausentes) que agora também gera `"Source save failed: missing url or folder context."`. Esse resultado entra em `roundToolMessages` (junto de `toolSearchMessage`, se houver, e de qualquer mensagem de rodada anterior via `priorToolMessages`) e é injetado no payload da próxima chamada exatamente onde `toolSearchMessage` já entrava — o modelo vê o resultado e consegue mencioná-lo na resposta final em vez de tentar chamar a tool de novo à toa.
- Logs de diagnóstico: os 3 `console.log` (`SAVE_WEB_SOURCE: outer gate`, `SAVE_WEB_SOURCE: gate check`/`tool registered in toolDefs for this turn`, `SAVE_WEB_SEARCH ACTVATE`) foram mantidos intactos, apenas com números de linha deslocados pelo comentário novo acrescentado acima da constante `MAX_TOOL_ROUNDS`. Não removidos, conforme instrução.
