# Task: Web research persistida via KB por chat-folder

## Objective
Hoje, quando o modelo faz uma busca web dentro de uma chat-folder, o resultado só existe naquele turno — uma nova pergunta relacionada dispara uma busca nova do zero. O objetivo é permitir que o modelo decida, por conta própria, persistir fontes web relevantes de forma que fiquem recuperáveis via RAG em conversas futuras na mesma pasta, sem re-buscar. A decisão de arquitetura (já validada em conversa com o Coordenador) é reaproveitar o pipeline de RAG/watched-folders existente — não criar um armazenamento novo, e não usar o campo de memória da pasta (que é reinjetado inteiro no system prompt a cada turno e não deve carregar conteúdo bruto de artigo).

## Context
- `src/hooks/useChat.ts` — `ChatFolder` (system prompt padrão/override, `memory`/`memoryEnabled` com tool `update_folder_memory`, `visibleDocumentIds`), fluxo de tool calls do chat (`web_search`, `web_search_route`). O bloco de RAG do chat (`useChat.ts:2015-2036`) lê `containingFolder?.visibleDocumentIds` e chama `documentsSearchByIds` direto — **não consulta `notebook_document_visibility`** (essa tabela é usada só pela feature de Notebooks/notas, espaço de IDs diferente de `ChatFolder.id`). Chats fora de uma pasta (`containingFolder` undefined) não têm RAG — confirmado no código, não é uma lacuna a resolver.
- `src/components/ChatPanel/FolderDocumentSelectorModal.tsx` — mecanismo **já existente** pelo qual o usuário torna uma watched-folder da KB visível numa chat-folder: `toggleKbFolder` (linhas 108-123) expande os filhos *disponíveis no momento do toggle* e grava os IDs deles em `visibleDocumentIds`. É um snapshot estático — arquivos adicionados depois à watched-folder não aparecem automaticamente até o usuário reabrir o modal e re-marcar.
- `src/lib/search.ts` — `webSearch()` chama Tavily; hoje o chat usa `webSearch(q, 3)` sem `includeRawContent` (só snippet curto). Raw content completo só é buscado hoje em `src/lib/deepResearch.ts`, truncado a 3000–5000 chars.
- `src-tauri/src/documents.rs` — pipeline de documentos/RAG: `documents` table (`type='file'|'folder'`, `is_external`), `documents_add_watched_folder` (usuário escolhe pasta existente via diálogo, scan on-demand via `scan_watched_folder_async`, sem file watcher de SO), `chunk_and_embed`/`run_indexing`, busca KNN via `documents_search_by_ids` (`vec_chunks`/sqlite-vec, embeddings `openai/text-embedding-3-small`).
- `DOCS/specs/productVision.md` — restrição de produto: o que for salvo deve ser a fonte extraída, não uma síntese/resumo autoral do modelo (ponto 3: preservar o esforço de elaboração do usuário).

## Requirements
- Nova tool exposta ao modelo (mesmo padrão de `update_folder_memory`: descrição instruindo a só chamar quando julgar a fonte durável e relevante) para persistir uma fonte web encontrada durante a conversa.
- Ao ser chamada, buscar o raw content completo daquela URL específica (Tavily `include_raw_content: true`) — não reaproveitar o snippet curto já presente no contexto.
- Salvar o texto extraído sem edição/resumo do modelo, como `.md`, com cabeçalho de proveniência (título, URL de origem, data da busca). Um arquivo por fonte/URL.
- Cada chat-folder deve ter sua própria watched-folder de KB, criada automaticamente em disco na primeira vez que a pasta salvar uma fonte web (reaproveitando `documents` `type='folder'` + `is_external=1`; sem novo schema para os arquivos-filho).
- Essa watched-folder deve ser marcada visível automaticamente para a chat-folder de origem reaproveitando o mecanismo **já existente** de `visibleDocumentIds` — não `notebook_document_visibility` (não se aplica ao chat, ver Context). Em vez de gravar um snapshot dos filhos (como o `FolderDocumentSelectorModal` faz hoje), gravar o **ID da própria pasta** em `visibleDocumentIds` e resolver pasta→filhos dinamicamente no bloco de RAG do chat a cada busca (não mais um snapshot no momento da seleção).
- Essa resolução dinâmica (pasta → filhos atuais, calculada a cada busca RAG) deve valer para **qualquer** watched-folder referenciada em `visibleDocumentIds`, não só a gerada pela IA — corrige de uma vez a mesma defasagem para pastas escolhidas manualmente pelo usuário via `FolderDocumentSelectorModal`, que hoje não veem arquivos novos sem o usuário reabrir o modal e re-marcar. Decisão do Coordenador: sempre dinâmico, para não depender do usuário lembrar de atualizar.
- Após salvar o arquivo, o próprio modelo deve disparar o scan daquela pasta (não esperar startup do app nem botão manual), pra ficar pesquisável ainda na mesma sessão.
- A watched-folder criada pela IA deve aparecer na Knowledge Base como qualquer outra, de forma que o usuário possa ver/gerenciar/apagar — idealmente diferenciável como "gerada pela IA" vs. escolhida pelo usuário.
- Checar antes de salvar se já existe arquivo equivalente (mesma URL) na pasta, pra evitar refetch/duplicação.
- Toda a feature deve ser controlada por uma chave liga/desliga por chat-folder, no mesmo padrão de `memoryEnabled` (ex.: `webResearchEnabled`): a tool de salvar fonte web só é registrada/exposta ao modelo quando a flag estiver ligada — desligada, o modelo não grava fontes novas.
- A flag também controla a visibilidade em runtime: com a flag desligada, a watched-folder de KB já criada para aquela chat-folder deixa de ser considerada na busca RAG daquela pasta — mesmo que os arquivos continuem existindo em disco. Isso espelha o comportamento já validado de `memoryEnabled`, que hoje gate a injeção do blob de memória no system prompt independente do conteúdo já existir.
- Religar a flag deve tornar a watched-folder visível de novo sem recriar ou reindexar nada — apenas reabilitar a leitura do ID já presente em `visibleDocumentIds`.
- Ao apagar a watched-folder de KB gerada pela IA pela UI, os arquivos `.md` devem ser apagados fisicamente do disco (`fs::remove_dir_all` ou equivalente) — diferente do comportamento atual para watched-folders do usuário, que nunca apagam arquivo físico. Precisa de um campo/coluna que diferencie origem ("gerada pela IA" vs. escolhida pelo usuário) para não vazar esse comportamento para pastas do usuário.

## Constraints
- Reaproveitar o pipeline de RAG/watched-folders existente (`documents.rs`, chunk+embed, `vec_chunks`) — não inventar um sistema de storage paralelo.
- Não usar o campo `memory` da pasta para conteúdo bruto de artigo — isso é fora de escopo aqui e não deve ser alterado.
- Conteúdo salvo é a fonte extraída (equivalente à extração já feita pelo `pdf-extract` para PDFs) — nunca uma reescrita/síntese do modelo.
- Sem file watcher de SO; o scan continua on-demand, mas passa a ser disparado explicitamente pela própria ação de salvar.

## Edge Cases
- Pesquisas repetidas/quase-duplicadas sobre o mesmo tema em sessões diferentes — dedupe por URL antes de re-buscar/gravar.
- `documents_add_watched_folder` hoje espera um `folder_path` já existente (escolhido via diálogo nativo) — precisa de criação automática (`fs::create_dir_all` ou comando equivalente) quando é a IA criando a pasta pela primeira vez.
- Associação `ChatFolder.id` ↔ watched-folder de KB precisa ser criada de forma preguiçosa (no primeiro save) — resolvida: o ID da pasta entra em `ChatFolder.visibleDocumentIds`, mesmo campo/lugar que `FolderDocumentSelectorModal` já escreve hoje.
- Resolução dinâmica pasta→filhos a cada busca RAG tem custo de uma consulta a mais (listar filhos atuais da pasta) antes de `documentsSearchByIds` — avaliar no plano se isso é uma query local rápida o suficiente para não impactar a latência percebida do chat.
- `web_search` do chat hoje só busca snippet curto; a nova tool de "salvar" precisa do próprio fetch de raw content por URL, com custo/latência — não deve acontecer silenciosamente para todo resultado de busca, só quando o modelo decidir salvar.
- Poda/crescimento da pasta ao longo do tempo é explicitamente fora de escopo agora — mas a descrição da tool deve orientar o modelo a checar duplicatas antes de salvar, no mesmo espírito de contenção já observado em `update_folder_memory`.
- Tornar essa KB visível para outras chat-folders no futuro é mencionado como extensão possível (não requisito desta task) — a visibilidade many-to-many já existente não deve ser impedida por decisões tomadas aqui, mas não é necessário implementar agora.
- Ligar/desligar a flag repetidamente não pode duplicar registros de visibilidade nem perder a referência à watched-folder já criada — habilitar/desabilitar precisa ser idempotente (natural com a abordagem de `visibleDocumentIds`: é só um ID numa lista, sem tabela de visibilidade separada para duplicar).
- Chats fora de uma pasta nunca têm essa feature (nem RAG de forma alguma) — comportamento correto e já garantido por a feature inteira viver em campos de `ChatFolder`, não precisa de tratamento extra.
