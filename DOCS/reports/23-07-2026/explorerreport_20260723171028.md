# Explorer Report — Web research persistida via KB por chat-folder

Task Report: `DOCS/reports/23-07-2026/taskreport_20260723165801.md`

## 1. Problema

Permitir que o modelo, dentro de uma chat-folder, decida persistir uma fonte
web (conteúdo bruto extraído, sem síntese) como arquivo `.md` numa
watched-folder de KB própria daquela pasta, reaproveitando o pipeline de
RAG/watched-folders (`documents.rs`) — controlado por uma flag por pasta
(`webResearchEnabled`, mesmo padrão de `memoryEnabled`).

Analisei `src-tauri/src/documents.rs`, `src-tauri/src/lib.rs` (migrations e
comandos), `src/hooks/useChat.ts`, `src/lib/search.ts`,
`src/lib/deepResearch.ts`, `src/lib/documents.ts`, `src/hooks/useDocuments.ts`,
`src/types/index.ts`, `src/storage/*`, e os componentes de KB/Chat
(`KnowledgeBaseModal.tsx`, `FolderDocumentSelectorModal.tsx`,
`ChatPanel.tsx`).

## 2. Nível de dificuldade: **Média**

Nenhum requisito é arquiteturalmente inviável — todos têm precedente direto
no código atual. A dificuldade vem da coordenação entre 4 camadas (SQLite via
`documents.rs`, filesystem, chamada externa Tavily, estado de `ChatFolder` em
localStorage) e de **um desalinhamento real entre o que o Task Report assume
sobre `notebook_document_visibility` e o que o código de chat de fato
consulta hoje** (seção 3). Resolver essa decisão antes do planejamento evita
retrabalho — sem isso, o risco sobe para Alta.

## 3. Achado arquitetural central (precisa de decisão do Coordenador)

O Task Report pede para reaproveitar `notebook_document_visibility` e sua
"propagação pai→filhos já existente" para tornar a watched-folder de KB
visível à chat-folder de origem. Essa propagação **existe** no backend
(`documents.rs:1230-1243`, dentro de `scan_watched_folder_async`), mas **o
chat não a consulta**:

- `ChatFolder` (`src/hooks/useChat.ts:176-188`) é persistida inteira em
  `localStorage` (`FOLDERS_KEY`), não tem relação com a tabela `notebooks`
  nem com `notebook_document_visibility`.
- A visibilidade de documentos para RAG do chat vem de
  `ChatFolder.visibleDocumentIds` — um array **estático** de IDs de arquivo,
  selecionado manualmente pelo usuário em
  `FolderDocumentSelectorModal.tsx` (que expande "pasta" para os IDs dos
  filhos *disponíveis no momento da seleção*, `toggleKbFolder`,
  linhas 108-123) e usado diretamente em `useChat.ts:2017-2036`
  (`documentsSearchByIds(folderDocIds, ...)`), sem nunca chamar
  `documents_get_notebook_visible_ids`.
- `notebook_document_visibility` / `documents_set_notebook_visibility` /
  `documents_get_notebook_visible_ids` só são usados hoje pela feature de
  Notebooks (notas), via `useNotebookVisibility` em
  `src/hooks/useDocuments.ts:131-175` e `App.tsx` (`notebookId` vem da
  tabela SQL `notebooks`, um espaço de IDs diferente do `ChatFolder.id`
  gerado por `nanoid()`).

Ou seja: usar `notebook_document_visibility` para esta feature seria uma
**aplicação nova** desse mecanismo ao chat (tecnicamente possível — a coluna
é `TEXT` sem FK, aceitaria o `ChatFolder.id`), mas exigiria também alterar o
bloco de RAG do chat em `useChat.ts` para passar a consultar essa tabela
(hoje ele não consulta). Além disso, a propagação pai→filhos só copia
visibilidade de um *sibling já visível* — o primeiro arquivo salvo numa pasta
nova ainda precisaria de um `documents_set_notebook_visibility` explícito.

**Recomendação:** não usar `notebook_document_visibility` para esta feature.
Guardar o vínculo `ChatFolder → webResearchFolderId` diretamente no
`ChatFolder` (mesmo lugar de `memory`/`memoryEnabled`) e, no bloco de RAG já
existente (`useChat.ts:2015-2036`), expandir dinamicamente os filhos
`available` dessa pasta (via `documentsListGlobal()` já disponível no
frontend) e mesclar com `visibleDocumentIds` antes de chamar
`documentsSearchByIds`. Isso:
- Resolve “ligar a flag reativa sem recriar nada” de graça (é só um `if` na
  hora da query — não há registro de visibilidade para duplicar/perder).
- Resolve “arquivos novos ficam visíveis automaticamente” de graça (a
  expansão é sempre pelo estado atual em disco/DB, não por um snapshot).
- Não impede a visibilidade many-to-many futura mencionada como extensão: a
  pasta de KB da IA continua sendo um `documents` row comum, selecionável
  por qualquer outra chat-folder via `FolderDocumentSelectorModal` já
  existente.
- Não precisa de nenhuma migration para visibilidade — só o campo novo em
  `ChatFolder`.

Se o Coordenador preferir manter `notebook_document_visibility` por
consistência conceitual com o resto do sistema, é viável, mas o escopo deve
explicitamente incluir a alteração do bloco de RAG do chat para consultá-la
(hoje não consulta) e o tratamento do "primeiro arquivo" sem propagação.

## 5. Edge cases do Task Report — análise

- **Dedupe por URL** — resolvido pela recomendação de nome de arquivo
  determinístico (hash da URL). Simples e evita fetch desnecessário.
- **`documents_add_watched_folder` exige pasta existente** — confirmado no
  código; precisa de comando/variante nova com `fs::create_dir_all`. Sem
  solução pronta no código atual, mas o padrão (`save_chat_doc`) já mostra
  como fazer isso com segurança de path.
- **Onde persistir a associação `ChatFolder.id ↔ watched-folder`** —
  respondido: no próprio objeto `ChatFolder` em localStorage, mesmo lugar de
  `memory`/`memoryEnabled`/`visibleDocumentIds`. Não há necessidade de tocar
  `src/storage/*` (essa camada só cobre notebooks/notas/books via
  `StorageAdapter`, não `ChatFolder`).
- **Custo/latência do fetch de raw content só ao salvar, não a cada busca**
  — natural na proposta: a tool `save_web_source` é uma ação separada de
  `web_search`, só disparada quando o modelo decide chamar.
- **Poda/crescimento fora de escopo** — confirmado, nada no código atual
  impede isso ficar para depois.
- **Não travar many-to-many futuro** — confirmado que a recomendação da
  seção 3 não trava isso (ver seção 3, último parágrafo).
- **Idempotência de ligar/desligar repetidamente** — resolvida "de graça"
  pela recomendação da seção 3 (não há registro de visibilidade para
  duplicar). Se o Coordenador optar por `notebook_document_visibility`
  mesmo assim, a idempotência já existe no SQL (`INSERT OR IGNORE` /
  `DELETE` em `documents_set_notebook_visibility`, `documents.rs:824-841`).

## 6. Gaps não listados no Task Report (riscos a decidir)

1. **Arquivos órfãos ao apagar a watched-folder pela UI.** Hoje,
   `documents_delete_watched_folder`/`delete_folder_child`
   (`documents.rs:1018-1034`, `1283-1323`) nunca chamam `fs::remove_file`
   para os filhos de uma pasta — por design, porque watched-folders hoje são
   sempre diretórios do usuário (não se deve apagar arquivo do usuário). Mas
   a pasta de KB da IA é gerenciada pelo próprio Monet (criada por ele, sob
   `app_data_dir`) — se o usuário a remover pela KB (requisito explícito do
   Task Report: "usuário possa ver/gerenciar/apagar"), os `.md` continuam no
   disco para sempre, e `ChatFolder.webResearchFolderId` fica apontando para
   um `documents.id` que não existe mais. Precisa de uma decisão: (a) aceitar
   o vazamento de disco e tratar a "pasta sumiu" recriando uma pasta nova na
   próxima gravação, ou (b) usar a nova coluna `origin`/`is_ai_generated`
   para, só nesse caso, apagar o diretório físico também
   (`fs::remove_dir_all`) — cuidado para não vazar esse comportamento para
   watched-folders normais do usuário.
2. **Corrida entre "salvar" e "ficar pesquisável".**
   `documents_scan_watched_folder` dispara indexação em background e
   retorna na hora (`documents.rs:1271-1281`); `run_indexing` envolve uma
   chamada de rede para embeddings. Se o modelo disser "salvei a fonte" e o
   usuário perguntar algo sobre ela no turno seguinte imediatamente, a
   indexação pode não ter terminado ainda. Não é um requisito do Task
   Report ("ainda na mesma sessão" é satisfeito mesmo com essa corrida —
   só não é *instantâneo*), mas vale registrar como comportamento esperado,
   não bug, para não gerar expectativa errada.
3. **`is_external` semanticamente não encaixa para a pasta de KB da IA.**
   A pasta seria escrita e gerenciada pelo Monet (não é um diretório
   "externo" do usuário), mas o único comando de criação de watched-folder
   hoje sempre grava `is_external=1`. Um comando novo dedicado pode gravar
   `is_external=0` corretamente — mas isso também intersecta com o ponto 1
   (deleção de arquivo físico), porque o único lugar que hoje olha
   `is_external` para decidir apagar arquivo é `documents_delete`
   (`documents.rs:739-774`), que trata documentos avulsos, não filhos de
   pasta.

## 7. Recomendações / mudanças de escopo sugeridas

1. **Adotar a abordagem da seção 3** (campo `webResearchFolderId` em
   `ChatFolder` + expansão dinâmica no RAG do chat) em vez de
   `notebook_document_visibility`. Reduz uma migration/mecanismo de estado
   inteiro e resolve dois dos edge cases (toggle idempotente, visibilidade
   automática) sem código extra.
2. Adicionar ao escopo, mesmo não estando explícito no Task Report: decidir
   o comportamento de exclusão da watched-folder de KB da IA (gap 1 da
   seção 6) antes do planejamento — evita um comportamento confuso
   ("removi a pasta, mas os arquivos continuam lá e a próxima gravação
   falha/recria estranho").
3. Usar hash determinístico da URL (calculado no frontend via
   `crypto.subtle.digest`) como nome de arquivo — resolve dedupe sem
   precisar de nova crate Rust nem de query extra ao SQLite.
4. Novo comando Tauri para criar a pasta (mkdir + insert) deve seguir o
   padrão de checagem de path de `save_chat_doc` (`lib.rs:250-271`), e
   gravar `is_external=0` + a nova coluna `origin='ai'`.
