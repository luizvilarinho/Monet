## Escopo
Três features no notebook Calendar: (1) dia da semana exibido no cabeçalho da nota diária (título persistido permanece DD/MM/YYYY); (2) atalho global Ctrl+K que alterna uma janela flutuante "keep" com a nota do dia atual e botão "Open Monet", replicando o padrão do Ctrl+M/assistant; (3) lembretes via chip Tiptap inline inserido por "@" + seletor de horário, com notificação nativa do Windows (`tauri-plugin-notification`), lembretes perdidos avisados no startup e estado "disparado" persistente.

## Decisões técnicas (prontas para o codeAgent)

### D1 — Estado "disparado" dos lembretes: tabela SQLite (não atributo no chip)
Tabela `reminder_state (id TEXT PRIMARY KEY, note_id TEXT NOT NULL, fired_at INTEGER NOT NULL)` — migration 11.
Motivo: gravar `fired` como atributo do chip exigiria o scheduler reescrever `note.content` no momento do disparo. Isso (a) colide com edição simultânea nas duas janelas (last-write-wins poderia ressuscitar `fired=false` e re-notificar), (b) dispara o `useEffect` de `setContent` do Editor e reseta o cursor de quem está digitando. Com a tabela, o disparo nunca toca no conteúdo da nota. Linhas órfãs (chip apagado depois) são inertes e desprezíveis em volume — sem rotina de limpeza.
O estado visual do chip vem de um `RemindersContext` (Set de ids disparados) carregado do banco e atualizado no disparo; o atributo do chip guarda apenas `id` e `time`.

### D2 — Scheduler roda no frontend da janela MAIN (única), não em Rust
A main fica viva em segundo plano (X esconde, nunca fecha — lib.rs ~1256-1264), então o JS dela continua rodando com a janela escondida. O parsing dos chips é trivial em TS (regex sobre o markdown da nota); em Rust seria preciso duplicar esse parsing e o acesso às notas. A janela keep NÃO roda scheduler (evita notificação dupla) — `main.tsx` monta `KeepPanel`, que não inclui o hook.
Formato: tick de 30s (`setInterval`) + recomputo quando as notas mudam. Cada tick recalcula "hoje" a partir de `new Date()` — isso resolve a virada do dia sem timer especial de meia-noite. Tick em vez de `setTimeout` exato tolera o throttling de timers do WebView2 em janela escondida (disparo pode atrasar segundos; atrasado continua sendo entregue e marcado).

### D3 — Formato do node Tiptap do chip
Node inline, `name: 'reminderChip'`, `group: 'inline'`, `inline: true`, `atom: true`, tag `<reminder-chip>`, attrs:
- `id` (`data-id`) — nanoid gerado na inserção; chave do estado disparado.
- `time` (`data-time`) — `"HH:MM"` 24h.
Serialização markdown (padrão EmbedBlock, mas inline — `state.write(...)` sem `closeBlock`): `<reminder-chip data-id="X" data-time="HH:MM"></reminder-chip>`. `fired` NÃO é atributo (ver D1). O texto do lembrete é o restante da linha (parágrafo) onde o chip está, com tags HTML removidas.
View React (`ReactNodeViewRenderer`): renderiza `⏰ HH:MM`; classe "fired" quando `id` ∈ `RemindersContext`. Fora do Calendar o chip renderiza igual porém nunca é agendado (o scheduler só varre a nota diária de hoje) — atende "colado fora do Calendar → inerte".

### D4 — Janela keep declarada em `tauri.conf.json` (padrão assistant)
Nova entrada `label: "keep"` (~420×520, `visible: false`, `alwaysOnTop`, `skipTaskbar: true`, `decorations: false`, `resizable: true`), adicionada ao array `windows` da capability default. ### D5 — Editor da keep usa o MESMO conjunto de extensões de nodes do Editor principal
Extrair a lista base de extensões de `Editor.tsx` para `src/components/Editor/extensions.ts` (StarterKit configurado, InlineCode, TaskList/TaskItem, Table*, Image, Placeholder, Markdown, EmbedBlock, ToggleBlock, LinkedNoteBlock, ReminderChip). Motivo crítico: se a keep abrir uma nota contendo `<embed-block>`/`<linked-note>`/`<toggle-block>` sem essas extensões registradas, o Tiptap descarta os nodes no parse e o autosave da keep **destruiria esse conteúdo**. A keep não inclui `CommandExtension` (decorações de comando /: desnecessárias lá e inofensivas como texto).

### D6 — Sincronização entre janelas (estratégia do Task Report, materializada)
- keep → recarrega ao ser exibida: no evento `keep-shown`, recomputa a data de hoje, busca a nota (`storage`) e faz `setContent`; cria a nota se não existir.
- main → recarrega ao ganhar foco: listener de foco; se a nota ativa no editor é nota diária do Calendar (`notebookId === 'calendar'` e `parseCalendarTitle(title)` válido), refaz o fetch dela do banco e atualiza o estado (o `useEffect` existente do Editor sincroniza o conteúdo). Acontece antes de o usuário digitar, então o reset de seleção do `setContent` é aceitável.
- `open-today-note` (botão "Open Monet"): main faz refresh das notas do banco e executa a lógica de `handleCalendarDayClick(new Date())` **sobre a lista recém-buscada** (não sobre o estado React possivelmente stale — a nota pode ter sido criada pela keep).
- Escrita: last-write-wins pelo upsert existente; sem merge.

## Riscos e pontos de atenção
1. **Throttling de timers do WebView2 em janela escondida**: o tick de 30s pode atrasar quando a main está oculta. Mitigado pelo modelo de varredura (disparo atrasado ainda é entregue e marcado); pior caso realista: notificação alguns segundos/minutos tarde. Não usar `setTimeout` único para o horário exato.
2. **Clique na notificação**: o plugin v2 não expõe callback de clique confiável no Windows desktop. Entregar o fallback previsto no Task Report (toast informa; navegação garantida é abrir o app). Não gastar esforço em deep-link de toast nesta task.
3. **Permissão/supressão de toasts no Windows**: além da permissão do plugin, Focus Assist/configurações do SO podem suprimir toasts silenciosamente. Comportamento: log, sem crash, sem marcar como disparado quando a permissão é negada.
4. **Colisão de saves entre janelas**: estratégia é reload-on-show (keep) / reload-on-focus (main) + last-write-wins. Se o usuário mantiver as duas janelas visíveis e editar alternadamente sem mudança de foco, a última gravação vence — aceito pelo Task Report ("sem sobrescrita silenciosa por cópia obsoleta" é garantido pelos reloads nos pontos de troca de contexto).
5. **Perda de conteúdo na keep por schema incompleto**: risco eliminado pela Etapa 4/D5 (mesmas extensões de nodes). Qualquer node novo futuro deve entrar em `buildBaseExtensions()` — ponto de atenção para o codereviewAgent.
6. **`setContent` no focus da main**: reseta seleção do editor; ocorre apenas no instante em que a janela ganha foco (antes de digitar). Não introduzir reload em outros momentos.
7. **Regex de chips**: serialização própria garante formato estável, mas a regex deve tolerar ordem de atributos e conteúdo colado de fora (chip malformado → ignorar silenciosamente).
8. **Migration 11 é aditiva** — sem risco para dados existentes; dev/prod continuam separados por identifier (nada hardcoded).

## Sinalizações ao Orquestrador (escopo)
- **"@" na janela keep**: o Task Report define o gatilho "na nota diária" sem citar a keep; como a keep edita exatamente a nota diária, o plano INCLUI o gatilho lá (Etapa 9d, custo baixo por reuso do TimePicker). Se o Coordenador preferir keep sem "@", basta suprimir o item 9d — nenhuma outra etapa depende dele.
- **Edge case "continuar digitando insere @ literal"**: o plano implementa cancelamento por Esc e clique fora (inserindo "@" literal); com o TimePicker aberto, a digitação vai para o campo de horário (input nativo `type="time"`). É uma leve variação da letra do edge case, mantendo o espírito (nunca travar a digitação, "@" literal sempre recuperável). Sinalizado para ciência; não considero mudança de escopo.
- **Clique na notificação navegar até a nota**: entregue como fallback (limitação do plugin no Windows), conforme já admitido pelo Task Report.
