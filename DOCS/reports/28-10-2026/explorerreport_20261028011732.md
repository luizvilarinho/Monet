# Explorer Report — Pasta de documentação .md no Library (leitura em modo árvore)

**Data:** 2026-10-28
**Task:** `DOCS/reports/28-10-2026/taskreport_20261028011506.md`

## Descrição do problema

O usuário quer apontar o Library para uma pasta do computador e ler os arquivos `.md` dela (com subpastas) numa experiência de leitura análoga à de livros: menu lateral com a árvore de documentos no lugar do sumário do EPUB, área de leitura confortável e navegação entre documentos sem sair do modo de leitura. O caso de uso é ler documentação de software guardada em Markdown local, **sem importar o conteúdo para as notas/base de conhecimento do Monet**.

## Veredito

**Viável. Dificuldade: Média.** Todos os blocos de construção já existem no projeto; nenhum impedimento de stack. O trabalho real é montar um componente novo de leitura e 2–3 comandos Rust pequenos, seguindo padrões que o codebase já estabeleceu.

## O que já existe (e serve diretamente)

- **Renderer de Markdown pronto e seguro:** `renderMarkdown()` em `src/lib/markdown.ts` (unified + remark-parse + **remark-gfm** + rehype-sanitize). Cobre tabelas e blocos de código (GFM) e já sanitiza o HTML. É usado hoje no chat, AiPanel e EmbedBlock — ou seja, é o caminho oficial de renderização.
- **Seletor de pasta pronto:** o comando `documents_pick_folder` (`src-tauri/src/documents.rs:35`, via `rfd::FileDialog::pick_folder`) já existe, está registrado e exposto ao frontend por `pickDocumentFolder()` em `src/lib/documents.ts:200`. **Reuso direto, zero código novo para o diálogo.**
- **Padrão de acesso ao disco com sandbox:** o projeto não usa os plugins `fs`/`dialog` do Tauri (não estão nem nas deps nem nas capabilities — `src-tauri/capabilities/default.json`). Todo filesystem passa por comandos Rust com validação de path (`canonicalize` + `starts_with` + rejeição de `..`), como em `books_read_file` (`src-tauri/src/books.rs:82`) e `read_chat_doc` (`src-tauri/src/lib.rs:299`). A feature nova deve seguir exatamente esse molde, com a diferença de que a raiz do sandbox é a pasta escolhida pelo usuário (guardada e revalidada), não uma pasta fixa do app.
- **Varredura recursiva de diretório:** `collect_files_recursive()` (`src-tauri/src/documents.rs:2104`) mostra o padrão de `read_dir` recursivo tolerante a erro — serve de referência para o comando que lista a árvore de `.md`.
- **Referência de UX:** `EpubReader` (`src/components/Reader/EpubReader.tsx`) tem o layout exato pedido: toolbar superior, painel lateral colapsável com abas ("Contents" = o `TocList` recursivo, que já é uma árvore com `depth`), área de leitura com controles de fonte/margem e estado de erro amigável para arquivo ausente. A árvore de documentos é essencialmente um `TocList` cujos `href` são paths de arquivos.

## O que NÃO dá para reaproveitar (e por quê)

- **O `EpubReader` em si não é reutilizável como componente.** Ele é profundamente acoplado ao epubjs: navegação por CFI, paginação por `locations`, iframe próprio, grifos com âncora CFI e persistência de posição na tabela `books`. Nada disso se aplica a um `.md` renderizado como HTML estático. A recomendação é **componente novo** (ex.: `src/components/Library/DocsReader.tsx`) que **imita o layout e copia os padrões** (CSS module com classes equivalentes, painel lateral colapsável, toolbar), mas renderiza o HTML do `renderMarkdown` num `<div>` normal. Isso também respeita a decisão de arquitetura já documentada no código: "os leitores são independentes" (comentário no EpubReader sobre duplicação deliberada de paleta).
- **O pipeline de pastas vigiadas da KB (`documents_*`) não deve ser reutilizado** além do `pick_folder`: ele indexa o conteúdo no banco para RAG, o que viola a constraint explícita da task ("não importar o conteúdo dos `.md`").
- **Painéis laterais de Chat/Notes do Reader** (`ReaderChatPanel`, `ReaderNotesPanel`) são acoplados ao tipo `Book` (id na tabela `books`, pasta de chat por livro, citações por página). Integrá-los à pasta de docs é possível mas é escopo extra — recomendo deixar fora da primeira entrega (ver recomendações).

## Impedimentos e pontos de atenção

1. **Imagens relativas nos `.md`:** o pipeline atual bloqueia/ignora o que não consegue carregar; um `![img](./assets/x.png)` não resolve dentro da webview. Solução padrão: pós-processar o HTML, trocar `src` relativo por data-URL vinda de um comando Rust que lê o arquivo de imagem (sempre validando que ficou dentro da raiz). Trabalho moderado; pode ser fase 2 sem bloquear a leitura de texto.
2. **Frontmatter YAML:** remark-parse não trata frontmatter; um `---\ntitle: ...\n---` vira linha horizontal + texto. Não há `remark-frontmatter` nas deps. Opções: strip manual simples no Rust/TS (sem nova dependência) ou adicionar a dependência. Detalhe pequeno, mas visível em docs de software, que costumam ter frontmatter.
3. **Encoding:** ler bytes no Rust e decodificar com `String::from_utf8_lossy` + strip de BOM cobre UTF-8 com/sem BOM e degrada com elegância em outros encodings. Não é impedimento.
4. **Mudanças no disco com a pasta aberta:** recomendo re-scan manual (botão refresh) e re-scan ao focar a janela. Watcher em tempo real exigiria a crate `notify` (não presente) e adiciona complexidade desproporcional para a v1.
5. **Links relativos entre `.md`:** interceptar o clique no HTML renderizado, resolver o `href` contra o diretório do documento atual e abrir o documento correspondente da árvore. Totalmente factível no frontend e é o que dá a sensação de "wiki local". Recomendo incluir, pois é barato e central ao caso de uso (documentação de software é interligada).
6. **Pasta removida/sem permissão:** o estado de erro do EpubReader ("file could not be found") é o modelo a copiar; a árvore deve mostrar erro e permitir re-selecionar a pasta.
7. **Sem impacto no modo browser:** `BrowserStorage.getBooks` já lança "not implemented" — o Library já é, na prática, desktop-only. A feature nova segue o mesmo regime, sem custo adicional à abstração `storage.ts`.

## Impactos

- **Backend:** módulo Rust novo pequeno (ex.: `docs_folder.rs`) com ~3 comandos: `docs_tree(root)` (árvore recursiva só de `.md`, com limite de profundidade/quantidade para pastas gigantes), `docs_read_file(root, path)` (bytes com sandbox sob a raiz) e opcionalmente `docs_read_asset(root, path)` para imagens. Mais registro no `invoke_handler` de `lib.rs`. Nenhuma permissão nova nas capabilities (comandos próprios não dependem de plugins).
- **Frontend:** seção nova no `Library.tsx` ("Documentation folder" com botão "Select folder", reusando `pickDocumentFolder`), persistência da pasta escolhida e do último documento em `localStorage` (mesmo padrão de `monet:reader-open-book`), e o componente novo de leitura. Nenhuma tabela nova no SQLite é estritamente necessária para a v1.
- **Zero risco de colisão** com livros existentes ou com a KB: a pasta de docs é um modo separado, sem escrita no banco.

## Recomendações

1. **Componente novo modelado no EpubReader, não reuso direto.** Copiar a estrutura visual (toolbar, painel lateral colapsável de 280px, área de leitura com controles de fonte) e renderizar via `renderMarkdown` existente. O "Contents" do EpubReader vira a árvore de pastas/documentos — o componente `TocList` recursivo é o modelo.
2. **Reusar `documents_pick_folder` como está.** O botão "Select folder" mora no header do Library, ao lado de "+ Import book", ou numa segunda aba/seção "Docs" dentro do Library (decisão de UI a detalhar no plano; ambas de baixo custo).
3. **Manter fora da v1:** integração com Chat/Notes/grifos (painéis acoplados a `Book`), watcher de filesystem e suporte a imagens relativas — listar como fase 2. Links relativos entre `.md`, em compensação, valem entrar na v1.
4. **Frontmatter:** strip manual do bloco `---...---` inicial antes do parse (evita dependência nova e resolve 99% dos casos de documentação).
5. **Sandbox por raiz escolhida:** validar todo path com `canonicalize` + prefixo da raiz salva, rejeitando `..` — mesmo padrão de `books.rs`, nunca confiar em path vindo do frontend.

## Conclusão

Feature viável com dificuldade **Média**: o renderer de Markdown, o seletor de pasta e o padrão de sandbox de FS já existem; o trabalho concentra-se em um componente de leitura novo (imitando o EpubReader) e ~3 comandos Rust pequenos. Sem impedimentos de stack ou de permissões. A principal decisão de escopo é deixar Chat/Notes/grifos, watcher e imagens relativas para uma fase 2.
