**C. Novo `src/components/Editor/BlockHandle.ts` — a extension do handle**

`BlockHandle.configure({ onRemoveResponse?: (id: string) => void })`, com um `Plugin` ProseMirror que guarda o próprio `DecorationSet` no estado do plugin.

**C.1 — chave estável (decisão fechada)**

- O `DecorationSet` fica no `state` do plugin. A cada transação: `set = prev.set.map(tr.mapping, tr.doc)`.
  - O `WidgetType.map` do ProseMirror (`node_modules/prosemirror-view/dist/index.js`) devolve `new Decoration(pos - offset, pos - offset, this)` — **o mesmo tipo**, portanto a mesma `spec.key`. E `WidgetType.eq` compara `this.spec.key && this.spec.key == other.spec.key` → **com a key igual, o DOM do widget é reaproveitado, não recriado**. É esse o mecanismo que elimina o churn de DOM por tecla.
- Depois do `map`, uma reconciliação: para cada bloco que deve ter handle e ainda não tem (posição sem widget), cria um widget com **chave nova** (`bh-<n>`, `n` de um contador monotônico do plugin, **nunca reutilizado**). Widgets cujo bloco não existe mais são removidos.
- Consequência: a chave é estável enquanto o bloco existir — digitar antes do bloco **desloca a posição mas não a chave**, e o DOM do handle (e o estado "armado") sobrevive.
- O widget é criado em `Decoration.widget(unit.pos + 1, (view, getPos) => makeHandle(view, getPos, options), { side: -1, ignoreSelection: true, stopEvent: () => true, key })`.
  - `getPos()` devolve a **posição viva** do widget (`prosemirror-view`: `self.parent.posBeforeChild(self)`) → o handle resolve a unidade no momento do clique/arrasto, sem precisar recriar o DOM.
  - `stopEvent: () => true` é o mesmo padrão de hoje (`CommandExtension.ts:721` e `:745`).
- **Blocos que recebem handle nesta etapa**: os blocos de topo do documento, **exceto** os contêineres de lista (`bulletList`, `orderedList`, `taskList`) — que ganham handle **por item** na Etapa 2.
- **Bloco sem conteúdo** (`hr`, `image` — nós folha): não há posição "dentro" do nó. O widget vai em `unit.pos` com `side: -1` (antes do nó) e ganha uma variante de CSS com `float: left; margin-left: -22px` (ver C.4).

**C.2 — clique vs. arrasto, e o handle virando lixeira (decisão fechada)**

Reusa o limiar de 4px que já existe: `DRAG_THRESHOLD = 4` (`CommandExtension.ts:382`) e o teste `Math.sqrt(dx * dx + dy * dy) < DRAG_THRESHOLD` (`CommandExtension.ts:415` e `CommandExtension.ts:604`).

| Momento | O que acontece |
|---|---|
| `mousedown` no handle | `preventDefault()` + `stopPropagation()`; guarda `startX/startY`; `isDragging = false`; `wasArmed = armed` |
| `mousemove` | se `!isDragging` e a distância ≥ 4px → `isDragging = true` (e desarma) |
| `mouseup`, **com** arrasto | faz o drop (ou cancela) e desarma — mesmo caminho de `CommandExtension.ts:446-458` |
| `mouseup`, **sem** arrasto, handle **desarmado** | **arma**: o elemento ganha a classe `is-armed` → o glifo vira lixeira |
| `mouseup`, **sem** arrasto, handle **armado** | **apaga** a unidade de bloco |

- **Estado "armado" no DOM** (classe CSS), não no plugin: mais simples e não invalida a key do widget (o DOM não é recriado).
- **Desarmar**: ao armar, registra um listener **único** de `mousedown` no `document` que desarma se o alvo estiver fora do handle; o listener se remove ao disparar. Clicar no handle de novo não desarma (o alvo está dentro).
- **"Vira lixeira no mesmo lugar"**: o elemento do handle é o mesmo; só o glifo troca. Implementação sugerida: o handle é um `span.monetBlockHandle` com `contentEditable = 'false'` contendo um glifo `::before` — `content: '⋮⋮'` no estado normal e `content: '🗑'` (ou um SVG inline estático) em `.is-armed`. O `::before` do CSS resolve o "mesmo lugar" sem trocar de elemento e sem mexer no layout.
- `Esc` cancela o arrasto (listener em captura no `document`, como `CommandExtension.ts:462-466`).

| Risco | Mitigação |
