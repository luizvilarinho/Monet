## Decisões de desenho

1. **O roteador entra como parâmetro novo de `rag_retrieve`, não como comando novo.** A assinatura fica `rag_retrieve(scope, message, history, rewriteModel, filters, router)`, e `router: null` mantém o fluxo atual intacto. Por que parâmetro:
   - uma só chamada IPC e um só embedding da consulta, reaproveitado na busca restrita e na da KB;
   - roteamento, resolução e orçamento ficam em Rust, onde há testes unitários (o front não tem runner de testes);
   - os outros chamadores não passam o parâmetro e não mudam;
   - `RagResponse.route` é aditivo (null para eles).

   Um comando novo duplicaria a resolução de escopo, a chave, a data local e a busca.
2. **Divisão de trabalho.**
   - O **front** monta os *dados* da árvore, porque subjects, tipos, arquivadas e a regra das tasks estão no storage do front. Também lê as notas escolhidas no storage, na hora (conteúdo atual, mesma limpeza do `get_note`).
   - O **Rust** monta o *texto* da árvore com as referências, chama o roteador, resolve as referências, decide entre nota inteira e trechos pelo índice e faz as buscas.
3. **Turno do roteador:**
   ```
   mode === 'notes' && turnAgent.id === GENERAL_AGENT_ID && ragScope?.notebookId
   ```
   - O roteador roda só quando o `ragGate` devolve `search`, ou `reuse` sem trechos.
   - O `skip` e o `reuse` com trechos ficam como hoje.
   - O roteamento só acontece sem `filters`.
4. **Árvore:**
   - só as notas do caderno ativo, agrupadas por subject, com tipo, data e arquivada;
   - referências curtas `n1…nK` em vez de UUIDs;
   - teto de 120 notas, ficando as editadas mais recentemente, com a contagem das omitidas;
   - a nota aberta e incluída fica marcada.

   Detalhes na seção "Árvore de títulos".
5. **Corpos de task fora da árvore.** São as notas do subject `tasks-<nb>`, escondido na coluna do caderno. *Ponto para o Coordenador.*
6. **Nota aberta.**
   - Incluída no contexto: fica na árvore, marcada, e nunca é lida de novo. A resolução descarta a referência a ela; se ela era a única nota de `notes`, a rota vira `none`. *Ponto para o Coordenador.*
   - Retirada pelo chip: sai da árvore.
7. **Orçamento de leitura:** 8.000 caracteres por nota e até 3 notas.
   - Uma nota entra inteira quando a soma dos chunks dela no índice cabe em 8.000.
   - Acima disso, entram os 2 melhores chunks dela (~8.000), achados por busca híbrida restrita à nota, sem rerank. *Ponto para o Coordenador.*
8. **Falhas.**
   - Se o roteador falha (timeout, HTTP, JSON inválido, rota desconhecida, `query` vazia fora do `none`), a rota vira `kb` com a consulta de fallback e `rewriteFailed = true`: é a busca de hoje, nunca a pula.
   - Se a montagem da árvore falha no front, a chamada vai sem `router`, ou seja, o fluxo atual.
9. **Timeout do roteador: 5 s** (a reescrita usa 4 s), porque a entrada é maior. `ROUTE_MAX_TOKENS` é 350.
10. **Calendar:** é o mesmo painel. Valem as mesmas regras, com títulos de data e lista plana (ver seção "Chat do Calendar").

## Contrato IPC

TS → Rust (`router`, em camelCase):

```ts
export interface RouterNote {
  id: string
  title: string
  subjectId: string | null
  type: string | null      // nome do tipo da nota
  date: string | null      // YYYY-MM-DD: data da nota, título do Calendar ou dia de criação
  archived: string | null  // YYYY-MM-DD da arquivação
  updatedAt: number        // ms
}
export interface RouterInput {
  notebookName: string | null
  subjects: Array<{ id: string; name: string }> // na ordem de sortOrder
  notes: RouterNote[]
  openNoteId: string | null // nota aberta E incluída no contexto
  hasAttachment: boolean
}
```

Rust → TS (`RagResponse.route`):
- é null fora do turno do roteador;
- também é null quando não havia nada a rotear: mensagem vazia, ou escopo vazio sem árvore.

```ts
export type RagRouteKind = 'none' | 'notes' | 'kb' | 'both'
export interface RagRoutedNote {
  ref: string                      // "n3"
  noteId: string
  title: string
  rowids: number[]                 // chunks da nota inteira, ou os dos trechos
  excerpts: RagCandidate[] | null  // não-null = nota longa: usar só estes trechos
}
export interface RagRouteTrace {
  route: RagRouteKind              // rota final (depois da resolução e do fallback)
  modelRoute: RagRouteKind | null  // a que o modelo devolveu; null = roteador falhou
  refs: string[]                   // referências devolvidas, normalizadas
  ignoredRefs: string[]
  notes: RagRoutedNote[]
  treeNotes: number
  treeOmitted: number
  treeChars: number
}
```

Nos turnos roteados, os campos de `RagResponse` têm este sentido:
- `selected`, `candidates` e `nothingRelevant` referem-se só à busca da KB; ficam vazios ou `false` sem ela;
- `rewrittenQuery`, `keywords` e `dateRange` vêm do roteador;
- `rewriteFailed` indica que o roteador falhou;
- `timings.rewriteMs` é o tempo do roteador, e `timings.searchMs` soma a busca restrita e a da KB.

Em Rust:
- `RouterInput`, `RouterSubject` e `RouterNote` são `Deserialize` + `Clone` com `rename_all = "camelCase"`, com `#[serde(rename = "type")] note_type` e `#[serde(default)]` nos opcionais;
- `RouteTrace` e `RoutedNote` são `Serialize` com `rename_all = "camelCase"`, com `#[serde(rename = "ref")] note_ref`;
- todos esses tipos e campos são `pub`, porque o `rag_eval` os usa.

## Árvore de títulos (`build_tree`, Rust)

`pub fn build_tree(input: &RouterInput) -> RouterTree`, com:
- `RouterTree { text: String, entries: Vec<TreeEntry>, omitted: usize }`;
- `TreeEntry { note_ref, note_id, title, open: bool }`.

Regras:
1. **Sem notas:** `text` vazio, sem entradas e `omitted` 0.
2. **Seleção:**
   - ordenar por `updated_at` decrescente, depois `id` crescente, e ficar com as 120 primeiras (`ROUTER_TREE_MAX_NOTES`);
   - se `open_note_id` está na entrada mas não entre as 120, ela substitui a 120ª;
   - `omitted` = total − mantidas.
3. **Agrupamento:**
   - os grupos seguem a ordem de `subjects`; dentro de cada grupo, as notas vão por `updated_at` decrescente;
   - notas sem subject, ou com subject fora da lista, vão para `## No subject`, por último;
   - os cabeçalhos `## <nome>` só aparecem se existir ao menos um grupo de subject; sem nenhum, a lista é plana, sem cabeçalhos;
   - grupo vazio não aparece, e subject com nome vazio vira `Untitled subject`.
4. **Referências:** `n1…nK`, na ordem em que as linhas aparecem.
5. **Linha da nota:**
   ```
   - n<k>: <title>[ · <type>][ · <date>][ · archived <archived>][ · open in the editor (already in the context)]
   ```
   As partes vazias saem.
6. **Texto:**
   - em título, nome de subject e nome de caderno, sequências de espaço (inclusive quebras de linha) viram um espaço, as pontas são aparadas e o texto é cortado em 100 caracteres (`ROUTER_TREE_TITLE_CHARS`);
   - título vazio vira `Untitled`.
7. **Linha de cabeçalho:**
   - começa com `Notebook "<nome>"` (sem nome: `Notebook`);
   - depois vem `: <K> note(s)`, com K = notas listadas;
   - depois `, grouped by subject`, quando há cabeçalhos;
   - depois ` (the <O> least recently edited notes are not listed)`, quando O > 0;
   - termina com `:`.

Exemplo (fictício):

```
Notebook "Estudos": 5 notes, grouped by subject:
## Arquitetura
- n1: Capítulo 3 — estilos · Summary · 2026-11-09
- n2: Reunião com o time · 2026-11-02 · open in the editor (already in the context)
## Leituras
- n3: Capítulo 3 — estilos · Summary · 2026-10-12 · archived 2026-10-30
## No subject
- n4: Ideias soltas · 2026-09-02
- n5: 05/09/2026 · 2026-09-05
```

Tamanho: de 40 a 70 caracteres por linha. Com 120 notas, a árvore tem de 6 a 8 mil caracteres (~2 mil tokens).

## Prompt, entrada e schema do roteador

### `route_prompt(current_date)` (texto exato; no `format!`, escapar `{` `}` como no `rewrite_prompt`)

O bloco abaixo usa a data 2026-10-18 como exemplo. Os bullets de `query`, `keywords` e `dateRange` repetem o texto da reescrita (`rag.rs:899-903`), com uma frase a mais no fim do `query`. O `rewrite_prompt` não muda: a duplicação é aceita, para não tocar no prompt dos outros chats.

```
Current date: 2026-10-18 (Sunday).

You route the latest message in a chat about one of the user's notebooks. Before the answer, the app can read notes of this notebook and search the user's knowledge base (their own notes, meeting transcripts, documents and saved web pages). You decide what the answer needs and write the search request.

Return JSON with:
- "query": one self-contained search query of at most 300 characters, in the language of the user's message. Resolve pronouns and references to earlier turns ("it", "that version", "and in version X?") using the conversation. Keep every specific entity: names, projects, notebooks, documents, versions, codes, dates. Drop greetings, filler and instructions about the answer itself ("search", "explain step by step", "make a list"), and ignore pasted text that does not help to find the information. Always fill it, whatever the route.
- "keywords": up to 8 exact terms likely to appear verbatim in the relevant text: proper names, project, product, notebook or file names, versions, codes, endpoints, table names, acronyms and distinctive technical terms. One term per item, 1 to 3 words, spelled as the user wrote them. Never generic words such as "meeting", "rule", "document", "how", "reunião", "regra".
- "dateRange": only when the message refers to a specific day or period ("on 14/10", "yesterday", "last week", "in August"): {"from": "YYYY-MM-DD", "to": "YYYY-MM-DD"}, inclusive. Numeric dates are day/month. A date without a year means its most recent occurrence not after the current date. Otherwise null.
- "route": what the answer needs.
  - "none": nothing beyond the conversation, the note open in the editor or an attached file: greetings, thanks and small talk, questions about this chat or your previous answers, and requests to rewrite, translate, shorten, format or continue text that is already there.
  - "notes": specific notes of the notebook tree that the message names or points to (by title, subject, type or date, such as the daily note of a given day), and those notes are enough.
  - "kb": information from the user's sources, with no note of the tree named or pointed to.
  - "both": notes of the tree named or pointed to, plus information from other sources.
  When unsure, do not choose "none": skipping a needed search gives a wrong answer, while an unneeded search only costs a second. When unsure which note is meant, choose "both" with your best guesses, or "kb".
- "notes": for "notes" and "both", the references of the chosen notes as listed in the tree (such as "n3"), never titles; at most 3, most relevant first. Use subject, type and date to tell similar titles apart. Never choose the note marked as open in the editor: its text is already in the context (when the answer is in it, the route is "none"). A follow-up about a note discussed earlier points to that note again. For "none" and "kb", an empty list.

When the notebook tree is not available, choose only "none" or "kb".
```

### `route_input(history, message, tree_text, has_attachment)`

Blocos separados por linha em branco:
1. **Árvore:** `Notebook tree:\n<tree_text>`. Com `tree_text` vazio, `Notebook tree: not available.`
2. **Histórico** (só quando há): `Conversation so far:\n<linhas>`. As linhas vêm de `history_lines(history)`: os mesmos 6 turnos × 1.500 caracteres, `User:`/`Assistant:`, da reescrita.
3. **Mensagem:** `Latest user message:\n<mensagem cortada em 2000>`. Com anexo, o cabeçalho é `Latest user message (an image or file is attached to it and is already in the context):`.

### Schema `rag_route` (strict)

```json
{
  "type": "object",
  "properties": {
    "query": { "type": "string" },
    "keywords": { "type": "array", "items": { "type": "string" } },
    "dateRange": { "anyOf": [
      { "type": "object", "properties": { "from": { "type": "string" }, "to": { "type": "string" } },
        "required": ["from", "to"], "additionalProperties": false },
      { "type": "null" } ] },
    "route": { "type": "string", "enum": ["none", "notes", "kb", "both"] },
    "notes": { "type": "array", "items": { "type": "string" } }
  },
  "required": ["query", "keywords", "dateRange", "route", "notes"],
  "additionalProperties": false
}
```

A ordem das propriedades é proposital: o modelo escreve a consulta (resolvendo as referências) antes de decidir a rota. Os parâmetros do request são os da reescrita: `temperature` 0, `max_tokens` `ROUTE_MAX_TOKENS` (350), modelo configurado (`RAG_REWRITE_MODEL_KEY`, padrão `openai/gpt-4.1-mini`) e headers iguais.

### `parse_route(content) -> Option<Route>`

`Route { kind: RouteKind, refs: Vec<String>, rewrite: Option<Rewrite> }`, com:
- `RouteKind { None, Notes, Kb, Both }`;
- `as_str()` devolve `"none"`, `"notes"`, `"kb"` ou `"both"`;
- `parse(&str)` aceita o texto aparado e em minúsculas.

Regras:
1. O objeto JSON sai por `parse_json_object` (o mesmo da reescrita, que aceita JSON envolto em markdown).
2. Se `route` falta ou é desconhecida, devolve `None` (falha).
3. `rewrite` = `rewrite_from_value(&v)`, com as mesmas validações da reescrita. Fica `None` com `query` vazia, e isso só é falha quando `kind != None`.
4. Normalização de cada item de `notes`:
   - aparar a string e tirar não alfanuméricos do início;
   - pegar o prefixo alfanumérico e passar para minúsculas;
   - só dígitos vira `n<dígitos>`;
   - vazio é descartado.

   Exemplos: `"[n12]"` → `n12`, `"n12: Título"` → `n12`, `"N3"` → `n3`, `"7"` → `n7`.
5. Deduplicar mantendo a ordem e cortar em `ROUTER_MAX_REFS` (10).

## Resolução da rota (`resolve_route`, Rust)

`pub fn resolve_route(route: &Route, tree: &RouterTree) -> ResolvedRoute`, com `ResolvedRoute { kind, notes: Vec<TreeEntry>, ignored: Vec<String> }`.

- **`none` e `kb`:** sem notas; todas as referências vão para `ignored`.
- **`notes` e `both`:** as referências são percorridas em ordem.
  - Vão para `ignored`: referência desconhecida, nota aberta (`open`; anotar que a nota aberta foi pedida), nota repetida e o que passar de 3 válidas (`ROUTER_MAX_NOTES`).
  - As outras viram notas.
- **Nenhuma nota válida:**
  - `notes` → `none` se a nota aberta foi pedida; senão, `kb`;
  - `both` → `kb`.

## Orçamento de leitura e busca restrita

**Rust** (`retrieve_routed`), para cada nota resolvida, com `doc = note_doc_id(note_id)`:
- **Nota no escopo** (`doc` em `doc_ids`):
  - `note_chunks(conn, doc)` = `SELECT rowid, length(content) FROM chunks_meta WHERE document_id = ?1 ORDER BY chunk_index`;
  - soma ≤ `ROUTER_NOTE_FULL_CHARS` (8.000): nota inteira, com `rowids` = todos os chunks e `excerpts` nulo;
  - soma maior: nota longa. `note_excerpts(conn, doc, embedding, keywords)` roda `hybrid_search(conn, &[doc], embedding, keywords, HYBRID_K_EACH, ROUTER_EXCERPT_CHUNKS)` (`pool` 2, que prefere trechos não vizinhos), ordena por `chunk_index` e devolve os candidatos sem rerank. `rowids` são os deles e `excerpts` é `Some`. Se vier vazio, a nota vai como inteira, com `rowids` cortados em 2.
- **Nota fora do escopo ou sem chunks** (índice atrasado ou nota vazia): nota inteira, com `rowids` vazios.
- **Por que a soma é conservadora:** o overlap de 400 caracteres entre chunks faz a soma passar um pouco do tamanho real. Uma nota pouco abaixo de 8.000 pode sair por trechos; o front corta em 8.000 de qualquer forma.

**Front** (`readRoutedNotes`):
- **Inteira:** corpo atual do storage, com a limpeza do `get_note` (embeds, OCR e `cleanNoteContentForAi` com os títulos visíveis, sem expandir nota linkada), cortado em `ROUTED_NOTE_MAX_CHARS` (8.000) + `" [truncated]"`.
- **Por trechos:** `excerpts.map((c) => c.content).join('\n…\n')`. São o texto do índice, já limpo na indexação.
- **TODOS:** com a nota inteira ou por trechos, entram as linhas das tasks do mesmo helper do `get_note` (até 40), depois de uma linha em branco.

**Total:**
- em `notes`: até 3 × 8.000 caracteres + tasks;

### `buildRoutedContext` (`rag.ts`)

```ts
export interface RoutedNoteRead {
  documentId: string   // note:<id>
  title: string
  date?: string
  folder?: string      // "Notes — <caderno>"
  archived?: string
  rowids: number[]
  excerpts: boolean
  text: string
}
export function buildRoutedContext(
  notes: RoutedNoteRead[], kbChunks: RagCandidate[], kbNothingRelevant: boolean, hasOtherContext: boolean,
): { content: string; sources: RagSource[] }
```

**Bloco de cada nota:**
- a nota é citada com `citeSource(sources, { documentId, title, kind: 'note', date, folder, rowids })`;
- formato: `[n] [<title> · note · <date> · archived <d> · <folder>]`, mais ` (excerpts)` nas notas por trechos, `\n<text>`;
- as partes vazias saem, como em `notesByDateText`.

**Texto, na ordem:**
1. Introdução das notas:
   ```
   Notes from this notebook picked for the user's message: each one in full, or only its passages most relevant to the message when the note is long (marked "excerpts"). Cite them inline as [n] right after the claim they support. Use only what they say when you describe these notes.
   ```
   - sem `kbChunks` e com `kbNothingRelevant`, acrescentar ` The search in the rest of the knowledge base found nothing relevant to this message.`;
   - nesse caso, com `hasOtherContext`, acrescentar também `OTHER_CONTEXT_NOTE`.
2. `\n\n` + os blocos das notas, separados por `\n---\n`.
3. Com `kbChunks`:
   - o texto `\n\nKnowledge base excerpts (the numbering continues). Cite them inline as [n] right after the claim they support. Use only what they say; if neither the notes above nor these excerpts answer the question, say you did not find it in the user's documents.`;
   - mais `OTHER_CONTEXT_NOTE`, com `hasOtherContext`;

Como `kbChunks` nunca vem de uma nota escolhida (o Rust tira esses docs do escopo da KB), notas e trechos dividem a numeração sem colisão.

## Casos de borda → onde são tratados

| Caso | Tratamento |
| --- | --- |
| Nota aberta incluída | `loadRouterInput` passa `openNoteId`. `build_tree` mantém e marca a nota, mesmo acima do teto. O prompt proíbe escolhê-la. `resolve_route` a descarta; `notes` só com ela vira `none` |
| Nota aberta retirada pelo chip | `loadRouterInput` tira `excludedNoteId` quando ela não é a `openNoteId`. O escopo da KB já a exclui (`excludeNoteId`) |
| Títulos duplicados | Referências `nK`. A linha traz subject (cabeçalho), tipo, data e arquivada. O prompt pede para desempatar por eles |
| Referência inexistente | `resolve_route` → `ignoredRefs`. `notes` sem nenhuma válida → `kb`; `both` sem válidas → `kb` |
| Nota apagada, movida ou esvaziada depois da árvore | `readRoutedNotes` relê no storage e pula a nota que não existe, que mudou de caderno ou que ficou sem texto (corpo + tasks). A tool continua de rede de segurança |
| Caderno sem notas | `build_tree` vazio → `Notebook tree: not available.` O prompt manda escolher só `none`/`kb`, e `resolve_route` leva `notes`/`both` a `kb` |
| Caderno com muitas notas | Teto de 120, ficando as editadas mais recentemente, com a contagem das omitidas no cabeçalho |
| Imagem ou arquivo anexado | `hasAttachment`, a partir dos argumentos do `send`. O painel do caderno não tem anexo hoje; o flag fica pronto |
| Follow-up sobre nota lida | O histórico vai ao roteador, e o prompt diz que o follow-up aponta para a mesma nota. O "continue" reaproveita os `rowids` das fontes (como hoje) |
| Calendar | Mesmas regras (seção acima) |
| Pedido misto | Rota `both`: notas + KB, com numeração contínua |
| Caderno com a IA desligada | `loadRouterInput` devolve entrada vazia (sem árvore e sem nome). `readRoutedNotes` confere de novo e não lê nada |
| Nota de outro caderno | A árvore só tem `WHERE notebook_id = $1`. `readRoutedNotes` exige `note.notebookId === notebookId`. Os chunks só vêm de docs do escopo |
| Falha do roteador | Rota `kb` com a consulta de fallback; `router failed` na linha e no inspetor |
| Falha da árvore no front | `router: null` → fluxo atual |
| Embedding falha em `notes` (sem KB) | A nota longa vai inteira, cortada, com `rowids` cortados em 2. Em `kb`/`both`, o erro sobe como hoje (o turno segue sem RAG) |
| Mensagem vazia, ou escopo vazio sem árvore | Sem chamada de LLM; `route` null (igual ao `!searchable` de hoje) |
| Agentes especializados, outros chats, tool, `/docs` e paleta | Não passam `router`: fluxo atual |

## Riscos

- **Latência:** a árvore acrescenta até ~2 mil tokens de entrada ao roteador. A etapa 11 mede a diferença para a reescrita; se o ganho do `none` não compensar, o teto de 120 é o ajuste mais barato.

- **Índice defasado (~10 s de debounce):**
  - a decisão entre nota inteira e trechos, os trechos e o "continue" usam o índice;
  - a leitura inteira usa o storage (conteúdo atual);
  - nota recém-criada e ainda sem chunks vai inteira.
- **Soma dos chunks:** superestima o tamanho (por causa do overlap), então uma nota perto de 8 mil caracteres pode sair por trechos.
- **Contexto em `both`:** 3 notas (~24 mil) + 8 trechos (~32 mil) é mais que hoje (~32 mil), dentro do que os modelos do chat aceitam.
- **Modelo configurado diferente do padrão:** pode não respeitar o `json_schema`/`enum`. O `parse_route` valida, e a falha vira busca.
