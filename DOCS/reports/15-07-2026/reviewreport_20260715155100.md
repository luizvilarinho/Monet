## Verificação dos pontos pedidos

### 1. Os 4 efeitos de restauração/recuperação em `ReaderNotesPanel.tsx`
Rastreei manualmente as sequências de render/effect para os cenários de carregamento assíncrono e de delete externo. Conclusão: **a guarda `array.length === 0` funciona corretamente e não há race condition.**

- A guarda evita o falso positivo: enquanto `notebooks`/`notes` ainda não carregaram (`[]`), os Efeitos A/B fazem `return` sem marcar as refs `*RestoreDoneRef` como concluídas, e os Efeitos C/D também sofrem `return` antes de qualquer `unlink`/`setSelectedX(null)`. Isso é reavaliado a cada nova referência de array recebida via prop, então quando os dados chegam de fato, os efeitos rodam de novo com a informação completa.
- Não há race entre os 4 efeitos porque cada `useEffect` roda com o snapshot de estado/props do **próprio** render — uma chamada de `setState` feita pelo Efeito A dentro de um mesmo commit não é visível para os Efeitos B/C/D executados na mesma passada (React só propaga o novo valor no próximo render). Concretamente:
  - Efeito C só age quando `selectedNotebookId` já é truthy — e `selectedNotebookId` só se torna truthy depois que o Efeito A validou a existência do notebook (ou por seleção manual do usuário, que também só oferece notebooks já presentes na lista renderizada). Logo, o "efeito de recuperação" nunca pode disparar antes do notebook ter sido de fato validado — ele não tem contra quê disparar (guarda `if (!selectedNotebookId) return`).
  - O mesmo raciocínio vale para o par Efeito B / Efeito D em relação a `selectedNoteId`.
- Verifiquei também que `Reader`/`ReaderNotesPanel` são efetivamente desmontados/remontados a cada troca de livro (`Library.tsx` não passa `key` para `<Reader>`, mas a troca de livro sempre passa por um estado intermediário `openBook = null` antes de abrir outro livro — `openReader`/`closeReader` são os únicos setters de `openBook`), então as refs `notebookRestoreDoneRef`/`noteRestoreDoneRef` nunca "vazam" de um livro para outro.
- Padrão de criar nota e selecioná-la imediatamente (`handleCreateNote`: `await onCreateNote(...)` seguido de `setSelectedNoteId(note.id)`) é idêntico ao já usado em `App.tsx` (`handleCreateNote` da tela de Notebook, linha ~901-910) — não é um risco novo introduzido por esta feature.

### 2. Integração `copyCitationAbout` → nota vinculada (`Reader.tsx`)
Código conferido (`Reader.tsx:1433-1463`):
```
async function appendQuoteDirectlyToNote(note: Note, text: string, page: number) {
  const { content: block } = buildQuoteBlock(text, book.title, page)
  const newContent = appendQuoteToContent(note.content, block)
  await onSaveNote({ ...note, content: newContent, updatedAt: Date.now() })
  const quote: BookQuote = { id: crypto.randomUUID(), bookId: book.id, page, text, targetNoteId: note.id, createdAt: Date.now() }
  await handleSavedQuote(quote)
}

function copyCitationAbout(text: string, page: number) {
  const link = getReaderNoteLink(book.id)
  const note = link?.noteId ? notesRef.current.find((n) => n.id === link.noteId) : undefined
  if (note) {
    appendQuoteDirectlyToNote(note, text, page).catch((err) => {
      console.error('failed to append quote to linked note', err)
      setQuoteContext({ text, page })
      setQuoteModalOpen(true)
    })
    return
  }
  setQuoteContext({ text, page })
  setQuoteModalOpen(true)
}
```
- `buildQuoteBlock`/`appendQuoteToContent` são exatamente as funções exportadas de `QuoteToNoteModal.tsx` (confirmado por leitura) e a lógica replica `appendToExistingNote` do modal (linhas 185-223) com paridade de comportamento (mesmo shape de `BookQuote`, mesmo `updatedAt`, mesmo uso de `onSaveNote`).
- `handleSavedQuote` (reaproveitada tal como já existia, linha 1569-1583) grava o `BookQuote` via `storage.saveQuote` **dentro de um try/catch que engole o erro** — ou seja, se o append no conteúdo da nota (`onSaveNote`) tiver sucesso, o fallback para o modal nunca é acionado por falha no registro do `BookQuote` (que é best-effort), evitando o risco de duplicar a citação ao reabrir o modal.
- O fallback só é acionado se `onSaveNote` (a escrita real do conteúdo) rejeitar — nesse caso nada foi persistido ainda, então abrir o modal para o usuário tentar de novo não duplica nada. Comportamento correto.
- Comportamento antigo (sem vínculo, ou nota vinculada não existe mais em `notesRef.current`) permanece bit-a-bit idêntico ao código anterior (`setQuoteContext` + `setQuoteModalOpen(true)`).
- `handleCopyCitation` e o botão "Copy citation" do popover de grifo não foram tocados — continuam chamando `copyCitationAbout` normalmente.

Nenhum bug encontrado neste ponto.
