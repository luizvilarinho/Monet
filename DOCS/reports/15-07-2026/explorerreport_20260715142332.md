# Explorer Report — Aba "Notes" na coluna lateral do Reader

## Problema
Adicionar uma segunda aba "Notes" ao lado da aba "Chat" já existente na coluna lateral do Reader (`src/components/Reader/Reader.tsx`), permitindo escolher Notebook → Nota (ou criar uma nova), editar com `Editor.tsx` completo (sem slash commands), persistir no mesmo storage do Notebook, e lembrar por livro a última nota aberta (mesmo padrão do vínculo livro→pasta de chat).

**Viável.** Todas as peças de storage e de persistência de vínculo já existem e podem ser reaproveitadas sem alterações de schema. O único ponto que exige mudança de código reaproveitável (não solução nova) é a supressão condicional dos slash commands no `Editor.tsx`.

## Nível de dificuldade: **Média**
Não há bloqueio técnico. A complexidade está em orquestrar estado (aba ativa, seleção Notebook→Nota, recuperação de vínculo apagado) em `Reader.tsx`/novo componente, não em criar mecanismos novos de storage.

---

## 1. Estrutura de tabs no Reader

- `Reader.tsx:417-419` — hoje existe só `chatOpen` (boolean), persistido em `CHAT_OPEN_KEY = 'monet:reader-chat-open'` (linha 69, efeito de persistência em 551-557).
- O toggle é um único botão "Chat" na toolbar (`Reader.tsx:1683-1691`), que faz `setChatOpen(v => !v)`.
- `ReaderChatPanel` é renderizado **sempre montado** fora de qualquer ternário (`Reader.tsx:2133-2147`), com o comentário explícito confirmando a regra ("fechar o toggle só esconde via CSS — desmontar o painel cancelaria o useChat e um stream ativo").
- A ocultação é só CSS: `ReaderChatPanel.tsx:336` aplica `styles.panelHidden` quando `open` é `false`; `ReaderChatPanel.module.css:16-18` — `.panelHidden { display: none; }`.

**Ponto de menor atrito**: trocar o único booleano `chatOpen` por um estado de aba ativa em `Reader.tsx`, ex. `sideTab: 'chat' | 'notes' | null` (ou manter um boolean `sideOpen` + `activeSideTab: 'chat'|'notes'`). Um novo componente irmão `ReaderNotesPanel` seguiria o EXATO mesmo padrão do `ReaderChatPanel`: sempre montado ao lado dele (`Reader.tsx` logo após a linha 2147), com uma prop `open`/`visible` própria computada como `sideOpen && activeSideTab === 'notes'`, escondido via uma classe `panelHidden` análoga no seu próprio CSS module. O botão único "Chat" na toolbar vira um par de botões/tabs ("Chat" / "Notes") que setam `activeSideTab` e abrem a coluna. Nenhuma mudança é necessária na lógica interna do `ReaderChatPanel` (ele já está pronto para esse padrão).

## 2. Suprimir slash commands no Editor.tsx

- Autocomplete é controlado por `updateAutocomplete` (`Editor.tsx:357-413`), chamado a cada transação do Tiptap via `editor.on('transaction', handler)` (`Editor.tsx:415-426`), e consome `getCurrentCommandLine`/`getCommandSuggestions` (importados de `CommandExtension.ts`/`commandParser.ts`) para popular o estado `autocomplete` que alimenta o componente `<CommandAutocomplete>` (`Editor.tsx:788-794`).
- `CommandExtension.configure({...})` é adicionado incondicionalmente na lista de extensões do `useEditor` (`Editor.tsx:159-164`). Essa extensão registra um `Plugin` ProseMirror (`commandPluginKey`, ver `CommandExtension.ts:748-822`) responsável pelas decorações visuais de comando executado/erro e pelos widgets de drag/botões de inserir resposta — nada disso é necessário na aba Notes.
- O handler de `Enter` em `editorProps.handleKeyDown` (`Editor.tsx:275-329`) também depende de `getCurrentCommandLine`/`commandPluginKey` para decidir se intercepta o Enter e executa um comando.

**Forma mais simples, sem duplicar o componente**: nova prop opcional `disableSlashCommands?: boolean`.
- Pular a extensão: `...(disableSlashCommands ? [] : [CommandExtension.configure(...)])` na lista de `extensions`.
- Guard no topo de `updateAutocomplete`: `if (disableSlashCommands) return` (ou nem registrar o listener no `useEffect` de `Editor.tsx:415-426` quando a prop estiver ativa) — evita o dropdown aparecer.
- Guard equivalente no bloco do `Enter` (`Editor.tsx:275-329`): pular o bloco inteiro quando `disableSlashCommands`, deixando o Enter cair no comportamento padrão do Tiptap (quebra de linha/parágrafo).
- **Confirmado como seguro omitir `getCurrentCommandLine`/`commandPluginKey` mesmo sem a extensão registrada**: `commandPluginKey.getState(state)` retorna `undefined` quando o plugin não está no schema, e todo uso já trata isso com `?.` (`Editor.tsx:286` `pluginState?.marks.get(...)`); `tr.setMeta(commandPluginKey, ...)` é um no-op silencioso se o plugin não estiver registrado. Ou seja, mesmo sem o guard extra no handleKeyDown, nada quebra — o guard é só para evitar trabalho/efeitos colaterais desnecessários (ex. o widget "[" de NotePicker, que é independente de slash commands, continua funcionando normalmente).
- `responses`/`onRemoveResponse`/`relatedContent` já são **opcionais** em `EditorProps` (`Editor.tsx:49-51`) e todos os usos internos já toleram ausência: `responsesRef.current = responses ?? []` (linha 142), `contextValue = { responses: responses ?? [] }` (linha 150-153, só alimenta o context provider, inofensivo), `onRemoveResponseRef.current = onRemoveResponse` (chamado só dentro do `CommandExtension.configure`, que nem seria criado com `disableSlashCommands`), `{relatedContent}` (linha 786, renderiza `undefined` = nada). **Confirmado: pode-se omitir os três sem quebrar nada.**

## 3. Seleção Notebook → Nota + criação inline (funções já existentes, reaproveitáveis)

Storage (`src/storage/index.ts:14-28`, implementado em `tauri.ts`/`browser.ts`):
- `storage.getNotebooks(): Promise<Notebook[]>`
- `storage.getNotes(): Promise<Note[]>` — retorna TODAS as notas; filtragem por notebook é client-side via `note.notebookId` (é o padrão já usado em `App.tsx:1177-1180`: `notes.filter(n => n.notebookId === id)`).
- `storage.saveNote(note: Note)` — upsert único, usado tanto para criar quanto atualizar (`tauri.ts:455-470`, `INSERT ... ON CONFLICT DO UPDATE`).
- `storage.getNote(id)`, `storage.deleteNote(id)`.

Não é necessário criar nada novo em storage. Camada de hook: `src/hooks/useNotes.ts:57-74` — `create(notebookId, subjectId?)` já monta um `Note` em branco (`title:'', content:''`) e chama `save` (linha 27-44, que persiste via `storage.saveNote`). Esse é o primitivo ideal para "criar nota nova" com nota vazia.

**No contexto do Reader especificamente**, `Reader.tsx` já recebe como props prontas (vindas de `App.tsx` → `Library.tsx:14-19` → `Reader.tsx:39-47`):
- `notebooks: Notebook[]`, `notes: Note[]` (arrays completos, já carregados)
- `onCreateNotebook(name): Promise<Notebook>`
- `onCreateNote(notebookId, title, content): Promise<Note>` (alias de `handleCreateNoteFromChat`, `App.tsx:1035-1053` — internamente chama `createNote(notebookId)` da `useNotes` e depois `saveNote` com título/conteúdo preenchidos)
- `onSaveNote(note): Promise<void>` (alias direto de `useNotes().save`)

Ou seja: **nenhuma nova prop de dados precisa subir de App.tsx até Reader.tsx** — tudo que a aba Notes precisa já chega em `Reader.tsx` hoje (é o mesmo grupo de props que `QuoteToNoteModal` já consome, `Reader.tsx:2150-2165`). Para "criar nota vazia" dentro do notebook selecionado, basta chamar `onCreateNote(notebookId, '', '')`.

**Padrão de seleção em 2 níveis já existente para reaproveitar**: não há um componente "compacto" pronto — `NotebookList.tsx` (lista de notebooks, coluna esquerda do modo Notebook) e `Sidebar.tsx` (lista de notas de um notebook, coluna do meio) são ambos componentes pesados (drag-and-drop via `@dnd-kit`, renomear inline, subjects, larguras redimensionáveis 140-400px) — não são bons candidatos a reuso literal dentro da coluna estreita do Reader (260-560px). O padrão de DADOS a reaproveitar é simples: `notebooks` para o 1º seletor, e `notes.filter(n => n.notebookId === selectedNotebookId)` para o 2º (mesma linha usada em `App.tsx:1177-1180`). `NotePicker.tsx` (`src/components/Editor/NotePicker.tsx`) é uma lista flat com busca textual, sem agrupar por notebook — serve de referência de estilo de dropdown, mas não resolve o 2-níveis pedido; provavelmente vale montar dois `<select>`/dropdowns simples dedicados à aba Notes, não reaproveitar `NotePicker` diretamente.

## 4. Persistência do vínculo livro→nota (padrão exato a replicar)

Implementado inteiramente em `src/hooks/useChat.ts`:
- Chave: `const READER_BOOK_FOLDER_LINK_KEY = 'monet:reader-book-folder-link'` (linha 144).
- Formato: um único objeto JSON `Record<bookId, folderId>` (tipo `ReaderBookFolderLinks`), serializado inteiro a cada escrita.
- `loadReaderBookFolderLinks()` (linha 491-507): lê a chave, faz `JSON.parse`, valida shape (objeto simples, valores string), fallback `{}` em qualquer erro.
- `saveReaderBookFolderLinks(links)` (linha 509-515): `localStorage.setItem(KEY, JSON.stringify(links))`, erro só logado.
- `getReaderChatFolderId(bookId)` (linha 517-520, **exportada**): getter público.
- `linkBookToReaderFolder(bookId, folderId)` (linha 522-526, **não exportada**, uso interno do hook): setter.
- `unlinkBookFromReaderFolder(bookId)` (linha 528-533, **exportada**): remove a entrada; usada em cascata na exclusão do livro (`Library.tsx:134-136`).

**Para o vínculo livro→nota**, o mesmo padrão com chave própria (ex. `monet:reader-book-note-link`) funcionaria assim: valor por livro seria `{ notebookId, noteId }` em vez de só uma string (já que a aba Notes precisa lembrar os dois níveis, não só a nota). Local natural para esse código: um novo arquivo pequeno (ex. `src/lib/readerNoteLink.ts`) ou direto dentro do novo `ReaderNotesPanel.tsx` — diferente do vínculo de chat, este não depende de nenhum hook de estado compartilhado (`useChat`), pode ser um módulo de localStorage puro e independente.

**Diferença importante de comportamento a decidir no planning**: na cascata de exclusão de livro, o chat **deleta a pasta inteira** (`deleteChatFolderById`, `Library.tsx:135`) porque a pasta é criada especificamente pelo próprio `ensureReaderBookFolder` só para aquele livro. Notebook/Nota da aba Notes são conteúdo do usuário pré-existente (não criados exclusivamente para o livro) — cascatear delete ao apagar o livro apagaria uma nota do usuário sem relação necessária só com aquele livro. O equivalente correto aqui é só `unlink` (remover a entrada do localStorage), nunca apagar a nota/notebook em si.

## 5. Riscos / edge cases

**a) Notebook/nota apagados enquanto vinculados a um livro** — mecanismo do chat a espelhar (sem a parte de "recriar", que não se aplica aqui):
- Recuperação "mid-session" (nota apagada em outra janela enquanto a aba está aberta): `ReaderChatPanel.tsx:247-263` — efeito que observa `activeId` (viraria `null` se a conversa ativa for removida) e reage.
- Recuperação "pasta sumiu entre renders" (id vinculado não existe mais na lista local): `ReaderChatPanel.tsx:237-242` — efeito que observa `folders`/`bookFolderId` e, se o id vinculado não estiver mais na lista, reage.
- Para a aba Notes, o equivalente SEM auto-recriação seria: um efeito que observa `notebooks`/`notes` (props já existentes em `Reader.tsx`) e, se `notebookId`/`noteId` lidos do link não existirem mais nessas listas, limpa a seleção local (`setSelectedNotebookId(null)`/`setSelectedNoteId(null)`) e opcionalmente já limpa o link órfão — sem tentar criar nada novo, coerente com o requisito "voltar graciosamente para nenhuma nota selecionada".

**b) Nenhum notebook existe ainda** — `NotebookList.tsx:466-469` já tem o padrão de "empty state" (`<li className={styles.empty}>no notebooks</li>`) a espelhar visualmente (texto orientando a criar notebook fora do Reader).

**c) Troca de livro com edição em andamento / autosave** — **achado relevante**: **não existe debounce de autosave para conteúdo de nota em nenhum lugar do código atual.** `Editor.tsx:333-336` chama `onChange(md)` a CADA transação do Tiptap (cada keystroke); em `App.tsx:883-886`, `updateActive` chama `saveNote(...)` diretamente, sem debounce; `useNotes.ts:27-44` (`save`) chama `storage.saveNote(note)` imediatamente; e o `INSERT ... ON CONFLICT DO UPDATE` em `tauri.ts:455-470` é um upsert idempotente simples. Ou seja, cada tecla digitada já dispara uma escrita real no banco — não há nada "pendente" para perder ao trocar de livro/desmontar o Reader (diferente do padrão de `SAVE_DEBOUNCE_MS` que o próprio `Reader.tsx:53,916-943` usa só para `lastPage`/`zoom` do livro, não para conteúdo de nota). Isso simplifica o requisito: reaproveitar `onChange`/`onSaveNote` tal como já funciona em qualquer outro lugar do app já resolve o edge case "salvar antes de trocar de contexto" — não é necessário nenhum flush explícito no unmount.

## Recomendações de escopo
1. Nenhuma mudança de schema ou de storage é necessária — confirmado.
2. O planner deve decidir o nome/estado exato da aba ativa em `Reader.tsx` (single source of truth) e garantir que o toggle único "Chat" na toolbar vire dois estados (aberto/fechado + aba ativa), sem alterar o contrato de `ReaderChatPanel` (que já está pronto para conviver com uma segunda aba).
3. A prop `disableSlashCommands` no `Editor` deve gatear tanto a inclusão da extensão quanto os dois pontos de leitura de `getCurrentCommandLine` (`updateAutocomplete` e o handler de Enter) — os três já foram confirmados como seguros de omitir/pular sem quebrar o restante do componente.
4. Para o vínculo livro→nota, seguir literalmente o padrão de `useChat.ts:490-533` (objeto JSON único em localStorage, load/save/get/unlink), mas com decisão explícita de **não** cascatear delete da nota/notebook ao apagar o livro (só `unlink`), diferente do que ocorre com a pasta de chat.
5. Vale o planner decidir se o componente de seleção Notebook→Nota na aba Notes é dois `<select>` simples (mais compatível com a largura estreita, 260-560px) em vez de tentar adaptar `NotebookList`/`Sidebar`/`NotePicker` — nenhum dos três resolve o caso em 2 níveis sem retrabalho significativo.
