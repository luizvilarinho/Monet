## Resumo do problema
Os 4 requisitos são todos incrementais sobre um Reader já funcional (renderização de página única por vez via `<canvas>` + text layer do pdf.js, sistema de grifos com persistência SQLite, coluna lateral retrátil, popover de ações). ## Requisito 1 — Busca textual no ebook
**Dificuldade: Alta**

O Reader renderiza **uma página por vez** (efeito em Reader.tsx:493-753, comentário explícito "apenas a página atual"): só existe canvas + text layer (`TextLayer` do pdfjs, importado em `src/lib/pdf.ts:12`) para `pageNum`. Não há texto/rects de outras páginas montados no DOM.

Já existe extração de texto por página via `getPageText` (Reader.tsx:468-491), usada hoje só como contexto do chat, com cache em `pageTextCacheRef` (`Map<number, string|null>`, `null` = página sem texto extraível/PDF escaneado). Isso resolve a parte de **indexação/contagem**: para buscar no documento inteiro é preciso rodar `getPageText` em todas as páginas (chamando `doc.getPage(n)` + `getTextContent()`), o que é assíncrono, não bloqueia o render, mas tem custo proporcional ao nº de páginas — para livros grandes (centenas de páginas) o "contagem total" só fica completo depois de varrer o documento todo. Isso é aceitável se feito em background com indicador de progresso, mas é trabalho novo (não existe hoje uma extração "de todas as páginas de uma vez").

A parte mais delicada é o **mapeamento de ocorrência → retângulo visual para destaque**, porque:
- Verifiquei que `pdfjs-dist` (v5.6.205) inclui um `PDFFindController` pronto (`node_modules/pdfjs-dist/web/pdf_viewer.mjs`), mas ele é acoplado ao `PDFViewer` completo da referência do pdf.js (multi-página contínuo, `EventBus`, `linkService` etc.) — adotá-lo exigiria substituir boa parte da renderização custom do Reader (que tem lógica elaborada e comentada de seleção manual, ver Reader.tsx:206-256 e 600-714). **Não recomendo reaproveitar o `PDFFindController`** — o custo de integração supera o ganho.
- A abordagem recomendada é replicar o padrão já usado para grifos: computar rects via `Range.getClientRects()` (igual a `handleTextMouseUp`, Reader.tsx:960-1012), mas isso só é possível para a página **atualmente renderizada** (a text layer de outras páginas não existe no DOM). Ou seja: a navegação next/previous precisa (a) usar o índice de texto para achar a próxima página com ocorrência, (b) chamar `goToPage` para essa página, (c) só depois que a text layer dessa página terminar de renderizar, percorrer os `<span>` da text layer para localizar a ocorrência e montar o `Range`/rects — um novo efeito, disparado por `[pageNum, scale, searchQuery]`, análogo ao já existente mas para "match do termo buscado" em vez de "grifo salvo".
- Edge cases do task report (case/acentos, termo vazio, 0 ocorrências, PDF sem text layer) são majoritariamente tratáveis reaproveitando o que `getPageText` já resolve (retorna `null` para páginas sem texto).

**Recomendação de escopo**: implementar como descrito acima (índice de texto documento-inteiro para contagem/navegação + highlight via DOM Range só na página corrente). Vale considerar, se o Planner achar o escopo muito grande, uma redução aceitável: manter a extração de texto **preguiçosa/incremental** (ex.: extrair sob demanda ao navegar, cachear, e permitir "Next" pular para a próxima página ainda não indexada como parte do fluxo) em vez de indexar o livro inteiro de uma vez ao abrir a busca — evita travar a UI em PDFs muito grandes. Isso é uma decisão de UX/performance a validar com o Coordenador se o Planner topar esse trade-off.

## Requisito 2 — Filtro por cor na coluna de highlights
**Dificuldade: Baixa**

`HIGHLIGHT_COLORS` já é uma constante fixa de 4 cores (Reader.tsx:50). A lista de grifos na aba "Highlights" (Reader.tsx:1457-1544) já itera `orderedHighlights` (memo derivado de `highlights`, Reader.tsx:910-916) e cada item já expõe `h.color` (usado no swatch de cada card, linha 1476). Basta:
- Um novo estado local `colorFilter: string | null`.
- Filtrar `orderedHighlights` por `h.color === colorFilter` quando setado.
- Renderizar os 4 swatches no fim da lista (mesmo componente visual do `highlightSwatch` já usado na toolbar de seleção, Reader.module.css:281-298), com clique alternando `colorFilter` (clicar de novo desmarca → volta a mostrar todos, conforme comportamento default pedido).

Não exige mudança de storage nem de tipos. Sem persistência entre sessões é aceitável (não foi pedido).

## Requisito 3 — Trocar cor de highlight existente
**Dificuldade: Baixa**

Confirmei em `src/storage/tauri.ts:592-613` que `saveHighlight` **já é um upsert**:
```sql
INSERT INTO book_highlights (...) VALUES (...)
ON CONFLICT(id) DO UPDATE SET page=excluded.page, text=excluded.text, color=excluded.color, rects_json=excluded.rects_json
```
E `persistHighlight()` em Reader.tsx:919-934 já sincroniza estado local + `storage.saveHighlight`. Ou seja: **não é preciso criar nenhuma função nova de update** — trocar a cor é literalmente `persistHighlight({ ...highlight, color: novaCor })`, mantendo o mesmo `id`, `rects`, `text`, `createdAt`.

Sobre o edge case "highlight com nota vinculada": verifiquei `BookHighlight` (`src/types/index.ts:66-74`) — não tem nenhum campo de referência a nota. Notas/citações (`BookQuote`, linhas 76-83) são registros **totalmente independentes** (ligados por `bookId`/`page`/`text`, não por `highlightId`), criados via fluxo separado ("Copy citation" → `QuoteToNoteModal`). Trocar a cor de um highlight não pode, portanto, afetar nenhuma nota — o "risco" citado no task report não existe no modelo de dados atual, não precisa de tratamento especial.

Basta adicionar, no popover já existente (`removalPopover`, Reader.tsx:1630-1689), uma nova linha de swatches (reaproveitando o mesmo array `HIGHLIGHT_COLORS` e estilo `.highlightSwatch`) chamando esse novo handler.

## Requisito 4 — Botões flutuantes de navegação de página
**Dificuldade: Baixa**

Estrutura confirmada (Reader.module.css:97-118):
```css
.pageArea { flex: 1; min-height: 0; overflow: auto; display: flex; justify-content: center; align-items: flex-start; padding: 24px; }
.pageWrap { position: relative; margin: auto; ... }
```
`.pageArea` é o container com scroll (quando o zoom excede a viewport); `.pageWrap` é a página em si. O padrão CSS para "botão sempre visível sobre um container com scroll, sem ocupar altura" é: dar `position: relative` a `.pageArea` e posicionar os botões como filhos diretos dela (irmãos de `.pageWrap`) com `position: absolute; bottom: Npx; left/right: Npx`. Como o containing block de um elemento `position:absolute` é a **padding box** do ancestral posicionado (que não se move ao rolar o conteúdo interno), os botões ficam fixos visualmente na parte inferior da área de leitura mesmo com scroll — exatamente o comportamento pedido ("sempre visíveis", "não ocupam altura extra").

Reaproveita diretamente `goToPage(pageNum - 1)` / `goToPage(pageNum + 1)` e a mesma condição `disabled` dos botões do topo (Reader.tsx:1280-1313). Único cuidado: os botões devem ficar montados fora do ternário `loading ? <p>... : <div className={pageWrap}>...` (ou replicados/condicionados a `!loading && doc`) para não desaparecerem durante o carregamento, e usar `z-index` alto o suficiente para não ficar atrás do canvas (as camadas existentes já usam z-index 2-4; sugiro 5).

## Riscos e observações gerais
- Nenhum teste automatizado cobre o Reader (`**/*.test.*` não retornou nada) — validação será manual, como já é padrão no projeto pré-lançamento.
- O requisito 1 é o único que introduz um efeito novo dependente de `pageNum`/`scale` (paralelo ao já existente), o que aumenta a superfície de bugs de sincronização (ex.: troca rápida de página durante uma busca ativa). Recomendo que o Planner trate isso como uma tarefa própria, separada dos requisitos 2-4 (que podem ser feitos em paralelo/sequência simples por serem isolados e de baixo risco).
- Requisitos 2, 3 e 4 não tocam schema de banco nem a interface `Storage` — são mudanças localizadas em `Reader.tsx` + `Reader.module.css`.

## Recomendações objetivas
1. Sequenciar a implementação: fazer 2, 3 e 4 primeiro (baixo risco, entregas rápidas e isoladas), deixar 1 (busca) para uma etapa própria de planejamento/execução dedicada, dado o novo efeito de render e o custo de indexação documento-inteiro.
2. Para a busca, **não** adotar `PDFFindController`/`pdf_viewer.mjs` do pdf.js — acoplamento incompatível com a renderização custom do Reader. Reaproveitar `getPageText` (extração) + técnica de `Range.getClientRects()` já usada nos grifos (destaque visual, só na página corrente).
3. Validar com o Coordenador se a indexação de busca deve ser "documento inteiro ao abrir a busca" (mais simples de raciocinar, mas custo inicial maior em PDFs grandes) ou "incremental/sob demanda" (mais complexo, melhor performance). Isso muda o esforço do requisito 1.
4. Requisito 3: nenhuma migração de banco necessária — confirmar no plano que a implementação usa `persistHighlight` existente, sem criar função de update paralela.
