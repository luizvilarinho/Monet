## `src/components/Reader/Reader.tsx`

### Correção
Os 4 requisitos e os 2 ajustes pontuais foram implementados corretamente e batem com o plano aprovado.

**Verificação específica pedida pelo Orquestrador — sincronização entre o novo efeito de busca e o efeito de render de página**: confirmado que a ordem de effects (hook order = ordem de declaração no componente) faz o effect "leve" (`useEffect(() => computeSearchMatchRects(), [searchOpen, normalizedQuery, pageNum, computeSearchMatchRects])`, linha 1234) rodar de forma síncrona ANTES da parte assíncrona do effect de render de página (`[doc, pageNum, scale]`, linha 645) atingir a limpeza/re-render da text layer (que só ocorre após múltiplos `await`). Isso significa que, ao trocar de página com busca ativa, o effect leve recalcula rects momentaneamente contra o DOM da página ANTIGA (ainda não trocado) — mas como o canvas/textLayer antigos também ainda não foram trocados nesse instante, o resultado é visualmente consistente (tudo "antigo" junto) até `computeSearchMatchRectsRef.current()` (chamado dentro do effect de render, após o `textLayer.render()` da página NOVA) sobrescrever com o valor correto. O effect de scroll (`[currentMatch, pageMatchRects, pageNum]`, linha 1144) também depende de `pageMatchRects`, então ele naturalmente re-executa quando o valor correto chega, evitando scroll para um elemento inexistente. Comportamento correto na prática, mecanismo intencional e documentado nos comentários do código — sem bug.

**Verificação específica — `goToMatch`/`jumpBackPage`**: confirmado que a versão final (linhas 1017-1025) seta `jumpBackPage` apenas quando ainda `null` (`setJumpBackPage((prev) => (prev === null ? pageNum : prev))`) e só quando `m.page !== pageNum`, chamando `goToPage` diretamente (não `jumpToPage`, que sempre sobrescreveria). O `useEffect` existente (linha 1007-1009) continua responsável por limpar o marcador quando `pageNum` volta a igualar `jumpBackPage`, inclusive quando isso acontece via ciclo de busca (não só pelo botão "Back"). Comportamento bate exatamente com o relatado pelo Coordenador como correto na 2ª rodada de ajuste. `jumpToPage` (usada por highlights/sumário) não foi alterada e mantém o comportamento de sempre sobrescrever — correto para esse uso.

**Edge cases de busca verificados**: termo vazio (`normalizedQuery` vazio → `matchesByPage` retorna `[]`, contagem exibida em branco), 0 ocorrências com índice pronto ("No results"), PDF sem text layer/scaneado (`getPageText` cacheia `null`, `matchesByPage` pula a página via `if (!text) continue`, `findAllOccurrenceRanges` retorna `[]` se não há spans — sem crash), troca rápida de página durante busca ativa (reaproveita o padrão existente de `cancelled`/cancelamento de `renderTaskRef`/`textLayerTaskRef`, já usado antes desta task — `computeSearchMatchRectsRef.current()` só roda depois dos guards `if (cancelled) return`, então nunca escreve resultado de uma renderização obsoleta). Todos corretos.

**"Nota vinculada ao trocar cor de highlight"**: confirmado em `src/types/index.ts` que `BookHighlight` (linhas 66-74) não referencia `Note`/`BookQuote` — `BookQuote` é uma entidade independente (linhas 76-83). Trocar a cor via `handleChangeHighlightColor`/`persistHighlight` não tem como afetar nenhuma nota. Correto.

### Simplicidade
- `matchesByPage` (linhas 1110-1126) recalcula a lista completa de páginas `1..searchIndexProgress` a cada incremento de `searchIndexProgress` durante a indexação em background (um incremento por página). Isso é O(P²) no número de páginas enquanto a indexação está em andamento e uma query já foi digitada, em vez de acumular incrementalmente o resultado da nova página. Para ebooks típicos (100-300 páginas) o custo é imperceptível; para documentos grandes (500+ páginas) é um trabalho redundante evitável com um acumulador incremental. `[nit]`

### Efeitos colaterais
Nenhum efeito colateral fora do escopo identificado. O `useEffect` que reseta `selection`/`removalCandidate` ao trocar página/zoom (linha 1043) ganhou `setPageMatchRects([])` — apropriado, evita flash de retângulos da página anterior. O `useEffect` que reseta highlights/seleção ao trocar de livro (linha ~524) ganhou os resets de `colorFilter`/`searchOpen`/`searchQuery`/`activeMatchIndex` — condiz com o requisito de não persistir busca/filtro entre livros.

### Padrões
- Reaproveitamento correto de `persistHighlight` (upsert já existente) para troca de cor, `goToPage`/`jumpToPage` para navegação, e a mesma técnica de `Range.getClientRects()` → retângulos normalizados já usada pelo `highlightLayer`. Nenhuma duplicação desnecessária de lógica de storage.
- Ordem alfabética dos novos ícones (`CaretDown, CaretLeft, CaretRight, CaretUp, ..., MagnifyingGlass, ..., X`) mantida corretamente.
- Os novos swatches de cor (filtro no painel de highlights, linha ~1900-1912; troca de cor no popover, linha ~2065-2077) usam `aria-label` estático e idêntico para todas as cores ("Filter highlights by color" / "Change highlight color"), sem diferenciar qual cor cada botão representa. O padrão já existente na toolbar de seleção (linha 1997, `aria-label={\`Highlight with ${c}\`}`) ao menos varia por cor (embora usando o hex cru). Leitores de tela não conseguem distinguir os botões nas duas fileiras novas. Essa redação já estava assim no plano aprovado (Etapas 1 e 2), não é desvio do codeAgent. `[nit]`
