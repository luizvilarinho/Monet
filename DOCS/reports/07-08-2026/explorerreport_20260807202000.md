# Spike — viabilidade do `@likecoin/epubjs` para o leitor de EPUB

**Data:** 07-08-2026
**Ativado por:** Coordenador (direto)
**Objetivo:** responder com evidência as quatro incógnitas levantadas em `explorerreport_20260807180845.md` §5.4, antes de escrever o `EpubReader.tsx`.

## Veredicto: **VIÁVEL — pode seguir**

As quatro incógnitas foram respondidas e nenhuma bloqueia. Há **uma mudança obrigatória** (CSP) e **uma decisão de escopo** que ficou mais cara do que se imaginava (rótulo de capítulo).

---

## Como foi medido

Página isolada servida pelo Vite em porta separada (5199), com a CSP aplicada por `<meta http-equiv>` em duas variantes — a de produção verbatim e a proposta com `blob:`. Executada em **Chrome headless real** (mesmo motor do WebView2), com os resultados enviados por HTTP para um coletor local.

Duas armadilhas de método que custaram iterações e ficam registradas:

1. **`--virtual-time-budget` não serve para isto.** Com ele, `rendition.display()` nunca resolvia — nas *duas* variantes de CSP. Se só a variante estrita tivesse sido executada, a conclusão teria sido "a CSP atual bloqueia o render", que é falsa. Medições finais foram feitas em tempo real.
2. **Violação de CSP dentro de um iframe dispara no documento do iframe, não no pai.** Com o listener só no pai, as duas variantes reportavam "zero violações" — falso negativo. O teste decisivo foi injetar um `<img src="blob:...">` dentro do iframe, com listener local.

**Arquivo de teste:** `Fausto - Série Ouro` (EPUB 3.0, 0,64 MB, sem DRM). Escolhido por ser caso limite: **o livro inteiro é um único XHTML de 1,06 MB** (spine de 2 itens), que é exatamente o formato onde a arquitetura do epubjs (um iframe por spine item + paginação por CSS columns) deveria sofrer.

## Resultados

| Verificação | Resultado |
| --- | --- |
| Parse (unzip + OPF) | **17 ms** |
| Metadados | `dc:title` e `dc:creator` corretos |
| TOC | **64 entradas** de 1º nível |
| **Primeiro render** (XHTML de 1,06 MB) | **470–634 ms** |

| `locations.save()` | **28,9 KB** para cachear no banco |

| Sandbox do iframe | `allow-same-origin`, **sem `allow-scripts`** |
| Script embutido executa? | **NÃO** (confirmado empiricamente, não só pelo atributo) |

### Surpresa: performance não é problema

A previsão do relatório anterior era que o arquivo de 1 MB num único spine item seria patológico para o epubjs. **Foi refutada:** 470 ms no primeiro render e paginação fluida. Se ele aguenta este arquivo, aguenta EPUBs normais com folga. A preocupação estava superdimensionada.

### Grifos: funcionam, mas a marca vive no documento PAI

`rendition.annotations.highlight(cfi, ...)` desenha via `marks-pane` um `<svg>` **sobrepondo** o iframe, no documento pai — não dentro do iframe. O clique no `<rect>` dispara o callback registrado. Detalhe de implementação importante para quem for escrever o `EpubReader`: procurar a marca dentro do `contentDocument` não acha nada.

## Mudança obrigatória: CSP

**Confirmado com evidência dos dois lados.** As imagens de dentro do EPUB são servidas como `blob:`:

- **CSP atual** → `[iframe] img-src bloqueou blob`; o probe `<img>` **falhou**.
- **CSP com `blob:`** → probe carregou (600×923), **zero violações**.

Precisão importante: sob a CSP atual o EPUB **abre e o texto é legível** — paginação, grifos e locations continuam funcionando. O que quebra são **as imagens**. Isso é mais brando do que o relatório anterior afirmava ("renderiza quebrado ou não renderiza").

CSP proposta (a de produção + `blob:`):

```
default-src 'self' blob!; script-src 'self' 'wasm-unsafe-eval'; style-src 'self' 'unsafe-inline' blob!;
img-src 'self' data: https: blob!; font-src 'self' data: blob!; frame-src 'self' blob!;
connect-src 'self' ipc: http://ipc.localhost https://openrouter.ai https://api.tavily.com
```
*(trocar `blob!` por `blob:` — escapado aqui só para não quebrar a tabela acima)*

**`script-src` deliberadamente NÃO recebe `blob:`** — é o que impede script de EPUB de terceiro de executar.

**Não exercitado:** as 4 fontes OTF do arquivo não foram usadas na página testada (`@font-face: 0 regras` na capa), então `font-src` não foi provado. Pelo mesmo mecanismo das imagens, `blob:` em `font-src` deve ser incluído — mas isso é inferência, não medição.

## Segurança: o alerta do `@xmldom/xmldom` é inerte aqui

`npm audit` acusa **high** em `@likecoin/epubjs` → `@xmldom/xmldom` ("XML injection via unsafe CDATA serialization"), com `fixAvailable: false` — o advisory cobre `<=0.8.12` e o pacote fixa `^0.7.5`, que trava abaixo de 0.8. Não sai sem o upstream mudar o pin.

**Mas o código vulnerável não roda no nosso runtime.** Verificado no fonte:

- `src/utils/core.js:619` — usa xmldom só se `typeof DOMParser === "undefined"` (Node) ou `forceXMLDom === true`.
- `src/section.js:99-103` — usa o serializer do xmldom só se `typeof XMLSerializer === "undefined"` ou em IE (`Trident`).

No WebView2/Chromium ambos os nativos existem, então o caminho nativo é o usado. O xmldom fica no bundle como peso morto.

Consequências reais, que não são risco mas são custo:
1. `npm audit` vai continuar acusando high — ruído permanente em CI.
2. Peso extra no bundle sem uso.
3. **Nunca passar `forceXMLDom: true`** em lugar nenhum — é o único jeito de acordar esse código.

### Achado colateral, sem relação com EPUB

`pdfjs-dist` tem advisory **high** em aberto: *"Arbitrary JavaScript execution upon opening a malicious PDF"*, faixa `>=5.6.83 <6.2.108` — e o projeto está em `^5.6.205`, dentro da faixa. Isso afeta o leitor de PDF que **já está em produção**. Merece task própria; a correção é subir para `>=6.2.108` (major).

## O que ficou mais caro do que o previsto

**Resolver o capítulo para a citação.** O arquivo de teste tem spine de 2 itens mas **64 entradas de TOC** — ou seja, os capítulos são âncoras de fragmento *dentro* do XHTML gigante, não itens de spine. Descobrir "em que capítulo estou" exige mapear a posição atual para a última âncora de TOC anterior, e não o trivial "qual spine item está aberto".

Isso não inviabiliza a opção "capítulo + %" para o rótulo da citação, mas encarece. Se o custo incomodar, "só porcentagem" continua barato e não depende de TOC.

## Recomendação

1. **Seguir com `@likecoin/epubjs`.** Funciona em tudo que importa, no pior arquivo disponível. `foliate-js` continua plano B, mas não há razão para pagar sua documentação fraca sem um motivo concreto.
2. **Ajustar a CSP** junto com a primeira alteração de EPUB — é pré-requisito para imagens.
3. **Atenção à resolução de versão — tem uma armadilha.** O `dist-tags.latest` do pacote aponta para **`0.3.94-beta.0`** (uma prerelease), mas `npm install @likecoin/epubjs` resolveu e gravou **`^0.3.93`** (estável), e é a **0.3.93 que está instalada e foi medida neste spike**. O npm evitou a prerelease sozinho.

   O risco não é a versão atual, é a instabilidade da resolução: com o `latest` apontando para uma prerelease, uma instalação limpa em outra máquina ou em CI pode não resolver igual. **Recomendo pin exato (`0.3.93`, sem `^`)** para garantir que o que roda em produção é o que foi medido aqui.
4. **Decidir o rótulo da citação** sabendo agora que "capítulo" custa mais do que parecia.
5. Abrir task separada para o advisory do `pdfjs-dist`.

## Artefatos

O spike foi descartado após a medição (`epub-spike-*.html`, `src/spike/`, `public/spike/`). A dependência `@likecoin/epubjs` foi mantida instalada, já que é a próxima a ser usada — mas até o `EpubReader` existir ela fica sem consumidor no código.
