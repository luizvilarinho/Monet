### Getters em vez de arrays no service — correto, e por um motivo mais forte do que o registrado

`BookQuoteDeps.getNotes`/`getNotebooks` são funções, não arrays. Isso não é preciosismo: no código antigo, `handleSavedQuote` lia `notesRef.current` **depois** de `await storage.saveQuote(quote)`. Um array capturado na entrada de `appendQuoteToNote` traria a lista de *antes* do await — e é exatamente nesse intervalo que o `onSaveNote` acabou de atualizar a nota no pai. O toast poderia mostrar o título antigo. A escolha do `codeAgent` preserva o comportamento; um array teria mudado silenciosamente. Confirmo a avaliação do Orquestrador.

Já em `copyCitationAbout` a leitura é síncrona (`p.notes`), espelhando o `notesRef.current.find(...)` síncrono do original. As duas semânticas diferentes estão corretas cada uma no seu lugar.

### Ordem dos effects — a avaliação do `codeAgent` procede; verifiquei

`useHighlights` é chamado no topo do componente, então o effect de carga de grifos passa a ser registrado **antes** do effect de carga do documento (que antes vinha primeiro). Fui atrás do risco real, porque o repo tem histórico de corrida de lock no `monet.db` no cold start:

- `TauriStorage.db()` (`src/storage/tauri.ts:266-278`) memoiza o `Promise<Database>`. As duas chamadas concorrentes compartilham a mesma conexão — não há segunda abertura, não há segunda migration, não há novo lock.
- `getHighlights` é `SELECT ... FROM book_highlights` (`:563`); `saveBook` é `INSERT ... ON CONFLICT` em `books` (`:524`). Tabelas distintas, nenhuma lê o resultado da outra.
- O `Reader` só monta depois que a `Library` já carregou, ou seja, `dbPromise` já está resolvido quando qualquer um dos dois dispara.

**Sem impacto — confirmado, não apenas aceito.**

### `[nit]` O cabeçalho de `useHighlights.ts` promete mais agnosticismo do que o hook entrega

`useHighlights.ts:5-7` diz *"Agnóstico de formato: nada aqui olha para `rects` ou para a página renderizada"*. A primeira metade é verdade — o hook realmente nunca lê `rects`. A segunda não é:

- `orderedHighlights` ordena por `a.page - b.page` (`:67`). É uma página numérica.
- O hook é tipado sobre `BookHighlight` (`src/types/index.ts:67-75`), onde `page: number` e `rects: BookHighlightRect[]` são **obrigatórios**. Um grifo de EPUB não cabe nesse tipo sem a union discriminada que ainda não existe.

Ou seja: o hook é **reaproveitável** pelo `EpubReader.tsx`, mas ainda não é agnóstico. O comparador é o **segundo** ponto onde o modelo de posição do PDF vaza — o primeiro é o `p. ${page}` de `buildQuoteBlock`, que já está registrado como decisão em aberto. Vale que os dois estejam na mesma lista, porque quem escrever o `EpubReader.tsx` vai bater nos dois no mesmo dia.

Não é defeito (nenhum código de EPUB entra nesta task), mas o comentário vai enganar. Sugestão de redação: *"Compartilhado entre leitores. A ordenação ainda assume `page` numérica — muda junto com a decisão do rótulo de posição do EPUB."*

### `[importante]` `QuoteToNoteModal`: criar o primeiro notebook pelo modal provavelmente joga o usuário de volta para a lista

`QuoteToNoteModal.tsx:110-117` reseta a máquina de estados sempre que `notebooks.length` muda:

```ts
useEffect(() => {
  if (!open) return
  setStage(initialStage(notebooks.length))
  // ...
}, [open, notebooks.length])
```

No caminho "You have no notebooks yet", `handleCreateNotebookFromEmpty` (`:169-183`) faz `await onCreateNotebook(name)` e então `setStage({ kind: 'new-note-title', notebookId: nb.id })`. Mas `onCreateNotebook` é o `handleCreateNotebookFromChat` do `App.tsx:1022-1033`, que atualiza o estado de notebooks do pai antes de resolver. Resultado esperado: no mesmo commit, `stage` vira `'new-note-title'` **e** `notebooks.length` vai de 0 para 1; o effect então dispara e sobrescreve com `initialStage(1)` = `'notebook-select'`. O usuário cria o notebook e cai na lista de notebooks em vez do campo de título da nota — a citação não se perde, mas o fluxo dá um passo para trás.

Cheguei nisso por leitura do código, **não executei**. Vale uma verificação manual antes de agir. Se confirmar, a correção natural é tirar `notebooks.length` das deps e resolver o estado inicial só na transição de `open`.
