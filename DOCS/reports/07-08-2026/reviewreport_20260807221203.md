## Achados

### `[importante]` 1 — `locations.generate()` congela o import 5–30 s num EPUB normal; a medição do spike não generaliza

**Onde:** `src/lib/epub.ts:91` (`await book.locations.generate(LOCATION_CHARS)`)

O `Locations` do epubjs espera **100 ms entre cada item de spine**, serialmente:

```js
// node_modules/@likecoin/epubjs/lib/locations.js
constructor(spine, request, pause) { this.pause = pause || 100 }
process(section) {
  return section.load(this.request).then(function (contents) {
    ...
    this.processingTimeout = setTimeout(() => completed.resolve(locations), this.pause)
```

e o `Book` constrói sem passar pause (`book.js:151`: `new Locations(this.spine, this.load.bind(this))`), então vale o default de 100 ms. Somando o tick de `requestAnimationFrame` da `Queue`, dá ~110 ms por item **independente do tamanho do item**.

O arquivo do spike (`Fausto`) tem **spine de 2 itens** — foi escolhido justamente por ser o caso patológico oposto (um XHTML gigante). Por isso os 175 ms pareceram baratos. Um EPUB de editora normal é um XHTML por capítulo: dezenas a centenas de itens.

**Medido** (Chrome headless, `src/lib/epub.ts` real via esbuild, dois EPUBs com **o mesmo texto total**, mudando só a divisão do spine):

| Fixture | Itens de spine | `extractEpubInfo` |
| --- | --- | --- |
| `spine2.epub` | 2 | **249 ms** |
| `spine120.epub` | 120 | **13.309 ms** |

**Correção verificada — uma linha.** Setar `book.locations.pause = 0` antes do `generate()`:

| Fixture | Atual | Com `pause = 0` | locations | `locations.save()` |
| --- | --- | --- | --- | --- |
| `spine2.epub` | 249 ms | **44 ms** | 274 → 274 | **idêntico** |
| `spine120.epub` | 13.309 ms | **1.998 ms** | 360 → 360 | **idêntico** |

O JSON serializado sai **byte a byte igual**, então a premissa de determinismo que o Orquestrador levantou (é ela que torna seguro cachear `locations_json`) fica preservada. E com `pause = 0` o loop ainda cede o thread a cada seção (setTimeout(0) + rAF da Queue), então a UI continua pintando — os 2 s de 120 seções são ritmo de rAF, não bloqueio.

Isto endereça diretamente o edge case que a própria task listou: *"`locations.generate()` em livro grande pode levar alguns segundos: o import deixa de ser instantâneo. Garantir que a UI não pareça travada durante o import."* Hoje o único feedback é o botão em "Importing…", sem progresso.

### `[importante]` 2 — `extractEpubInfo` sem timeout: EPUB malformado pode travar o import para sempre, sem rollback

**Onde:** `src/lib/epub.ts:88-104` e `src/lib/books.ts:39-91`

O `codeAgent` identificou corretamente essa classe de problema e desviou de duas ocorrências (decisão 2: não aguardar `book.ready`/`book.opened`, que podem nunca resolver). Mas a mesma forma existe no caminho que ficou:

```js
// node_modules/@likecoin/epubjs/lib/archive.js — request()
if (response) {
  response.then(function (r) {
    let result = this.handleResponse(r, type)   // pode lançar
    deferred.resolve(result)
  }.bind(this))
}                                                // sem .catch
return deferred.promise                          // nunca settla se lançar
```

Se `handleResponse` lançar, `deferred.promise` nunca settla → `section.load()` nunca settla → a fila do `Locations` nunca drena → `generate()` **nunca resolve nem rejeita**.

Consequência no app, que é o que importa: o `try/catch` de `importBook` nunca roda, então **não há rollback** — o arquivo fica em `books/` sem registro no banco; e `setImporting(false)` está no `finally` do `handleImport`, que também nunca roda, então o botão de import fica desabilitado em "Importing…" **até o app ser reiniciado**. É o pior desfecho possível do fluxo, e é o único que escapa da rede de rollback que a task pediu explicitamente.

Sugestão: um `Promise.race` com timeout dentro de `extractEpubInfo` (ou em volta dela, em `importBook`), rejeitando com erro comum — assim a falha cai no caminho de rollback + mensagem amigável que já existe. Com o achado 1 corrigido, um teto de ~60 s é folgado até para EPUBs grandes.

### `[nit]` 6 — `isDrmProtected` não conta `EncryptedData` sem método declarado

`src/lib/epub.ts:47-59`. A lógica está certa e os dois algoritmos permitidos estão corretos e completos — IDPF `2008/embedding` e Adobe `pdf/enc#RC` são os dois esquemas padrão de ofuscação de fonte, e ADEPT/LCP usam `xmlenc#aes128-cbc`/`aes256-cbc`, que caem no `.some()`. XML ilegível ou sem nenhum método → tratado como DRM, conservador e documentado.

A brecha teórica: só os `EncryptionMethod` são contados. Um `encryption.xml` com uma entrada legítima de ofuscação de fonte **mais** um `EncryptedData` sem `EncryptionMethod` declarado passaria como "não é DRM". Fechar é barato: comparar `getElementsByTagNameNS('*','EncryptedData').length` com `methods.length` e tratar a diferença como DRM. Fica a critério — nenhum esquema de DRM real omite o algoritmo.

### `[nit]` 7 — ordem da checagem de DRM

A checagem roda depois de `book.open()`, que já parseou `container.xml` e o OPF. Um esquema que criptografasse o próprio OPF falharia antes, com a mensagem de "corrompido" em vez da de DRM. Na prática ADEPT, LCP e FairPlay deixam container.xml e OPF em claro (só o conteúdo é cifrado), então não afeta caso real — e a ordem atual é a pragmática, já que é o epubjs que abre o zip.

### `[nit]` 8 — aviso de "EPUB ainda não disponível" usa o banner de erro, no topo da página

`src/components/Library/Library.tsx:158-165`. Funciona e a mensagem é clara, mas: (a) é `styles.errorBanner` com `role="alert"` para uma informação que não é erro; (b) o banner fica no topo, então numa lista longa, clicar num EPUB lá embaixo pode não produzir nada visível na viewport; (c) a linha continua com `styles.bookRow`, ou seja, com afordância de clicável. Aceitável para a Fase A, já que a Fase B remove o caso — é só o ponto mais fraco do requisito 9.

### `[nit]` 9 — `buildQuoteBlock` com `label` vazio

`src/lib/bookQuotes.ts:41` produz `— *Título*, ` com vírgula solta se `label` for `''`. Impossível no PDF (`p. ${page}` é sempre não-vazio) e o fallback previsto para EPUB ("só porcentagem") também é sempre não-vazio, então é preventivo.

### QUESTÃO ABERTA — `worker-src`: **a observação do `codeAgent` está incorreta; nenhuma correção é necessária**

A cadeia de fallback de `worker-src` **passa por `script-src`**: `worker-src → child-src → script-src → default-src`. Não é `worker-src → child-src → default-src` como registrado. Como a CSP tem `script-src 'self' 'wasm-unsafe-eval'` explícito (sem `blob:`), a resolução **para em `script-src`** e worker a partir de `blob:` continua bloqueado. Adicionar `blob:` a `default-src` **não alargou `worker-src` em nada**.

Medido em Chrome headless real (mesmo motor do WebView2), CSP por `<meta http-equiv>` — mesmo método do spike —, criando um `Worker` de blob e um same-origin e observando `securitypolicyviolation` + se o worker responde (o bloqueio no Chromium **não** é throw síncrono; é evento de erro, o que invalida testes que só checam try/catch):

| Variante de CSP | `new Worker(blob:)` | `new Worker('/x.js')` | violação reportada |
| --- | --- | --- | --- |
| **produção (a nova, verbatim)** | **BLOQUEADO** | permitido | `worker-src blocked blob` |
| produção + `worker-src 'self'` | **BLOQUEADO** | permitido | idêntico |
| **CSP antiga** (sem `blob:` nenhum) | **BLOQUEADO** | permitido | idêntico |
| controle: produção **sem** `script-src` | permitido | permitido | — |
| controle: produção + `child-src blob:` | permitido | **BLOQUEADO** | — |

Os dois controles provam o mecanismo, não só o resultado: tirar `script-src` libera o blob (aí sim a cadeia chega ao `default-src blob:`), e pôr `child-src blob:` libera o blob **e bloqueia o same-origin** (child-src vence script-src). A CSP nova e a antiga se comportam **igual** para workers.

**Recomendação: não adicionar `worker-src 'self'`.** Ele é inócuo (comportamento medido idêntico ao da produção) e pode ser incluído como documentação explícita se o Coordenador preferir deixar a intenção no arquivo em vez de depender da cadeia de fallback — mas não corrige nada, porque não há nada quebrado.

**E, para encerrar a preocupação com o pdf.js:** ele **não** seria quebrado nem se `worker-src 'self'` fosse adicionado.
- `src/lib/pdf.ts:7` importa `pdfjs-dist/build/pdf.worker.min.mjs?url`; o build emite o worker como asset e a URL é raiz-relativa — verificado no `dist/` recém-buildado: `"/assets/pdf.worker.min-FHbmGBN0.mjs"`, com o arquivo presente (1,24 MB).
- `node_modules/pdfjs-dist/build/pdf.mjs:15555` só troca o workerSrc por um wrapper `blob:` quando ele é **cross-origin** (`if (!PDFWorker._isSameOrigin(window.location, workerSrc))`). Não é o caso.
- O app só empacota para Windows (`tauri.conf.json` → `bundle.targets: ["nsis","msi"]`), onde o Tauri serve de `http://tauri.localhost` — origem HTTP real, então `_isSameOrigin` devolve true. (Se um dia houver build de macOS/Linux, onde o Tauri usa `tauri://localhost` e a origem é `"null"`, o pdf.js cairia no wrapper `blob:` — mas isso **já** seria bloqueado pela CSP antiga, então não é algo que esta task introduza.)
- Existe **exatamente um** `new Worker(` em todo o bundle de produção, e é o do pdf.js. O `@likecoin/epubjs` não cria worker nenhum (grep em `node_modules/@likecoin/epubjs/lib`), e não há `new Worker`/`?worker`/`SharedWorker`/`serviceWorker` em `src/`.
- Mesmo num cenário imprevisto, `pdf.mjs:15609` captura a falha do construtor e cai em `#setupFakeWorker()` (main thread, carregado por `import()` same-origin, permitido por `script-src 'self'`): degradação de performance, não leitor quebrado.

**Nota lateral, de menor peso:** o que `blob:` em `default-src` de fato alargou são as diretivas sem valor próprio que caem nele — `media-src`, `object-src`, `manifest-src`. `media-src blob:` provavelmente será necessário na Fase B (áudio/vídeo em EPUB 3); `object-src blob:` é o único sem uso previsto. Como `default-src` com `blob:` é decisão fechada (requisito 2), fica só como registro.
