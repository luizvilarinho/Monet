### Sugestões (opcional)

#### S1. Comentário enganoso em `findHighlightAtPoint` — `Reader.tsx:862-863`

**Descrição:** O comentário afirma "highlights mais recentes ficam depois na lista e devem interceptar cliques que cruzem múltiplos grifos sobrepostos", mas o `getHighlights` no storage usa `ORDER BY page ASC, created_at DESC` — ou seja, os mais recentes vêm PRIMEIRO na lista (não depois). Para adições locais via `persistHighlight`, os novos são sim anexados ao final (depois), mas a ordem do DB é o oposto.

**Comportamento real:** A iteração `for (let i = pageHighlights.length - 1; i >= 0; i--)` encontra o último elemento primeiro. No carregamento inicial do DB, isso é o highlight mais antigo (que visualmente fica no topo do stack de DOM, sendo renderizado por último no `flatMap`). Em adições locais, é o mais recente (também no topo). Em ambos os casos, o topmost visual é encontrado primeiro — o comportamento está correto.

**Impacto:** Nenhum funcional. Risco de confusão para quem ler o código no futuro e tentar entender a intenção.

**Recomendação:** Reescrever o comentário para algo como:
```ts
// Itera do fim para o início: os highlights renderizados por último no
// .highlightLayer ficam no topo do stack visual (último irmão = maior
// z-order), então devem ser checados primeiro para que grifos sobrepostos
// removam o que o usuário realmente vê/clica.
```

#### S2. Falta de feedback visual para "Copy" — `Reader.tsx:827-836`

**Descrição:** A ação "Copy" copia o texto para o clipboard e fecha a toolbar, mas não exibe nenhum toast ou indicação de sucesso. Se a cópia falhar (permissão negada, contexto inseguro), o erro vai apenas para `console.error`.

**Impacto:** O usuário não tem confirmação visual de que a cópia foi bem-sucedida. Em ambientes onde `navigator.clipboard.writeText` falha silenciosamente, o usuário pode pensar que copiou quando não copiou.

**Recomendação:** Reusar o `showSaveToast` existente para exibir "Copied to clipboard" por 1.5s, ou pelo menos logar o erro de forma visível.

---

#### S3. Otimismo sem rollback em `persistHighlight`/`removeHighlight` — `Reader.tsx:700-724`

**Descrição:** As funções atualizam o state local antes de chamar `storage.saveHighlight`/`storage.deleteHighlight`. Se a chamada ao storage falhar, o state local já foi atualizado e a UI não reflete a realidade do banco. No próximo carregamento do livro, o highlight "removido" reaparece (ou o "adicionado" some).

**Impacto:** Inconsistência UI ↔ DB em caso de falha de storage. O Task Report não exige rollback explícito, e o padrão do projeto (ex.: `useNotes.save`) também é otimista sem rollback, então isso é consistente com o codebase.

**Recomendação:** Opcional. Se desejado, capturar o erro e reverter o state local. Mas dado que o projeto inteiro segue o padrão otimista, manter como está é aceitável.

---

#### S4. Duplicação das constantes de zoom — `Reader.tsx:36-37` vs `tauri.ts:152-153`

**Descrição:** `MIN_SCALE = 0.5` / `MAX_SCALE = 3` no Reader e `BOOK_MIN_ZOOM = 0.5` / `BOOK_MAX_ZOOM = 3` no storage. O comentário em `tauri.ts:148-151` reconhece a duplicação e justifica a decisão de não criar um módulo compartilhado.

**Impacto:** Se alguém mudar o range em um lugar e esquecer o outro, o zoom pode ser persistido com um valor que o Reader não aceita (ou vice-versa). O `clampZoom` na escrita + `clampScale` na leitura mitigam isso na prática, mas é um risco latente.

**Recomendação:** Opcional. Mover para `src/lib/books.ts` (que já exporta `importBook`) ou criar `src/lib/readerConstants.ts` com `READER_MIN_ZOOM` / `READER_MAX_ZOOM` e importar de ambos os lados. O autor do código já considerou e preferiu não fazer — registrar como decisão consciente.

---

#### S5. `page.cleanup()` não chamado na página atual — `Reader.tsx:525-528`

**Descrição:** O `prevPageRef.current.cleanup()` é chamado para a página ANTERIOR quando uma nova é renderizada. A página atual (a última renderizada) só é liberada quando `loadedDoc.destroy()` roda no unmount do effect de carga do documento. Em sessões longas com muita navegação de página, isso pode acumular referências internas do pdfjs.

**Impacto:** Minor memory concern. O `loadedDoc.destroy()` limpa tudo no unmount, então não é um leak persistente.

**Recomendação:** Opcional. Chamar `page.cleanup()` no cleanup do effect de render quando `prevPageRef.current === page` (última página) ou simplesmente aceitar que o `loadedDoc.destroy()` cobre.

---

#### S6. `mousedown` no textContainer não chama `stopPropagation` — `Reader.tsx:397-445`

**Descrição:** O `onTextLayerMouseDown` é adicionado como native listener no `textContainer`. Ele não chama `e.stopPropagation()`, então o `onDocMouseDown` (no `document`) também dispara no mesmo evento. O `onDocMouseDown` chama `setSelection(null)` e `setRemovalCandidate(null)`, que no fluxo atual são no-ops (selection não foi setada ainda, removalCandidate é null no início do drag). Mas se alguém alterar a ordem dos effects ou adicionar lógica intermediária, isso pode causar um bug sutil.

**Impacto:** Fragilidade, não bug atual. O fluxo funciona porque `selection` só é setada no `handleTextMouseUp` (após `mouseup`), e `removalCandidate` é setada no `handlePageClick` (após `onClick`), ambos depois do `mousedown`.

**Recomendação:** Opcional. Adicionar `e.stopPropagation()` no `onTextLayerMouseDown` para isolar o handler e tornar o fluxo mais robusto a mudanças futuras. O `onDocMouseDown` continuaria funcionando para cliques fora do textContainer (toolbar, popover, painel, etc.).

---

#### S7. `useEffect` de reset do stage no modal pode causar flash — `QuoteToNoteModal.tsx:110-117`

**Descrição:** O effect `[open, notebooks.length]` reseta o stage para `initialStage(notebooks.length)` sempre que `notebooks.length` muda. Quando o usuário cria um novo notebook no stage `notebook-empty-create`:
1. `onCreateNotebook` é awaitado
2. O pai atualiza `notebooks` (length incrementa)
3. O effect roda e seta stage para `notebook-select`
4. O handler então seta stage para `new-note-title`

O usuário vê um flash de `notebook-select` (1 frame) antes de `new-note-title`. O estado final é correto.

**Impacto:** Visual glitch mínimo. Funcionalmente correto.

**Recomendação:** Opcional. Usar `[open]` como dependência (reset apenas ao abrir) e gerenciar transições de stage manualmente, ou usar `useLayoutEffect` para evitar o flash.

---

#### S8. `useWindowMouseMove` atualiza ref em todo mousemove — `Reader.tsx:447-451`

**Descrição:** O listener de mousemove no `window` atualiza `lastMousePosRef.current` em CADA movimento do mouse na janela, mesmo quando o usuário não está arrastando uma seleção na text layer. Isso é uma operação barata (atribuição de ref), mas acumula trabalho para o event loop.

**Impacto:** Performance negligenciável. Refs não disparam re-render.

**Recomendação:** Opcional. Guardar com `if (!isDraggingRef.current) return` no início do handler. Isso evita a atribuição quando não há drag ativo. Ganho mínimo.

## Observações Adicionais (positivas)

1. **Defesa em profundidade na cascata:** A cascata manual no `deleteBook` (`tauri.ts:550-561`) é complementada pelo `ON DELETE CASCADE` na FK da migration v13. Qualquer uma das duas cobre o caso se a outra falhar.

2. **Clamp triplo no zoom:** `clampZoom` no `rowToBook` (leitura), `clampZoom` no `saveBook` (escrita), `clampScale` no `useState` do Reader (inicialização). Três camadas de defesa contra dados corrompidos.

3. **`isConnected` check no controlador de seleção:** O guard `!anchor.node.isConnected` (`Reader.tsx:465-473`) cobre o caso de re-render mid-drag (troca de página/zoom durante o arrasto), limpando os refs stale sem crash.

4. **`queueMicrotask` para liberar `isClampingRef`:** O padrão de setar a flag, fazer `setBaseAndExtent`, e liberar via microtask (`Reader.tsx:435-440, 507-510`) garante que o `selectionchange` síncrono disparado pelo `setBaseAndExtent` seja ignorado, sem afetar o próximo `selectionchange` genuíno do browser.

5. **Acessibilidade:** `aria-label` em todos os botões interativos, `aria-pressed` no toggle, `role="dialog"` + `aria-modal` no modal, `role="status"` no toast, `aria-hidden` em elementos decorativos, `aria-invalid` no input com erro.

6. **Sem dead code:** O `rowToQuote` foi removido na Etapa 3 (conforme mencionado no execution report). O `onNavigateToNote` é mantido no contrato de props para paridade com `ChatPanel` mas não é consumido — decisão justificada.

7. **Estilos consistentes:** Uso correto de CSS custom properties do projeto (`--bg-panel`, `--border`, `--accent`, `--accent-warn`, `--accent-ai`, `--text-primary`, `--text-secondary`, `--text-muted`, `--surface-1`) com fallbacks. CSS Modules em todos os componentes.

8. **`BrowserStorage` com stubs "not implemented":** Consistente com o padrão pré-existente (todos os métodos de notes/notebooks/subjects também lançam). A interface `StorageAdapter` é genérica, mas o app roda exclusivamente em Tauri (verificado por `__TAURI__` / `__TAURI_INTERNALS__` em `storage/index.ts:67-73`).
