# Explorer Report — Fase 1 do Leitor de Livros (Library + Leitor de PDF)

- Task Report: `DOCS/reports/06-07-2026/taskreport_20260706013006.md`
- Branch: `feature/ebook-reader`
- Data: 06-07-2026

## Descrição do problema

Criar um novo modo "Library" (lista de livros PDF importados + leitor com navegação, zoom e memória de última página), reusando pdfjs-dist (já no package.json, nunca usado), a camada `src/storage/`, o backend Tauri de documentos e o padrão de CSS Modules. A exploração confirmou viabilidade em todos os pontos; abaixo os achados e recomendações.

## Nível de dificuldade: **Média**

Nenhum bloqueador. A parte nova de verdade é a integração do pdfjs (worker + text layer + assets wasm/fonts) — o resto segue padrões já existentes no projeto.

---

## 1. pdfjs-dist no Tauri (worker offline)

- **Não há nenhum uso nem configuração existente**: `pdfjs-dist` aparece só em `package.json`/`package-lock.json`. `vite.config.ts` é o boilerplate padrão do Tauri, sem nada de worker. Versão instalada em `node_modules`: **5.6.205** (build ESM: `node_modules/pdfjs-dist/build/pdf.mjs`, worker: `build/pdf.worker.min.mjs`). O package **não tem campo `exports`**, então qualquer subpath (`pdfjs-dist/build/...`) é importável sem restrição.
- **Mecanismo recomendado (offline, sem CDN)** — Vite empacota o worker como asset servido same-origin:
  ```ts
  import * as pdfjs from 'pdfjs-dist'
  import workerUrl from 'pdfjs-dist/build/pdf.worker.min.mjs?url'
  pdfjs.GlobalWorkerOptions.workerSrc = workerUrl
  ```
  A alternativa `new URL('pdfjs-dist/build/pdf.worker.min.mjs', import.meta.url).toString()` também funciona no Vite; `?url` é mais explícito e é o suficiente aqui. Em produção o asset sai no `dist/` e é servido pelo protocolo do Tauri (`http://tauri.localhost`), same-origin — funciona offline.
- **CSP compatível**: a CSP em `src-tauri/tauri.conf.json` é `default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; ...`. Não define `worker-src`, então o browser faz fallback para `script-src 'self'` — worker same-origin permitido. O `'wasm-unsafe-eval'` (já presente) é exatamente o que o pdfjs 5.x precisa para os decoders WASM. **Nenhuma mudança de CSP necessária** se os bytes vierem por comando Rust (ver §6).
- **Text layer**: pdfjs 5.x expõe a classe `TextLayer` (a antiga `renderTextLayer` foi removida). Uso: `new TextLayer({ textContentSource: page.streamTextContent(), container, viewport }).render()`. O container precisa da CSS var `--total-scale-factor` (5.6 usa esse nome, não mais só `--scale-factor`) e do CSS do text layer — dá para importar `pdfjs-dist/web/pdf_viewer.css` ou escrever um CSS mínimo próprio (recomendado: mínimo próprio; o pdf_viewer.css completo traz muita coisa do viewer que não usaremos).
- **Assets auxiliares** (importante para robustez):
  - `node_modules/pdfjs-dist/wasm/` (jbig2.wasm, openjpeg.wasm, qcms_bg.wasm) — usados para PDFs escaneados (JBIG2/JPEG2000). Sem eles, essas páginas não renderizam.
  - `standard_fonts/` e `cmaps/` — fontes padrão e PDFs CJK.
  - Esses diretórios precisam ser copiados para o bundle e apontados nas options do `getDocument` (`wasmUrl`, `standardFontDataUrl`, `cMapUrl`). Como a constraint proíbe novas dependências de UI, a opção limpa é um mini-plugin inline no `vite.config.ts` que copia os diretórios para `dist/` no build (ou copiá-los para `public/pdfjs/`). É pouco código e evita `vite-plugin-static-copy`.

## 2. Camada de storage e tabela `books`

- **Arquitetura**: `src/storage/index.ts` define a interface `StorageAdapter` e escolhe `TauriStorage` (via `window.__TAURI__`) ou `BrowserStorage` (stub que lança `not implemented` em quase tudo — só reminders têm fallback localStorage). Todos os métodos novos de books devem ser adicionados às três classes (no browser, stub que lança erro, seguindo o padrão).
- **Migrations**: ficam em `src-tauri/src/lib.rs`, no vetor `migrations` do `tauri_plugin_sql::Builder` (`add_migrations("sqlite:monet.db", ...)`). Hoje vai até a **versão 11**. A tabela `books` entra como **Migration versão 12** (`CREATE TABLE IF NOT EXISTS books (...)`), mesmo mecanismo das demais.
- **Padrão de persistência** (seguir `notebooks`/`notes` em `src/storage/tauri.ts`): interfaces de Row snake_case + função `rowToX`, `db.select`/`db.execute` com `INSERT ... ON CONFLICT(id) DO UPDATE`, e **chamar `this.scheduleCheckpoint()` após toda escrita** — é o mecanismo que mantém o WAL drenado (bug histórico das "notas que somem"). O update de `last_page` a cada troca de página se beneficia do throttle de 1,5s já embutido.
- **Corrida de lock (histórico)**: o `monet.db` é aberto por DUAS vias — tauri-plugin-sql (frontend) e rusqlite (`documents.rs`, `DocDb`, com `busy_timeout` de 5s). O comentário no topo de `documents.rs` documenta o invariante: **cada tabela tem um único dono**. `documents`/`notebook_document_visibility` são do backend; `notebooks`/`notes`/etc. são do frontend. Recomendação: a tabela `books` deve ser **propriedade exclusiva do frontend** (via plugin-sql/TauriStorage), e o comando Rust de import **não deve tocar o banco** — só copia o arquivo e devolve o path; o frontend insere a linha. Isso respeita o invariante e evita reintroduzir a corrida de cold start (que já é mitigada pelo retry de 15 tentativas no `TauriStorage.load()`).

## 3. Backend Tauri (file dialog, cópia de arquivo, capabilities)

- **File dialog**: feito via crate `rfd` em comando Rust (`documents_pick_file` em `documents.rs`, com `spawn_blocking`), não via plugin dialog do Tauri — não há permissão de dialog nas capabilities e não precisa. O comando atual filtra `pdf/txt/md`; para a Library, criar um `books_pick_file` só-PDF (ou parametrizar) é trivial.
- **Cópia para o diretório do app**: `documents_upload_global` já faz exatamente o fluxo desejado: valida mime/size (`MAX_FILE_BYTES` = 50 MB), copia com `fs::copy` para `app_data_dir()/documents/<uuid>.<ext>` e insere na tabela `documents` via rusqlite. **Não é diretamente reutilizável** porque ele dispara indexação RAG e grava na tabela `documents` (fora do escopo da Fase 1). Será preciso um **novo comando** `books_import_file` (copia para `app_data_dir()/books/<uuid>.pdf`, valida que é PDF, devolve o path destino) — ~30 linhas seguindo o padrão de `documents_upload_global`/`save_chat_doc`. Também: `books_read_file` (bytes para o leitor, ver §6) e `books_delete_file` (remoção com validação de path dentro de `books/`, padrão do `delete_chat_doc`).
- **Capabilities/permissões** (`src-tauri/capabilities/default.json`): há `core:default`, sql (`allow-execute/load/select`), notification, opener, updater, process, global-shortcut. **Não há plugin fs nem dialog** — e não precisam ser adicionados: todo acesso a arquivo é feito em comandos Rust próprios (invoke), que não passam pelo sistema de permissões de plugins. Nenhuma mudança de capability necessária.
- Registro dos comandos novos: adicionar ao `invoke_handler` em `lib.rs` e criar wrappers no front (padrão `src/lib/documents.ts` → sugerido `src/lib/books.ts` com `invoke(...)`).

## 4. Padrão de UI

- **Alternância de modos**: `ActiveMode = 'notebook' | 'chat'` em `src/components/Toolbar/Toolbar.tsx` (nav com botões `modeButton`/`modeButtonActive`). Em `src/App.tsx`: estado `activeMode` (linha ~264) persistido em `localStorage['monet:active-mode']` — atenção: a restauração faz `saved === 'chat' ? 'chat' : 'notebook'` e precisa ganhar o caso `'library'`. O roteamento é um ternário na renderização (linha ~1140): `activeMode === 'chat' ? <div className="workspace"><ChatPanel/></div> : <div className="workspace">…notebook…</div>`. O modo Library entra como terceiro ramo com o mesmo padrão de `<div className="workspace">` ocupando a tela toda.
- **CSS Modules**: todo componente é uma pasta `src/components/X/` com `X.tsx` + `X.module.css`. Novos: `Library/` e `Reader/`.
- **Referência de tabela**: `KnowledgeBaseModal` (`src/components/KnowledgeBaseModal/KnowledgeBaseModal.tsx`, linhas 211–290) usa um **`<table className={styles.table}>` real** com pills de status, skeleton de loading (`<ul className={styles.skeletonList}>`) e ações por linha — é a melhor referência de estilo para a tabela de livros. Também tem o fluxo completo de import (pick → upload → erro) e usa `useConfirm()` (`src/hooks/useConfirm`) para confirmação de remoção — reutilizar para o "remover livro".
- **Referência de tela cheia**: `ChatPanel` — substitui todo o workspace quando `activeMode === 'chat'`; a Library segue o mesmo esquema.

## 5. Metadados do PDF

- **pdfjs-dist cobre tudo**: `doc.numPages` (total de páginas) e `await doc.getMetadata()` → `info.Title` / `info.Author` (podem vir vazios/undefined — fallback para nome do arquivo, como o Task Report pede). Recomendação: extrair no **frontend durante o import** — depois da cópia pelo Rust, carregar o PDF uma vez com pdfjs, ler numPages/Title/Author e só então inserir a linha em `books`. Bônus: isso valida o PDF (corrompido/senha lança `InvalidPDFException`/`PasswordException`) **antes** de registrar no banco, atendendo o edge case de não criar livro órfão — o comando de import deve desfazer a cópia se a validação falhar.
- **Alternativa Rust**: `pdf-extract` 0.7 (única crate PDF no Cargo.toml) é focada em extração de texto; não expõe metadados/numPages de forma utilizável. Uma alternativa exigiria crate nova (ex.: `lopdf`) — desnecessário, o pdfjs no front resolve.

## 6. Riscos concretos de integração

1. **Leitura do binário do disco para o front** — decisão necessária. Não há plugin fs instalado e `convertFileSrc` exigiria habilitar o assetProtocol (`app.security.assetProtocol` em tauri.conf.json) **e** alterar a CSP. Recomendação: **comando Rust `books_read_file` retornando `tauri::ipc::Response::new(bytes)`** (Tauri 2 transfere bytes crus eficientemente pelo IPC, sem JSON) e no front `getDocument({ data: new Uint8Array(await invoke(...)) })`. Zero mudança de CSP/capabilities, validação de path no Rust (padrão `read_chat_doc`). Com o limite de 50 MB já praticado no projeto, carregar o PDF inteiro em memória é aceitável para desktop.
2. **Assets do pdfjs (wasm/fonts/cmaps) fora do bundle** — sem copiá-los e configurar `wasmUrl`/`standardFontDataUrl`/`cMapUrl`, PDFs escaneados (JBIG2/JPX) e alguns PDFs sem fontes embutidas renderizam páginas em branco ou quebradas — exatamente o edge case "PDF escaneado deve renderizar". Mitigação no §1 (cópia via plugin inline no Vite + options no getDocument).
3. **CSP**: risco baixo — worker same-origin e `'wasm-unsafe-eval'` já cobertos. Só vira problema se optarem por `convertFileSrc` (exigiria `asset:`/`http://asset.localhost` na CSP) — mais um motivo para o comando Rust.
4. **Persistência de `last_page` em alta frequência**: gravar a cada troca de página gera muitas escritas; o `scheduleCheckpoint` throttled já mitiga o WAL, mas vale debounce leve no front (ex.: 300–500 ms) para não enfileirar um execute por tecla ← / →.
5. **Restauração do modo no localStorage** (`monet:active-mode`): o parse atual descarta valores desconhecidos — precisa ser atualizado junto com o tipo `ActiveMode`, senão o modo Library nunca é restaurado (bug silencioso).
6. **API do pdfjs 5.x difere de exemplos antigos**: `renderTextLayer` não existe mais (usar classe `TextLayer`), variável CSS é `--total-scale-factor`. Exemplos da web (v3/v4) não funcionam — o plano deve citar a API correta para o codeAgent não cair nisso.
7. **Renderização sob demanda (500+ páginas)**: renderizar só página atual ± vizinhas e chamar `page.cleanup()` nas distantes; manter o `PDFDocumentProxy` aberto enquanto o leitor estiver montado e `doc.destroy()` ao sair (senão o worker vaza memória entre livros).

## Recomendações / ajustes de escopo

- **Sem mudança de escopo em relação ao Task Report.** Todos os requisitos são viáveis com a infra atual. Duas decisões que o planner deve fixar:
  1. Transporte do binário: comando Rust com `tauri::ipc::Response` (recomendado) em vez de assetProtocol/convertFileSrc.
  2. Propriedade da tabela `books`: frontend (plugin-sql + migration v12), com comandos Rust restritos a operações de arquivo (import/read/delete) — sem tocar o banco — para respeitar o invariante documentado em `documents.rs`.
- Incluir no plano a cópia dos assets do pdfjs (wasm/standard_fonts/cmaps) — é fácil de esquecer e só quebra em PDFs específicos, passando batido em teste superficial.
- Duplicata de import: sugerir comportamento "permitir duplicata" (mais simples; cada import gera UUID e cópia própria) com aviso opcional — evita hashing de arquivo na Fase 1.
