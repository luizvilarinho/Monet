# Explorer Report — Sub-pipeline acadêmico (Crossref → Unpaywall/DOAJ → PDF → RAG)

**Timestamp:** 20260724172653
**Dificuldade global:** Média
**Veredito:** Viável, sem bloqueadores técnicos. Toda a infra necessária (reqwest com bytes/redirect/timeout, padrão `librarian_decide`, escrita atômica temp→rename, ingestão de PDF via `pdf_extract`, serialização por pasta) já existe. O trabalho é **aditivo** — nada precisa ser refatorado no pipeline web. As decisões abertas são de produto (abstract ausente, PDF escaneado), não de viabilidade.

## 1. Cliente HTTP no Rust para download binário

**Como o Rust faz HTTP hoje:** `reqwest` 0.12 (`Cargo.toml:26`), com `default-features=false` + features `json`, `stream`, `rustls-tls`. Todas as chamadas externas usam `reqwest::Client::new()` + `.post(...).bearer_auth().header().json(&body).send()` e leem a resposta com `.json()` ou `.text()`. Exemplos: `deep_research_generate_sub_queries` (`lib.rs:438`), `librarian_decide` (`lib.rs:545`), `web_search_route` (`lib.rs:753`), streaming em `lib.rs:1013`.

**O cliente consegue tudo que o download precisa — sem adicionar crate nem feature:**

- **Ler bytes:** `Response::bytes()` é core do reqwest (não depende de feature). Retorna `bytes::Bytes` (o corpo inteiro em memória — adequado a papers ≤ 50MB; não precisa de streaming). A feature `stream` já presente habilitaria `bytes_stream()` caso se queira cortar cedo, mas **não é necessária** para o MVP.
- **Seguir redirects:** ligado por padrão. `Client::new()` usa `redirect::Policy::default()` = segue até 10 redirects. Unpaywall/publishers costumam redirecionar (ex.: `doi.org` → landing → PDF), então isso é essencial e já vem grátis. Se quiser limitar, `Client::builder().redirect(Policy::limited(n))`.
- **User-Agent:** `Client::builder().user_agent("Monet/0.1 (mailto:luizvilarinho@gmail.com)")` OU header por request `.header("User-Agent", ...)`. Ambos disponíveis.
- **Timeout:** `Client::builder().timeout(Duration::from_secs(30))` ou `.timeout()` no RequestBuilder. `tokio` já tem a feature `time` (`Cargo.toml:27`) e `use tokio::time::timeout` já é importado (`lib.rs:74`).

**Conclusão:** **nada a adicionar** ao Cargo.toml. Basta trocar `reqwest::Client::new()` por um `Client::builder().user_agent(...).timeout(...).build()` no comando novo (os outros comandos podem continuar com `::new()`). Diferença de padrão em relação ao código atual: os comandos existentes leem `.json()`/`.text()`; o novo lê `.bytes()`. É a única novidade real.

## 2. Comando de escrita binária — recomendação: **comando único "baixa→valida→grava"**

`documents_write_ai_source_file` (`documents.rs:1090`) hoje:
- Assinatura: `(folder_id, filename, content: String)`.
- Valida `content` não-vazio e `content.len() <= MAX_FILE_BYTES` (`documents.rs:1100`).
- Resolve `original_path` + `origin` da pasta; exige `origin == "ai"` (`documents.rs:1117`).
- Sanitiza `filename` via `Path::file_name()` e **exige `.ends_with(".md")`** (`documents.rs:1125`) — é o único ponto text-only.
- Escreve atômico: `fs::write(tmp)` → `fs::rename(tmp, final)`, com sufixo `.tmp` (que o scan ignora) e limpeza do `.tmp` órfão em falha (`documents.rs:1129-1140`).

**O que mudaria para binário:** aceitar `&[u8]` em vez de `String` (remover `content.trim().is_empty()` → checar `bytes.is_empty()`), e trocar a exigência `.md` por `.pdf`. `fs::write` já aceita `&[u8]`. `MAX_FILE_BYTES`, temp→rename e o gate `origin=='ai'` ficam iguais.

**Trade-off — dois desenhos possíveis:**

**(A) Generalizar/duplicar o comando de escrita e baixar no frontend.** Inviável: o download é binário + CORS (o Task Report já trava isso no Rust). Passar os bytes do Rust→frontend→Rust via IPC seria absurdo (serialização JSON de array de bytes, dobro de cópia). Descartado.

**(B) [RECOMENDADO] Um único comando Rust `librarian_fetch_and_save_pdf(folder_id, url, filename)` que: baixa → valida `%PDF` → escreve atômico → retorna `Ok(())`/`Err`.** Vantagens:
- Os **bytes nunca cruzam o IPC** — nascem e morrem no Rust.
- Reduz superfície: uma trip de invoke por paper, não três (resolver-url, baixar, gravar).
- Reaproveita literalmente o bloco temp→rename de `documents_write_ai_source_file` (extrair um helper `write_bytes_atomic(dir, safe_name, &bytes)` que ambos os comandos chamam, mantendo o `.md`/`.pdf` gate no chamador).
- A validação `%PDF` fica colada à escrita — impossível gravar HTML por engano.

Manter o `documents_write_ai_source_file` de `.md` **intacto** (o pipeline web depende dele). O novo comando é irmão, não substituto. Recomendo o helper compartilhado `write_bytes_atomic` para não duplicar a lógica de rename/cleanup.

**Nota de sanitização de filename:** replicar o `Path::file_name()` + comparação `safe_name != filename` do comando `.md` (`documents.rs:1121-1124`), trocando a checagem de extensão para `.pdf`. Como o filename é gerado por nós (`{ano}_{slug}.pdf`), o slug precisa ser sanitizado no TS (sem `/`, `\`, `:`, etc.) — ver §6.

## 3. APIs Crossref / Unpaywall / DOAJ — shapes e onde hospedar

### Crossref — `GET https://api.crossref.org/works`
- **Params:** `query.bibliographic=<termos>` (ou `query=`), `rows=<N pequeno, ex. 8>`, opcional `filter=type:journal-article`, `select=DOI,title,published,type,abstract` para enxugar o payload.
- **Polite pool:** incluir `mailto=luizvilarinho@gmail.com` no query string **e** no `User-Agent` (`Monet/0.1 (mailto:luizvilarinho@gmail.com)`). Isso move a chamada para o pool "polite" (mais estável). Não exige chave.
- **Response:** `message.items[]`, cada item com `DOI` (string), `title` (**array** de strings — usar `[0]`), `published['date-parts'][0][0]` (ano, int), `type` (ex. `"journal-article"`), `abstract` (**quando existe**, vem como **JATS XML** embutido, ex. `<jats:p>...</jats:p>` — precisa stripar tags antes de mandar ao modelo).
- **Abstract confiável?** **Não.** Crossref só tem abstract se o publisher depositou — cobertura parcial (grosso modo ~40-60%, muito variável por editora). Quando vem, é JATS com tags. **Este é o principal ponto fraco** (ver Edge Case §4 e §7).

### Unpaywall — `GET https://api.unpaywall.org/v2/{doi}?email=luizvilarinho@gmail.com`
- **Email obrigatório e real** — recusa placeholders (`test@example.com` → erro). Fixar `luizvilarinho@gmail.com`.
- **Response:** `is_oa` (bool), `best_oa_location` (objeto ou null) com `url_for_pdf` (link direto do PDF, pode ser null mesmo com OA) e `url` (landing). Também `oa_locations[]` (lista completa — fallback se `best_oa_location.url_for_pdf` for null, varrer por `url_for_pdf` não-nulo).
- **Regra:** se `is_oa == false` ou nenhum `url_for_pdf` disponível → descartar em silêncio.
- **Rate:** 100k/dia, pede throttle. Loop por-DOI precisa de pausa curta entre chamadas.

### DOAJ — `GET https://doaj.org/api/search/articles/{query-url-encoded}`
- **Fallback** quando Unpaywall não dá OA. Periódicos 100% OA.
- **Response:** `results[]`, cada `bibjson.link[]` com `type: "fulltext"` e `url` — **mas o link costuma ser HTML da landing, não PDF direto**. A validação `%PDF` (§3b) vai rejeitar boa parte. DOAJ é fallback fraco para *download de PDF*; útil mais como sinal de "é OA". Vale começar **só com Crossref+Unpaywall** e adicionar DOAJ só se a taxa de sucesso for baixa demais — evita complexidade de baixo retorno (nota anti-overengineering para o planner).

### Onde hospedar as chamadas — **recomendação mista:**
- **Crossref e Unpaywall:** podem viver no **frontend** (`src/lib/librarian.ts`), via `fetch`. Ambas retornam **JSON** (não binário) e historicamente enviam `Access-Control-Allow-Origin: *` (CORS liberado). Isso mantém a orquestração no TS junto do resto do pipeline (mais fácil de testar, sequenciar, cancelar). **Porém**, o webview do Tauri em produção usa origin `tauri://localhost` / `https://tauri.localhost` — algumas APIs podem barrar origins não-http. **Risco baixo mas não-zero.**
- **Download do PDF:** **obrigatoriamente no Rust** (binário + CORS + redirects + `%PDF`), conforme §1/§2.

**Justificativa da recomendação:** minimizar superfície de backend novo. Metadados em JSON com CORS aberto → frontend; só o binário → Rust. **Alternativa conservadora** (se o planner preferir uniformidade com os outros comandos externos, todos no Rust): mover Crossref/Unpaywall para comandos Rust irmãos de `web_search_route`. Custo: 2 comandos a mais e o parsing de JATS em Rust. **Não decido — reporto**; minha inclinação é frontend para os metadados, mas o planner deve pesar o risco de CORS/origin do webview vs. a uniformidade. Um teste rápido de `fetch('https://api.crossref.org/works?query=test&rows=1')` de dentro do app resolve a dúvida em 1 minuto.

## 3b. Assinatura `%PDF` e PDF escaneado

- **Validar `%PDF` é trivial no Rust — confirmado.** `bytes.starts_with(b"%PDF")` (os 4 primeiros bytes do magic number; a versão completa é `%PDF-1.x`). Uma linha, sem crate. Rejeita HTML de landing/login/erro antes de gravar.
- **PDF escaneado (só-imagem) passa no `%PDF`** — o magic byte não diz nada sobre haver texto. O comportamento atual está em `read_document_text` (`documents.rs:502-523`): `pdf_extract::extract_text` roda; se o texto extraído for vazio, `documents.rs:520` retorna `Err("PDF has no extractable text (may be scanned)")`. Ou seja, **hoje o scan já trata isso graciosamente** — o documento entra com status de erro e **não gera chunks** no RAG (vira "arquivo morto": ocupa espaço em disco e uma linha na tabela `documents`, mas não polui os embeddings).

**Opções (não decido — reporto):**
1. **Aceitar como está.** Salvar todo PDF que passe no `%PDF`; o scan marca os escaneados como erro e não indexa. Simples, zero código novo. Custo: PDFs mortos no disco e na listagem da KB.
2. **Detectar/pular antes de salvar.** Rodar `pdf_extract::extract_text` sobre os bytes baixados **antes** do rename; se vier vazio, descartar sem gravar. Custo: `pdf_extract` só aceita path, não bytes — precisaria gravar o `.tmp`, tentar extrair, e só então renomear ou apagar. Adiciona uma extração síncrona (pesada) no caminho de download. Mais limpo na KB, mais lento e mais código.
3. **Meio-termo:** salvar, deixar o scan detectar, e (futuro) uma varredura apaga PDFs com status de erro. Fora do escopo v1.

**Minha leitura:** a Opção 1 é suficiente para o v1 — o dano de um PDF escaneado é cosmético (não corrompe o RAG, graças ao guard em `documents.rs:520`), e a barra de relevância + cap de 3 já limitam o volume. A Opção 2 só se justifica se o Coordenador quiser a KB impecável. Deixo para o planner/Coordenador.

## 4. Extração de termos + filtro de relevância — reaproveita `librarian_decide`

**Sim, o padrão `librarian_decide` (`lib.rs:528`) serve para as duas etapas, com prompts novos.** Ele é genérico: recebe um `prompt: String` + um `field: &str`, chama `LIBRARIAN_MODEL` (`deepseek/deepseek-chat`) com `response_format: json_object`, faz parsing tolerante e retorna `Vec<String>` (ou `vec![]` em qualquer falha). Dois comandos novos, espelhando `librarian_triage`/`librarian_judge`:

- **(a) `librarian_academic_query(question, current_date) -> Vec<String>`:** prompt que transforma o tópico do turno em 1-2 queries bibliográficas para o Crossref (termos canônicos, sem sintaxe de pergunta — igual ao espírito de `deep_research_generate_sub_queries`). `field: "queries"`. **Ajuste necessário:** `librarian_decide` hoje retorna `Vec<String>` — perfeito para queries.
- **(b) `librarian_academic_relevance(question, candidates_block, current_date) -> Vec<String>`:** prompt que, dado título (+abstract quando houver) de cada candidato, devolve os DOIs genuinamente on-topic e substanciais, barra conservadora, **cap implícito no prompt** ("no máximo 3"). `field: "dois"` (retorna DOIs verbatim; o TS filtra contra o conjunto de candidatos, como já faz com URLs). O cap final de 3 é reforçado no TS (`.slice(0,3)`), não confiando só no modelo.

Nenhum comando novo de infra — só dois `#[tauri::command]` finos que montam prompt e chamam `librarian_decide`, registrados no `generate_handler!` (`lib.rs:1595-1596`, ao lado de `librarian_triage`/`librarian_judge`). Wrappers TS em `src/lib/librarian.ts` no mesmo estilo de `librarianTriage`/`librarianJudge` (`librarian.ts:8-22`).

**Sobre abstract ausente (Edge Case do Task Report):** a etapa (b) fica fraca julgando só por título. Opções para o planner: (i) aceitar (mais conservador quando não há abstract — o prompt instrui "sem abstract, aprove só se o título for inequivocamente on-topic"); (ii) buscar abstract em Semantic Scholar/OpenAlex (escopo novo — desaconselho no v1). Recomendo (i).

## 5. Encaixe no `runPipeline` de `librarian.ts`

O sub-pipeline acadêmico roda **em paralelo lógico** ao web, dentro do **mesmo turno e mesma pasta**, compartilhando toda a infra. Pontos de integração exatos:

- **Contexto:** `librarianContextRef` (`useChat.ts:933-940`) já carrega `question`, `searchResults`, `chatFolderId`, `folderName`, `visibleDocumentIds`, `webResearchEnabled` — **o `question` necessário para gerar a query Crossref já está lá.** Nada a adicionar ao ref. É populado nos dois caminhos de busca (`useChat.ts:2067` sem-tools e `:2337` com-tools) e consumido/limpo em `onOpenRouterDone` (`:1690`).
- **Disparo:** `enqueueLibrarian` (`librarian.ts:46`) é o ponto único. O acadêmico deve rodar **dentro da mesma cadeia serializada por pasta** (`folderChains`, `librarian.ts:31`) para não escrever concorrente com o web na mesma pasta. Duas formas:
  1. **[RECOMENDADO]** Dentro de `runPipeline`, após o bloco web terminar, rodar um bloco `runAcademicPipeline(input)` sequencialmente (mesma promise da cadeia). Assim os dois compartilham `existingAiFolder`, `documentsEnsureAiFolder`, o scan e o toast **naturalmente**, e a serialização por pasta já cobre ambos. O `inFlightUrls` (`librarian.ts:30`) — hoje só de hashes web — pode ganhar as chaves acadêmicas (`doi:<doi>` ou o filename `.pdf`) para dedupe cross-pipeline no mesmo namespace Set.
  2. Enfileirar um segundo `enqueueLibrarian` com um flag `mode: 'academic'`. Mais isolado, mas duplica a busca da AI folder e o scan. **Desaconselho** — a Opção 1 reaproveita mais.
- **`documentsEnsureAiFolder`:** mesma chamada (`librarian.ts:125`), **mesma pasta** ("Web research — {folderName}"). Criação preguiçosa: só chamar quando houver ≥1 PDF aprovado E baixado com sucesso (papers podem falhar no OA/`%PDF` e sobrar zero). Atenção: se o web já criou a pasta neste turno, o acadêmico reusa o `aiFolderId` retornado — idempotente por `original_path` (`documents.rs:1051-1064`).
- **`scan`:** `documentsScanWatchedFolder(aiFolderId)` (`librarian.ts:148`) — chamar **uma vez** cobrindo ambos. Se rodarem sequenciais dentro do mesmo `runPipeline`, basta um scan no fim que pega `.md` e `.pdf` juntos.
- **`onSaved` / toast:** `input.onSaved(count)` (`librarian.ts:151`) alimenta `webSourcesSaved` (`useChat.ts:1712`) → toast "N sources saved" (`ChatPanel.tsx:503`). **A contagem deve somar páginas web + papers.** Se os dois blocos rodam no mesmo `runPipeline`, acumular `savedCount` de ambos e chamar `onSaved` **uma vez** com a soma. Se forem enqueues separados, o toast dispararia duas vezes (feio) — mais um motivo para a Opção 1.

**Resumo:** o encaixe mais limpo é **estender `runPipeline`** para, depois do web, rodar a fase acadêmica, acumular no mesmo `savedCount`, e disparar scan+toast uma vez. Zero mudança no `useChat.ts` e no `enqueueLibrarian`.

## 6. Dedupe por DOI / nome de arquivo e convivência com `hashUrlToFilename`

- **Namespaces distintos, sem colisão.** Web: `hashUrlToFilename(url)` → `<sha256>.md` (`search.ts:132-138`). Acadêmico: `{ano}_{titulo-slug}.pdf`. Extensões diferentes (`.md` vs `.pdf`) e esquemas de nome diferentes → **impossível colidir** na mesma pasta.
- **Dedupe em disco:** `runPipeline` já monta `existingFilenames` com **todos** os filhos da AI folder (`librarian.ts:66-71`), incluindo `.pdf`. A fase acadêmica reusa esse mesmo Set: antes de baixar, se `{ano}_{slug}.pdf` ∈ `existingFilenames` → pular.
- **Dedupe in-flight:** adicionar a chave acadêmica ao mesmo `inFlightUrls` Set (`librarian.ts:30`). Sugiro chavear por **`doi:<doi-lowercase>`** (mais robusto que o filename, pois o mesmo DOI pode gerar slugs ligeiramente diferentes) **e** reivindicar o filename, cobrindo o TOCTOU como o web já faz (`librarian.ts:75-84`).
- **Slug seguro:** o `{titulo-slug}` precisa ser sanitizado no TS (lowercase, `[^a-z0-9]+`→`-`, truncar ~60 chars) porque vira nome de arquivo e o Rust rejeita filenames com separadores de path (`documents.rs:1121`). Ano ausente no Crossref → usar `unknown` ou o ano corrente como prefixo.
- **Dedupe cross-turno:** o mesmo paper em turnos diferentes cai no `existingFilenames` (disco) do turno seguinte → não rebaixa. Coerente com o comportamento web.

## 7. Desalinhamentos / riscos não mapeados no Task Report

1. **CORS/origin do webview para Crossref/Unpaywall (risco médio, fácil de testar).** O Task Report assume que "Crossref/Unpaywall costumam permitir CORS" — verdade para navegador normal, mas o webview Tauri usa origin `tauri://localhost`. Se alguma delas checar `Origin` além do wildcard, o `fetch` do frontend falha. **Mitigação barata:** testar `fetch` real de dentro do app antes de commitar a arquitetura; se falhar, mover para comandos Rust (o `web_search_route` já é o molde). O planner deve prever esse fork.

2. **Abstract JATS-XML (risco baixo, mecânico).** Quando o abstract vem do Crossref, é XML JATS com tags (`<jats:p>`, `<jats:italic>`). Passar isso cru ao modelo de relevância suja o prompt. Precisa de um strip de tags simples no TS (regex `<[^>]+>` → ``). Não é bloqueador, mas não está no Task Report.

3. **`pdf_extract` só aceita path, não bytes.** Se o Coordenador escolher a Opção 2 do §3b (detectar escaneado antes de salvar), a extração exige gravar o `.tmp` primeiro. Isso muda o fluxo do comando único (baixa→grava tmp→extrai→decide→rename/apaga). Impacto de escopo se a Opção 2 for adotada — sinalizo para não pegar o planner de surpresa.

4. **Latência do sub-pipeline (risco baixo, aceitável).** O caminho acadêmico é serial e lento: query Crossref (1 modelo) → busca Crossref → relevância (1 modelo) → loop Unpaywall por-DOI (com throttle) → downloads de PDF (podem ser MBs). Como roda em background fire-and-forget na cadeia por pasta, o usuário não espera — mas o toast pode aparecer **bem depois** do fim do turno. Coerente com "modo oportunista silencioso", só registrar a expectativa.

5. **Ordem web-depois-acadêmico prolonga a cadeia da pasta (risco baixo).** Se ambos rodam sequenciais no mesmo `runPipeline`, o próximo turno na mesma pasta espera os dois terminarem (serialização por `folderChains`). Já é o design atual para o web; o acadêmico só alonga. Aceitável, mas o planner deve decidir se web e acadêmico rodam sequenciais (mais simples, toast único) ou concorrentes-dentro-da-mesma-etapa via `Promise.all` (mais rápido, mas exige cuidado no scan/toast único e na criação da pasta). **Recomendo sequencial no v1** pela simplicidade e pelo toast somado.

6. **`max_tokens: 300` em `librarian_decide` (`lib.rs:541`) pode ser apertado** se o bloco de candidatos gerar muitos DOIs. Para a etapa de query (1-2 strings curtas) sobra; para relevância com até ~8 DOIs, 300 tokens bastam. Só vigiar se o planner aumentar o número de candidatos Crossref.

7. **Cap de 3 é do turno, não da pasta.** Nada limita o crescimento acumulado da KB entre turnos (mesmo risco já registrado do pipeline web). Fora do escopo v1, mas o volume de PDFs cresce mais rápido que `.md` (arquivos maiores). Só registro.

## Recomendações consolidadas para o planner

1. **Não mexer no Cargo.toml** — reqwest já basta (bytes/redirect/timeout/UA prontos).
2. **Um comando Rust único** `librarian_fetch_and_save_pdf(folder_id, url, filename)`: baixa (UA+timeout, segue redirect) → valida `%PDF` → escreve atômico via helper `write_bytes_atomic` compartilhado com o comando `.md`. Bytes nunca cruzam o IPC.
3. **Dois comandos DeepSeek finos** via `librarian_decide`: `librarian_academic_query` e `librarian_academic_relevance`. Registrar em `generate_handler!`.
4. **Crossref/Unpaywall no frontend** (JSON+CORS), com fork para Rust se o teste de CORS no webview falhar. DOAJ **fora do v1** (baixo retorno para download de PDF).
5. **Estender `runPipeline`** para rodar a fase acadêmica sequencialmente após o web, mesma AI folder, `inFlightUrls` com chave `doi:`, `savedCount` somado, um scan e um `onSaved` só.
6. **Slug sanitizado no TS** (`{ano}_{slug}.pdf`), dedupe por DOI + filename; convive sem colisão com os `.md` do web.
7. **Abrir ao Coordenador:** (a) PDF escaneado — aceitar como arquivo morto (Opção 1, recomendada) vs. detectar antes de salvar (Opção 2, mais código); (b) abstract ausente — julgar por título com barra extra-conservadora (recomendado) vs. buscar abstract externo (fora do v1).

**Nenhum ponto exige parar a análise** — a viabilidade está confirmada; os itens abertos são escolhas de produto de baixo risco que o planner pode apresentar como defaults.
