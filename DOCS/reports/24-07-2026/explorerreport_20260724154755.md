# Explorer Report — Web research via "bibliotecário" (pipeline em background)

Task Report: `DOCS/reports/24-07-2026/taskreport_20260724153714.md`

## 0. Resumo executivo

A remoção da coreografia multi-rodada é **limpa e viável** — `web_search`,
`deep_research` e `update_folder_memory` nunca precisaram encadear rodadas; o
loop existe **só** para o par `read_web_source`/`save_web_source`. Existe uma
versão pré-feature completa desse handler no branch `main` para reverter (§1).

Nível de dificuldade geral: **Média** — a limpeza é mecânica, mas o novo
pipeline tem **três decisões arquiteturais reais** que precisam ser resolvidas
antes do plano:

1. **Ponto de disparo x citações** (§2): "disparar logo após web_search" e "dar
   prioridade às URLs que o modelo citou" são mutuamente exclusivos no tempo —
   quando `web_search` retorna, o modelo principal ainda **não** escreveu a
   resposta. Resolver: disparar no **fim do turno** (`onOpenRouterDone`), não no
   retorno do `web_search`.
2. **Dois caminhos de busca** (§2): o chat tem DOIS pontos onde o web search
   acontece (modelos com tools → dentro do handler; modelos sem tools → bloco
   pré-turno). O pipeline precisa captar dos dois.
3. **Como detectar o modo "explícito"** (§6): sem a tool `save_web_source`, o
   código não tem mais o sinal "o modelo decidiu salvar". Falta definir como
   distinguir explícito x oportunista.

Além disso, dois desalinhamentos com infra "a preservar": a escrita **não é
atômica** hoje (§4) e `containingFolder`/search results **não são acessíveis**
no handler de `onOpenRouterDone` (§2), exigindo um ref de contexto.

## 1. Pontos de corte em `src/hooks/useChat.ts`

### Como era o fluxo ANTES da feature (ao que reverter)
Confirmado por `git show main:src/hooks/useChat.ts`. O handler pré-feature era
**uma única rodada de follow-up**, não recursivo:

- `toolCallHandlerRef.current` fechava sobre o `requestId` da 1ª chamada.
- No início do handler zerava `activeStreamRef.current = null; setIsStreaming(false)`
  (comentário `// Clear streaming state while tool executes`).
- Uma única variável `let toolSearchMessage: ChatMessageInput | null = null`,
  preenchida pelos branches `deep_research`/`web_search`; `update_folder_memory`
  só chamava os setters, sem mensagem.
- Após o loop, montava `toolApiMessages` (system + ephemeral + rag +
  `toolSearchMessage` + history + user), gerava `requestId2 = crypto.randomUUID()`,
  setava `activeStreamRef` para o novo id, **zerava `toolCallHandlerRef.current = null`**
  e disparava `startOpenRouterStreamMessages` **sem `tools`** → força a resposta
  final em texto. Fim. Ou seja: rodada 1 (tools) → tool executa → rodada 2 (texto).

Reverter = restaurar exatamente esse handler. **Nota:** a linha "clear streaming
early" do pré-feature foi a causa raiz do bug #3 (input destravava durante a
tool). Com o pipeline novo o fetch pesado (extract) sai do turno vivo, então o
turno com tools volta a ser curto (web_search → texto). Ainda assim vale
**manter o fix** (não zerar `isStreaming`/`activeStreamRef` no início do handler,
zerar só nos 4 pontos de fim real) em vez de reintroduzir a versão bugada —
decisão do planner, mas recomendo manter o fix.

## 2. Ponto de disparo do pipeline (achado central)

### Os dois caminhos de web search
Existem **dois** lugares onde a busca web acontece — o pipeline precisa captar
de ambos:

1. **Modelos SEM tools** (`!supportsTools`): busca no **bloco pré-turno**
   (`useChat.ts:1934–2014`) via `web_search_route` → `webSearch()`/`runDeepResearch()`.
   Os resultados (`deduplicated`, com URLs+snippets) existem como variável local
   ali, **antes** do modelo streamar. `containingFolder` já foi resolvido? Não —
   `containingFolder` é resolvido só na linha 2030, **depois** desse bloco. (Ver
   ordem no arquivo.)
2. **Modelos COM tools** (`supportsTools`): busca **dentro do handler**, no branch
   `web_search` (2357–2381). `deduplicated` existe ali; `containingFolder` está
   no closure de `send()`.

### Tensão "disparar logo após web_search" x "prioridade por citação"
O Task Report pede as duas coisas:
- (Req.) "disparado por código logo após o resultado de `web_search` retornar";
- (Etapa 2, oportunista) "URLs que o modelo principal citou na resposta ganham
  prioridade".

Elas **não coexistem** no mesmo instante: quando `web_search` retorna (dentro do
handler), o modelo ainda vai gerar o texto na rodada seguinte — as citações
**ainda não existem**. Disparar o pipeline nesse ponto significa não ter as
citações.

**Recomendação:** disparar o pipeline no **fim do turno** (`onOpenRouterDone`),
não no retorno do `web_search`. Nesse ponto:
- a resposta já foi streamada ao usuário (zero latência percebida — requisito
  satisfeito: o pipeline roda "depois");
- o texto final do assistant está em `message.content` (parse de URLs citadas é
  trivial — as URLs vêm dos snippets, então dá pra casar por `includes`);
- os snippets/URLs da busca precisam ter sido **capturados num ref** durante o
  turno (não estão disponíveis em `onOpenRouterDone` senão).

### Obstáculo concreto: `onOpenRouterDone` não vê o contexto de `send()`
Os handlers `chunk`/`done`/`error` são registrados **uma única vez** num
`useEffect` (1641–1738), fora do closure de `send()`. Eles só enxergam
`activeStreamRef.current` (`{requestId, convId, assistantId, model}`) — **não**
enxergam `containingFolder`, `deduplicated`, nem `trimmed` (a pergunta). Para
disparar o pipeline dali, é preciso **stash de contexto num ref por turno**, ex.:

```
librarianContextRef.current = {
  folder: containingFolder,          // precisa webResearchEnabled + id + name
  question: trimmed,
  searchResults: deduplicated,       // snippets + URLs
}
```

populado nos DOIS caminhos de busca (pré-turno e handler), e lido/consumido em
`onOpenRouterDone` (e limpo em error/cancel). Isso resolve tanto o acesso ao
contexto quanto a captura dos resultados.

**Alternativa mais simples (se o Coordenador abrir mão da prioridade-por-citação
no v1):** disparar fire-and-forget de dentro do branch `web_search`/bloco
pré-turno, onde `containingFolder` e `deduplicated` já existem no closure — sem
ref, sem citações. Reduz a feature mas elimina o obstáculo. Decisão do
Coordenador.

## 3. Modelo secundário (DeepSeek via OpenRouter) com saída JSON

**Precedente direto e forte** — não precisa inventar nada:

- `src-tauri/src/lib.rs:401` `deep_research_generate_sub_queries` é exatamente o
  padrão desejado: chamada **não-stream** a `POST /chat/completions` do
  OpenRouter, com **`response_format: { type: "json_schema", json_schema: {..strict..} }`**
  (linhas 421–435), parsing do `choices[0].message.content` como JSON (462–500),
  com fallback tolerante (tenta parsear direto, senão extrai o `[...]`). Retorna
  `Vec<String>` ao frontend via `invoke`.
- `web_search_route` (`lib.rs:560`) é outro precedente: recebe history + mensagem,
  chama o mesmo endpoint, devolve `serde_json::Value` — mostra como retornar JSON
  arbitrário ao TS.
- Frontend chama via `invoke('deep_research_generate_sub_queries', {...})`
  (`deepResearch.ts:31`) — a chamada ao modelo secundário roda **no Rust**, fora
  do stream conversacional. Reaproveitável 1:1.

**IDs de modelo:** hard-coded em constantes no frontend/backend:
`deepResearch.ts:4` `INTERMEDIATE_MODEL = 'openai/gpt-4.1-mini'`,
`:5` `RERANK_MODEL = 'cohere/rerank-4-fast'`; e hard-coded em `lib.rs:619`
(`web_search_route` fixa `"openai/gpt-4.1-mini"`). Não há registro central de
modelos nem exposição ao usuário. O `deep_research_generate_sub_queries` recebe
`model` como **parâmetro** (flexível); `web_search_route` fixa internamente.

**O que falta para plugar DeepSeek:** basicamente nada estrutural. Criar 2
comandos Rust novos (ou 1 genérico parametrizado por prompt+schema) espelhando
`deep_research_generate_sub_queries`, com `"model": "deepseek/deepseek-chat"` (ou
o id DeepSeek escolhido — decisão de sistema, não exposta) e o `json_schema` de
triagem/julgamento. **Atenção:** nem todo modelo no OpenRouter suporta
`response_format: json_schema` strict; DeepSeek suporta `json_object` mas o
suporte a `json_schema` strict varia por rota. Recomendo confirmar o modo exato
(`json_schema` strict vs. `json_object` + prompt) no planning, e manter o
fallback tolerante de parsing que `deep_research_generate_sub_queries` já
demonstra (nunca gravar sem uma decisão parseada — casa com o edge case "JSON
malformado" do Task Report).

**Onde as chamadas devem viver:** manter no Rust (padrão atual) mantém a chave
OpenRouter fora do JS e reaproveita o parsing tolerante. Recomendo um módulo
`src/lib/librarian.ts` (orquestração TS: dedupe, extract em lote, persistência,
feedback) que chama comandos Rust para as 2 decisões-JSON.

## 4. Persistência e anti-corrida

### Assinaturas reais (confirmadas)
Frontend (`src/lib/documents.ts`):
- `documentsEnsureAiFolder(chatFolderId: string, folderName: string): Promise<string>`
  → `invoke('documents_ensure_ai_folder', { chatFolderId, folderName })` (103–105).
- `documentsWriteAiSourceFile(folderId: string, filename: string, content: string): Promise<void>`
  → `invoke('documents_write_ai_source_file', { folderId, filename, content })` (107–113).
- `documentsScanWatchedFolder(folderId): Promise<void>` (115–117).

Rust (`src-tauri/src/documents.rs`):
- `documents_ensure_ai_folder` (1031): sanitiza id (file_name), resolve
  `ai_web_folder_dir`, faz **SELECT idempotente** por `original_path` antes de
  criar (1051–1065), `fs::create_dir_all`, INSERT com `origin='ai'`, `is_external=1`.
  Idempotente por pasta. Bom.
- `documents_write_ai_source_file` (1090): valida vazio/tamanho (`MAX_FILE_BYTES`),
  SELECT `origin` do folder e exige `origin == 'ai'` (1117), valida `filename`
  (file_name + termina em `.md`), e grava.

### Atomicidade — **DESALINHAMENTO com o Constraint do Task Report**
O Task Report exige escrita atômica (temp→rename) "para não deixar `.md` parcial
indexável". A implementação atual **NÃO é atômica**:

```
documents.rs:1129  fs::write(Path::new(&original_path).join(safe_name), &content)
```

`fs::write` cria/trunca o arquivo final e escreve direto — se o app morrer no
meio, sobra `.md` truncado que o scan indexa. **Ação necessária:** alterar
`documents_write_ai_source_file` para escrever num `*.md.tmp` (ou nome oculto) e
`fs::rename` para o nome final (rename é atômico no mesmo volume; o dir é sob
`app_data_dir`, mesmo volume). Isso é uma **modificação na infra "a preservar"**
— o Task Report lista esse comando como reaproveitado sem citar que ele precisa
dessa mudança. Flag para o planner.

### `Set` in-flight + serialização por pasta — onde vive o estado
`ChatFolder` vive em localStorage; o pipeline é frontend. O estado in-flight NÃO
deve ir para localStorage (é efêmero por sessão). Opções:
- **Módulo-level singleton** em `src/lib/librarian.ts`: um `Set<string>` global de
  hashes de URL in-flight + um `Map<folderId, Promise>` para serializar (cada
  novo job por pasta encadeia `.then` no último) — sobrevive a re-renders,
  independe do ciclo de vida do React, e é naturalmente único no app. **Recomendo
  esta.** É o análogo frontend do que o Task Report chama de "Set in-flight +
  serialização por pasta".
- Ref no hook (`useRef`) — não serve: cada painel (`ChatPanel`/`AssistantPanel`/
  `ReaderChatPanel`) tem sua própria instância de `useChat`, então refs não são
  compartilhados entre eles; dois painéis poderiam extrair a mesma URL. O
  singleton de módulo cobre isso.

O dedupe TOCTOU do Task Report (dois pipelines checando "existe?" antes de gravar)
é coberto pelo `Set` in-flight de módulo (checagem em memória antes do extract) +
o SELECT `alreadySaved` já existente em disco. O `documents_ensure_ai_folder`
idempotente evita corrida na criação da pasta.

## 5. Feedback de UI "N fontes salvas"

**Padrão pronto para copiar** — o "memory toast" é exatamente isto:

- `useChat.ts`: estado `folderMemoryUpdatedAt: number | null` (879, 940),
  setado com `Date.now()` quando a memória muda (2386), exposto no retorno (2700).
- `ChatPanel.tsx`: consome `folderMemoryUpdatedAt` (81), `useEffect` que dispara
  um toast por 4s (218–223), e o JSX do toast reusando `styles.webSearchProgress`/
  `styles.webSearchDot` (498–503, texto "Folder memory updated").

É **exatamente** um "evento de UI não-textual emitido por processo de background",
não uma mensagem do modelo — o que o Task Report pede. Replicar: um estado tipo
`webSourcesSaved: { count: number; at: number } | null` no `useChat`, setado pelo
pipeline ao concluir, consumido por um `useEffect` em `ChatPanel` mostrando
"N fontes salvas na base de conhecimento". **Nenhuma infra de toast nova
precisa ser criada.** (Como o pipeline vive num módulo e o setter é do hook,
passar o setter/callback ao pipeline resolve o acoplamento — ou o pipeline expõe
um callback `onDone` que o hook liga ao setter.)

Para o **modo explícito com falha visível**: o mesmo canal serve, com uma
variação de mensagem de erro (ex. reusar `setError`, que já existe e é exibido).

## 6. Desalinhamentos / riscos não mapeados no Task Report

1. **Detecção do modo "explícito" perdeu seu sinal.** Antes, "o modelo decidiu
   salvar" era o próprio `save_web_source`. Sem tool, o código não sabe mais se o
   usuário pediu "salva isso". O Task Report descreve os dois modos mas não diz
   **como** o código decide qual rodar. Opções: (a) a própria chamada de triagem
   DeepSeek recebe a pergunta e classifica intent (explícito/oportunista) junto,
   (b) reusar o `intent` do `web_search_route` (mas ele não tem categoria "salvar"),
   (c) heurística de keywords. **Precisa de decisão do Coordenador.**

2. **Prioridade por citação exige disparo no fim do turno** (§2) — conflita com
   "disparar logo após web_search". Reconciliar antes do plano.

3. **Escrita não-atômica hoje** (§4) — o comando "reaproveitado" precisa de
   mudança para cumprir o Constraint de atomicidade.

4. **`onOpenRouterDone` não tem o contexto de `send()`** (§2) — exige um
   `librarianContextRef` por turno; não é trivial "só chamar uma função".

5. **Dois caminhos de busca** (modelos com/sem tools, §2) — o pipeline precisa
   ser alimentado dos dois; fácil esquecer o caminho pré-turno (modelos sem tools),
   que é o único onde web search roda para esses modelos.

6. **Feedback cruza a fronteira módulo↔hook.** O pipeline (módulo) precisa
   sinalizar a UI (estado do hook). Resolver via callback passado ao pipeline ou
   um pequeno event-emitter — decisão de design menor, mas explicitar.

7. **Corrida save↔RAG** (fonte salva em background pode não estar indexada no
   turno seguinte) — já reconhecida como aceitável no Task Report; confirmo que o
   código atual (`documents_scan_watched_folder` fire-and-forget + `run_indexing`
   com chamada de rede de embeddings) tem exatamente essa janela. Sem ação, só
   registro.

8. **Custo do gate por flag:** o Task Report exige que NENHUMA chamada ao
   secundário aconteça com a flag desligada. Como o pipeline dispara no fim do
   turno e lê `containingFolder.webResearchEnabled` do ref, o gate é um `if` no
   início do pipeline — trivial, mas precisa estar ANTES da chamada de triagem.
