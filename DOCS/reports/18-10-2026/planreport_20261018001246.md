## Escopo

Os 18 requisitos foram divididos em 17 etapas, cada uma executável por um único `codeAgent`, e em 5 checkpoints de teste do Coordenador (CP-A a CP-E):
- **Parte A (RAG):** golden set, consulta com histórico, metadados por chunk com reindexação única, fontes, inspetor, busca híbrida, rerank, roteamento, OCR e higiene.
- **Parte B (Assistant):** ícones, seletor de pasta, conjuntos de documentos, salvar em nota, apelidos, espaçamento e paridade com o Chat.

Cada etapa compila e deixa o app funcionando.

**Arquitetura escolhida (vale para todas as etapas):**
- **A recuperação passa a morar em Rust, num módulo novo `src-tauri/src/rag.rs`** (`pub mod rag` em `lib.rs`).
  - Ele concentra: escopo, KNN, FTS5, RRF, reescrita da consulta, rerank, pesos, limiar e trace.
  - O frontend só orquestra o turno: gating, montagem do prompt, fontes na mensagem e UI.
  - **Motivo:** o golden set precisa rodar **o mesmo código** que o app, como script de linha de comando executável por agentes e pelo Coordenador. Por isso ele é um *cargo example* que linka `monet_lib`. Um runner em TS dependeria de devtools e de um humano.
- **Os metadados ficam no `monet-vec.db`**, onde já moram `chunks_meta` e `vec_chunks` e que é aberto só pelo rusqlite em `vec_db::init`:
  - colunas novas em `chunks_meta`;
  - tabela `doc_index_state`;
  - FTS5 `chunks_fts`.

  Assim **nenhum `ALTER` é feito na tabela `documents`** (criada pelas migrations do tauri-plugin-sql): isso evita a corrida de primeira instalação.
- **As tabelas novas do `monet.db`** (`folder_aliases`, `document_sets`, `image_ocr_cache`) são todas `CREATE TABLE IF NOT EXISTS` em `open_doc_db`.
  - Nenhuma depende de `documents` existir, e não há número de migration (constraint do Task Report).
- **Uma única reindexação completa (Etapa 8)**, depois de tudo que muda o texto ou os metadados dos chunks:
  - higiene (E5), cabeçalhos (E6), OCR (E7) e apelidos (E2).
  - O FTS5 (E9) é preenchido a partir de `chunks_meta`, sem custo de API, e por isso pode vir depois.

## Golden set — formato, local e acesso ao banco

**Local, sempre fora do repositório:** `%APPDATA%\com.monet.app.dev\rag-eval\`
- `goldenset.json`: perguntas e gabarito. É escrito pelo orquestrador e marcado pelo Coordenador.
- `candidates.md`: ajuda para marcar o gabarito, gerada pelo script.
- `results\<YYYYMMDDHHmmss>-<label>.json`: resultado por pergunta, só com ids e posições, sem conteúdo.
- O resumo numérico (recall/MRR por classe) pode ir para o Execution Report: são números, sem dados de trabalho.

**Formato de `goldenset.json`:**
```json
{
  "version": 1,
  "k": 5,
  "questions": [
    {
      "id": "q01",
      "class": "document",
      "question": "qual é a especificação da Migração?",
      "history": [
        { "role": "user", "content": "texto do turno anterior" },
        { "role": "assistant", "content": "resposta anterior" }
      ],
      "scope": {
        "ids": ["<id de pasta ou arquivo da KB>", "notes-folder:<notebookId>"],
        "notebookId": null,
        "includeAiFolders": false,
        "excludeNoteId": null
      },
      "expected": [
        { "documentId": "note:<noteId>", "label": "Especificação (Notes — Migração)" }
      ],
      "confirmed": false,
      "comment": ""
    }
  ]
}
```
- `class` é um destes valores: `follow-up | exact-term | document | temporal | sweep | image`.
- `history` é opcional. Os turnos vão em ordem cronológica e são obrigatórios na classe `follow-up`.
- O `scope` repete o que o chat faz:
  - os `ids` são ids de visibilidade (arquivo ou pasta da KB), expandidos como no `resolveSearchableIds`;
  - `notebookId` corresponde a uma pasta de chat vinculada a um caderno e inclui a pasta de notas dele.

  O escopo é expresso em ids da KB (que vêm no `monet.db` clonado), e não em ids de pasta de chat, porque o chat do perfil dev não tem o localStorage de produção.
- O gabarito é **por documento** (`documentId`), não por chunk: os rowids mudam na reindexação, os ids de documento não.
- O orquestrador propõe o `expected` a partir do `candidates.md`. O Coordenador corrige e muda `confirmed` para `true`.
- O script só pontua as perguntas com `confirmed: true`.

**Métricas** (por pergunta, médias por classe e geral):
- Lista ranqueada de documentos: os `document_id` dos chunks selecionados (top-k no baseline, os selecionados no pipeline completo), sem duplicatas e na ordem da 1ª ocorrência.
- `recall@k` = |esperados ∩ docs do top-k| / |esperados|.
- `hit@k` = 1 se algum esperado aparece no top-k.
- `MRR` = 1/posição do 1º esperado na lista (0 se nenhum).

**Acesso ao banco (só DEV):**
- Os examples resolvem `%APPDATA%\com.monet.app.dev\` via `std::env::var("APPDATA")` e abrem `monet.db` e `monet-vec.db` **somente leitura** (`OpenFlags::SQLITE_OPEN_READ_ONLY`).
- A chave vem de `%APPDATA%\com.monet.app.dev\openrouter_key`, o mesmo arquivo que `read_key` usa no perfil dev.
- Qualquer caminho resolvido que não contenha `com.monet.app.dev` aborta o script.
- O modo WAL permite ler com o app dev aberto.

**Uso (rodar de `src-tauri/`):**
- `cargo run --example rag_eval -- init`: cria o `goldenset.json` modelo, com 2 perguntas fictícias, se ele ainda não existir.
- `cargo run --example rag_eval -- candidates`: para cada pergunta não confirmada, lista os 15 melhores documentos (id, nome, pasta e 200 caracteres do melhor trecho) em `candidates.md`.
- `cargo run --example rag_eval -- run --label baseline --pipeline baseline`
- Na E10 entram `--pipeline full`, `--no-rewrite`, `--no-fts`, `--no-rerank` e `--threshold <f>`.

## Riscos e limitações

- **Clonar prod para dev (E1/CP-A).** Sem a reescrita de caminhos, o app dev **apagaria arquivos de produção**: `notes_index_upsert` remove `old_path`, `documents_delete` remove arquivos não externos e a exclusão de pasta `ai` usa `remove_dir_all`.
  - A verificação "0 caminhos com `\com.monet.app\`" é obrigatória, com o backup do dev antes.
  - Os caminhos de pastas monitoradas externas (DOCS do repo, VOLP) são compartilhados com a produção. O dev só os **lê**: o scan não apaga arquivo externo.
- **Baseline contaminado.** Rodar o app dev com o código da E6 em diante antes do CP-A reindexa as notas sozinho. A regra de gate cobre isso.
- **Classe "sweep" do golden set.** As varreduras ("todas as reuniões", "liste os projetos") pedem contexto longo ou map-reduce (I6 no estudo). O Task Report só pede as tools `get_day`, `notes_by_date` e `search_knowledge_base`, então essa classe deve continuar fraca. **Não está no escopo;** se o Coordenador quiser, vira uma task futura.
- **Cota do localStorage.** `ragSources` compactos somam cerca de 1–2 KB por resposta com RAG, e o chat já usa cerca de 3,8 MB de 5–10 MiB. Por isso o trace do inspetor fica só em memória. O aviso de cota já é uma pendência conhecida (memória do projeto) e não entra aqui.
- **OCR via WinRT.** Inicialização de apartment, ou idioma ausente. A E7 tem o fallback `RoInitialize`, e a falta de engine devolve `None` sem gravar no cache. O base64 de vários MB atravessa o IPC uma vez por imagem (cache por hash).
- **`cargo` examples linkam o `monet_lib` inteiro.** O primeiro build é demorado. Nenhum binário novo entra no `tauri build`, porque examples não são empacotados.
- **Custo.** A reindexação custa cerca de US$ 0,08 (estudo). Cada consulta passa a custar cerca de US$ 0,0003 (reescrita) + US$ 0,001–0,002 (rerank). Cada rodada do golden set full custa centavos.
- **O rerank Cohere em pt-BR com limiar 0,2 é um chute inicial.** O ajuste fino sai do golden set (CP-C). Se o limiar cortar demais, o sintoma é "nada relevante" frequente.
- **Notas e reindexação em produção.** Ao instalar a versão nova, a reconciliação reembute todas as notas no primeiro start (minutos, em série). Os arquivos esperam o botão. Durante a transição, o índice é misto (antigo e novo), mas segue pesquisável.

### D1 — Clonar os dados de produção para o perfil dev para o golden set e a reindexação?
- **Por que importa:** o golden set usa perguntas reais e precisa da base real. A reindexação e o "depois" só podem ser medidos onde ela roda: o app dev.
- **Opções:**
  - **A) Clonar com o `clone_prod_to_dev` (E1).** Copia os bancos e as pastas, reescreve os caminhos e faz backup do dev.

    - Contra: o dev passa a ter os dados de trabalho (local, fora do repo); o dev atual vira backup.
    - Se der errado: a verificação aborta e restaura o backup. A produção nunca é aberta para escrita.
  - **B) Snapshot somente leitura da produção só para o baseline.**
    - A favor: zero risco de escrita.
    - Contra: o "depois" não é mensurável na mesma base; perde-se o efeito da reindexação.
  - **C) Golden set sobre os dados do dev atual.**
    - A favor: simples.
    - Contra: as perguntas deixam de ser "reais"; os números perdem valor.
